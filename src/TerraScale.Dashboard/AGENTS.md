# ts-dashboard


- .NET 11, RazorSlices and Datastar. Use the official Stripe.net library. Store dashboard state in relational tables through the TerraBase EF Core provider (`docs/dashboard/state-storage.md`). Reach TerraBase's product APIs over MagicOnion through the shared contracts library, never a TerraBase project or binary.
- Dashboard data lives in relational tables of the `ts-dashboard` database through `DashboardDbContext` and the TerraBase EF Core provider (`docs/dashboard/state-storage.md`); it is the only storage path, and a lost concurrency race surfaces as `DbUpdateConcurrencyException`. Accounts and organizations go through `AccountStore` and `OrganizationStore` only: read the aggregate, change the record, save it with its root `version`; an erased row carries `erasure_id`. One table per migration, generated through `src/TerraScale.Dashboard.EntityFrameworkDesign`; request paths save with one `SaveChangesAsync` and no explicit transaction; ULID keys, foreign keys, unique indexes and check constraints carry the invariants.
- Read-modify-write on stored state must be idempotent and conflict-retrying: reread the row, apply the change to what is stored now, skip the save when nothing differs, and on `DbUpdateConcurrencyException` reread and apply again. Creates are insert-or-get (a unique-key loss rereads the winner's row). A change many requests make at once (sign-in audit events, first-sign-in provisioning) must commute or be a no-op when the state already matches, never a counted retry loop that two tabs, a double-click or a callback retry can exhaust. A conflict that still can't be resolved answers a retryable `409`, never `500`; never swallow it.
- `src/TerraScale.Dashboard/` contains `Features/`, `Platform/`, `UI/` and `web/`. Keep each product area's components and abstractions together. The SDK source lives in `sdk/dotnet/` and is consumed through ProjectReference.
- Own dashboard authentication integration, MCP, organizations, projects, users, billing, plans and Stripe management. Identity belongs to ts-auth; usage metrics and regional availability/latency come from TerraBase.
- Production uses persistent TerraBase state and ts-auth authorization. Runtime demo paths are implementation gaps, not deployment requirements. The journey (`e2e/`) covers account creation and customer-SDK database round trips end to end against a real TerraBase built from the same commit.
- The signed-in dashboard is dark-only; only the signed-out organization picker (`/organizations/choose`) ships a light theme.
- Build: `make dashboard-build`. Lint: `make dashboard-lint`. Full validation: `make dashboard-check`. The journey in `e2e/` is the only test: it drives every dashboard page against the real TerraBase and ts-auth (`e2e/AGENTS.md`).
- Asset commands: `make -f scripts/dashboard/Makefile css`, `make -f scripts/dashboard/Makefile js`, `make -f scripts/dashboard/Makefile check-css`. Bundle CSS with Lightning CSS into one shipped stylesheet; committed assets must match their sources.
- Serve logos, wordmarks and favicons from committed SVG files, including auth pages, app shell and metadata. Never inline their path/polygon data in templates, styles or components.
- Use `dotted-map` only for maps. Load map code/data only where needed. Accessible controls are the canonical input; include machine-readable map data in the SVG.
- Every map is the one shared region map component: slice `Common/UI/Slices/RegionMap.cshtml`, model `Common/UI/RegionMapModel.cs`, styles `Common/UI/region-map.css`, script `web/assets/js/region-map.js` with the dot data `web/build/generate-region-map.mjs` writes. It has two modes, `select` and `read-only`, and renders every map: creating a database, a database's regions, overview, analytics, sign-in, onboarding and project regions. Change its look or motion in those files only; never build a second map, a per-screen map style or a per-screen map script.
- Regions are equal: the dashboard never shows or names a home, primary or replica region. A database has one set of regions with at least one selected, and `Features/Databases/DatabasePlacementEndpoints.cs` derives what TerraBase's placement operations need from that set.
- Every feature is always on. Do not add feature flags, activation settings, deploy toggles, kill switches or tuning knobs. Keep one correct value in code. CI allowances for unavoidable third-party switch names need a one-line reason. No fakes, demo stores or skip-auth.
- Discover authentication, database and orchestrator endpoints automatically. Every region serves automatically after NetBird admission, discovers all regions and infers its own region without an enable step.

- The existing official Stripe.net dependency may transitively bring Newtonsoft.Json; direct Newtonsoft package references and API usage remain banned.

- Treat TerraBase, ts-auth and stored data as untrusted input: never `ToDictionary`/`Add` keys or pass values to `ArgumentException`-throwing BCL calls without checking first (`TryAdd`, `TryParse`, range tests), and reject a bad response as the area's `JsonException` or validation failure. See `docs/dashboard/analytics.md#platform-data-and-optional-panels`.
- Optional page parts (sync, metrics, analytics) load through `OptionalPanel`, which renders the page with the part's notice and logs EventId 44 with code frames. Required reads never go through it; add no other broad `catch (Exception)`.
