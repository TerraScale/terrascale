# TS-1429: Terminal API-key lifecycle and step-up qualification

## Question

Can a terminal (`ts` CLI or equivalent HTTP) client create, list and revoke API
keys, with a revoked key refused within 60 s, using only an **existing**
terminal/native step-up path — without new auth design and without relaxing
step-up?

## Answer

The key lifecycle itself is fully served by the existing ts-auth management API,
including its step-up gate. **No contract gap exists for the API surface.**
What does not exist is the terminal *UX*: no installed CLI command performs the
step-up approval loop, so a terminal-only client (no browser aid) cannot get
past `403 step_up_required` for create/rotate today. That is a CLI feature gap,
not an auth contract gap, and it is the only remaining auth-owner decision.

## Source map (origin/main 06892e828)

- `sdk/go/tsauth/management.go:477` `CreateAPIKey` →
  `POST /v1/terrascale/organizations/{org}/projects/{project}/api-keys`;
  `:518` `RevokeAPIKey` → `DELETE …/api-keys/{key}`;
  `:524` `RotateAPIKey` → `POST …/api-keys/{key}/rotate`;
  `:498` `APIKeys` (list) → `GET …/api-keys`.
- `src/TerraScale.Authentication/Features/Platform/ApiKeyEndpoints.cs:265` and
  `:312`: create and rotate call
  `StepUpProofs.ConsumeHeaderAsync(..., "create_api_key"/"rotate_api_key", ...)`
  before any mutation. List (`:271`), get (`:281`), revoke (`:290`) and
  allowed-CIDRs (`:319`) consume no proof.
- `src/TerraScale.Authentication/Features/Platform/StepUpProofs.cs:248` `Pair`:
  `create_api_key` and `rotate_api_key` are valid **with audience `ts-auth`**
  (not `ts-dashboard`). Proof: 5-minute expiry, single use, purpose+audience
  bound, approved only by fresh primary credentials on the hosted page.
- `POST /v1/terrascale/step-up` (`RequestStepUpEndpoint.cs`) accepts a
  management bearer token and returns `{proof, step_up_url, expires_at}`; the
  proof is then sent on the sensitive call in `X-TerraScale-Step-Up-Proof`.
- `ConsumeStepUpEndpoint.cs` (the `ts-dashboard` bridge) is restricted to
  `create_pat` and `delete_account` and is **not** needed for API keys: the
  proof for `create_api_key`/`rotate_api_key` is consumed at the key endpoint
  itself (`ApiKeyEndpoints.cs:265,312`).
- `sdk/go/cmd/ts/keys.go:86` maps `step_up_required` to the dashboard API-keys
  URL; there is no terminal step-up implementation anywhere in the Go SDK
  (`ErrStepUpRequired` at `tsauth/management.go:549` is only an error code).

## Rotate: source-confirmed, live attempt bounded

`RotateApiKeyEndpoint` (`ApiKeyEndpoints.cs:312`) requires purpose
`rotate_api_key`, audience `ts-auth`, same proof mechanics as create; the CLI
(`keys.go:32` `rotateKey`) already validates the sensitive success response
and preserves no-remote-message/no-secret-error guarantees. My live rotate
attempt was stopped after two bounded device-grant timeouts (rate/attempt
budgets; per instructions no retry loop), so rotate is **source-confirmed
only**, not live-proved here. Create's live proof exercises the identical
request/approve/consume mechanics, differing only in the purpose string.

## What is proved vs what remains

Proved live, unchanged production behavior, this identity only:

1. list/get/revoke need no step-up; create needs one;
2. `POST /v1/terrascale/step-up` + hosted approval + proof header authorizes
   `create_api_key` for the CLI's own device-grant bearer, single use;
3. revoke removes the key and the revoked secret gets `401 invalid_client`
   within 0–55 s at the token endpoint.

Remaining (auth/CLI owner, not qualification): a terminal-only step-up UX.
Today the approval must happen in a browser session on
`auth.terrascale.tech/ui/terrascale/step-up/{id}` (fresh password or emailed
code; `StepUpHosted.cs`). The CLI prints the dashboard URL instead
(`keys.go:86-91`). Whether the CLI should open the hosted step-up URL
directly (it needs a hosted sign-in session, which the CLI device flow does
not create), or another existing-native mechanism qualifies, is a product
decision in the auth lane; this ticket deliberately does not design it.

## Untested parts

- `rotate_api_key` live (bounded attempt stopped; source-confirmed only).
- Organization-level keys (`/organizations/{org}/api-keys` without project):
  same endpoint family, not exercised.
- MFA-enabled accounts: hosted step-up requires an active factor; the
  synthetic identity has none.
