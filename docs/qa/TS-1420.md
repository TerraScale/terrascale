# TS-1420: psql to a non-home region without replicas answered "database does not exist"

## Question

Why does `psql` to `sjc.pg`/`fra.pg` fail with "the database does not exist" for a database with
home `gru` and `replicaRegions: []`, when `docs/terrabase/cross-region.md` ("Forwarding to the
home") promises the session is relayed to the home for its whole life? Where is the precise
routing/auth contract gap, if any still exists?

## Answer

**The reported symptom no longer reproduces.** Home-region whole-session Postgres relay shipped in
`5c9a7a62f` on 2026-11-04 05:06Z; the TS-1405 report of 2026-11-04 predates or coincides with that
ship window, and live behavior on 2026-11-05 matches the documented contract for a **ts-auth
dashboard API key**: all three regional pg hosts serve a GRU home-only database.

Two real, narrower observations remain for the engine owner:

1. **Credential-kind gap (observed in source, live NOT TESTED).** `PostgresConnectionHandler.
   AuthorizeAsync` (src/TerraBase/Features/Postgres/PostgresConnectionHandler.cs:286-300) resolves
   **local operator-issued** API keys (`IApiKeyStore.FindAsync`, local catalog only) and returns
   `28P01 password authentication failed` on a local miss — it never calls `ElsewhereAsync` and so
   never relays. Only the ts-auth dashboard-key path (`AuthorizeDashboardKeyAsync`, :302-374) falls
   through to `ElsewhereAsync` (:376) on project/database `NotFound`. A local operator key that is
   valid in the issuing region therefore cannot reach its database from another region. The
   documented public contract (transport-security.md "PostgreSQL clients authenticate with an API
   key"; cross-region.md "any region serves any database") does not scope the promise to dashboard
   keys only.
2. **Unreachable/unasked home masquerades as absence (observed in source).** `ElsewhereAsync`
   (:376-379) asks `IHomeLocator.LocateAsync` and answers `3D000 the database does not exist in
   this project` when the locator returns null. `HomeLocator.LocateAsync`
   (src/TerraBase/Features/Regions/HomeLocator.cs:31-58) returns null both when **no peers are
   configured** (`others.Count == 0`) and when **every peer errors or times out** within 3 s
   (`AskAsync` swallows `HttpRequestException`/`OperationCanceledException`, :76-78). A region with
   a dead mesh thus reports a *proved-absent* database instead of an availability failure, which
   the docs separate as `FATAL 08001`. This can only mislead, never leak; it is the same class of
   answer `HomeForwarding` avoids for REST by returning `421 wrong_region` with the home named.

Neither is the reported defect; the reported defect (dashboard key, all regions reachable,
`3D000`) is fixed by the existing relay, and one Slow integration test already covers the journey.

## Source map (origin/main f1169c708)

- `src/TerraBase/Features/Postgres/PostgresConnectionHandler.cs`
  - `AuthenticateAsync` :195-251 — password is the API key; `HomeNode` access becomes a
    whole-session `Relay` (:219-222), `ServeConnectionAsync` :74-77 hands it to `PostgresRelay`.
  - `AuthorizeAsync` :273-301 — **credential dispatch**: `TsAuthKeyExchange.IsKey(secret)` (shape
    `<26-char ULID>_<secret>`) selects the dashboard-key path; everything else resolves against the
    **local** catalog (`Keys.FindAsync`) and answers `Denied` (`28P01`) on a local miss — no
    `ElsewhereAsync`, no relay (observation 1).
  - `AuthorizeDashboardKeyAsync` :302-374 — ts-auth exchange, IP allowlist, key-liveness, then
    `Tenants.FindDatabaseAsync`; `NotFound` for project (:339-342), narrowed (:356-359) or database
    (:371) falls through to `ElsewhereAsync`.
  - `ElsewhereAsync` :376-379 — relay only when `!relayed` and the locator answers a home;
    otherwise `3D000 the database does not exist in this project` (observation 2).
- `src/TerraBase/Features/Regions/HomeLocator.cs` :23-58 — asks every other region over the
  internal listener (`GET /v1/internal/home`, peer credential, 3 s budget), caches 30 s; returns
  null on no peers and on all-peers-failed (:31-35, :76-78).
- `src/TerraBase/Features/Postgres/PostgresRelay.cs` :43-111 — duplex HTTP/2 `POST
  /v1/internal/postgres` to the home with the peer credential and the original startup (including
  the secret) replayed; the home re-authenticates. Unreachable home → `FATAL 08001` naming the
  region (:113-129). Untouched by this ticket.
- `src/TerraBase/Features/ApiKeys/EngineApiKeyStore.cs` :44-69 — `FindAsync` reads only the local
  system catalog (observation 1's mechanism).
- `docs/terrabase/cross-region.md:51-55` — the promise: relay for the session's whole life,
  `FATAL 08001` unreachable home, `FATAL 3D000` database that exists in no region.
- Existing integration test: `tests/TerraBase.Slow/Platform/HomeRegionForwardingTests.cs:17`
  "Rest_and_postgres_in_other_regions_reach_the_database_home..." drives fra → home with a
  dashboard key over the Postgres wire (`PostgresSql.Source(fra, DashboardKey(...), ...)` :41).

Timeline: relay + locator + docs shipped together in `5c9a7a62f` (2026-11-04 05:06Z); the
`3D000` message for the else-branch predates it (`2020a18ee`, 2026-11-04 06:42 shows it already
present with relay). The TS-1405 finding (2026-11-04) is consistent with a pre-relay deployment or
with observation 1/2 above; it cannot be reproduced today through the public interface.

## Owner decision (one)

Engine owner: when `ElsewhereAsync` cannot **prove** absence (no peers configured, or every peer
unreachable/timed out), should the Postgres answer distinguish availability from absence — e.g.
answer `57P03`/`08001`-style retryable instead of `3D000` — and should the local-operator-key path
(`28P01` without any home lookup) either relay or be documented as region-bound? Both are
engine/forwarding code and were intentionally not changed by this qualification.
