# TS-1383: dashboard merged-but-undeployed

## What was observed

- Live `https://dash.terrascale.tech/readyz` reported `x-terrascale-revision: 47024c8708c6a2d7ccae4d52d5f449cabfe471ea` (Oct 30) while `origin/main` was at `f650baa42bd9466abea7eccb478690f407eb8c43` (Nov 3): 18+ dashboard commits merged but not deployed.
- The newest `dashboard/qualified-*` release was `dashboard/qualified-47024c8708c6a2d7ccae4d52d5f449cabfe471ea` (Oct 30 18:22Z). `docs/qualified-*` releases kept flowing every few hours.
- Every later Images (GHCR) run reported `deploy=false` in the `ready` gate.

Commands:

```sh
curl -s https://dash.terrascale.tech/readyz -D- -o /dev/null | grep -i x-terrascale-revision
# x-terrascale-revision: 47024c8708c6a2d7ccae4d52d5f449cabfe471ea
gh release list -R TerraScale/terrascale --limit 15 --json tagName,createdAt
gh run view 41611396545 -R TerraScale/terrascale --json jobs   # ready: success, test/image: skipped
```

## Root cause (four stacked failures)

1. **The release gate requires a per-revision dev-host qualification that nothing automated.**
   `.github/workflows/images-ghcr.yml` only publishes when the exact main SHA carries a
   `dashboard-release/dashboard` success status by MarioGK plus a `dashboard/qualified-<sha>`
   release with the verified application bytes. That status/release is created only by
   `scripts/dashboard/prepare-deployment.sh`, which no workflow or hook invoked after the
   Oct-30 monorepo import (the standalone `ts-dashboard` repo's workflow did not map to it).
   Docs solved this with a ts-ship hook (`docs-release` phase running
   `docs-site/scripts/qualify-built.sh`); the dashboard never got the equivalent.

2. **Dev-host podman was broken, so even manual qualification failed.**
   Both `delta` and `mariogk-dev` had `/etc/containers/storage.conf` pointing rootless podman
   at rootful paths (`/run/containers/storage`), so every podman command died with
   `default OCI runtime "crun" not found` / `mkdir /run/containers: permission denied`.
   `audit-runtime-images.py` (inside `prepare-deployment.sh`) was the first casualty.
   Fixed with `~/.config/containers/storage.conf` (user graphroot/runroot) on both hosts.

3. **A Nov-3 commit broke release-check lint on main.**
   `09e042699` left a two-line anonymous-object initializer in
   `tests/TerraScale.Dashboard.E2E/Features/Home/HomeReportingJourneyTests.cs` that
   `dotnet format --verify-no-changes` rejects when the check runs without `BASE_SHA`
   (which is exactly how the release qualification runs it). Dashboard Fast does not run
   the format check (it is behind `make -f scripts/dashboard/Makefile check` in the
   qualification), so main stayed green while the release path was broken.

4. **The regions' release verifier rejects the workflow_run event, so the only automated run
   whose gate could pass could never release.** ts-orchestrator's
   `internal/releasepush/oidc.go` accepts a run's GitHub OIDC token (the release credential —
   CI holds no secret) only from `push` and `workflow_dispatch` events. The `push`-event
   Images run evaluates its gate seconds after the push, while CI is still running, so it
   always reported `deploy=false`; the `workflow_run`-event run (fired after CI) passed every
   GitHub-side check and was then refused by NATS in every region
   (`nats: Authorization Violation`). The Oct-30 release worked only as a manual
   `workflow_dispatch` — the exact manual step this ticket removes.

## Fix

- `ts-ship` (delta + mariogk-dev, identical SHA-256): a green dashboard Fast now runs
  `scripts/dashboard/prepare-deployment.sh` on the dev host in a new
  `@@TS_SHIP_PHASE dashboard-release` phase (900 s budget), publishing
  `dashboard/qualified-<sha>` and the `dashboard-release/dashboard` status before main is
  pushed — mirroring the existing docs-release automation. Carried Fast proofs never
  substitute for release bytes (a carried proof without the release status is discarded).
  Dashboard release-workflow diffs (`dashboard-ci.yml`, `images-ghcr.yml`) map to the
  dashboard area, so pipeline changes ship with full dashboard qualification.
- `.github/workflows/images-ghcr.yml`: the `ready` gate of the push run now waits up to
  15 minutes for its commit's CI, then deploys when the revision is still current green
  main qualified by MarioGK — a token the regions' verifier accepts. The `workflow_run`
  run never deploys (it validates nothing new; its token can never release).
- `tests/.../HomeReportingJourneyTests.cs`: formatting fix so the release check passes.
- `docs/dashboard/development.md`: the deployment path description states which run
  deploys and why; `scripts/dashboard/workflows-reference/images-ghcr.yml` synced.

With the qualification status on the exact green main SHA, the Images (GHCR) push run
(`ready` → `test` → `image` → release to every region → `verify-live.py`) deploys
automatically; there is no deploy switch or manual dispatch in the path.
