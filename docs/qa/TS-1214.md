### Why export schedule parity is missing (deletion provenance)

`git log --all -S get_export_schedule` and `-S ExportSchedule` converge on the E4b
SQL-first pivot. `git show b6323eeb2 -- .../BackupMcpTools.cs` deletes:

- `get_export_schedule` (read the project's own backup bucket + database's scheduled NDJSON export + last run)
- `set_export_schedule` (5-field UTC cron NDJSON export scheduling)
- `BackupService.ExportAsync` and `ExportScheduleView`/`BackupExportView` models.

The commit message states: "Removed: … NDJSON export and scheduled bucket
exports". No successor tool exists: the only remaining "export" surfaces are the
auth-management users export (`/api/v1/auth-management/users/export`) and audit
NDJSON export (`/audit/export`), which are different products. Any ticket
claiming missing export-schedule parity against current main is therefore
OBSOLETE-by-design (E4b), not a regression. TS-1194's nullable-output failure can
no longer reproduce on main because the tool is gone.

### Plan allowance facts (source)

- `DatabaseService.DatabaseLimit` (`Common/Databases/DatabaseService.cs:486`) reads `PlanCatalog.ResourceLimits(org)`; `pricing.json` plans: free=1, starter=5, pro=25, team=100, enterprise=null (unlimited).
- `DemandRoom` (line 494) throws 409 "reached its plan's database limit" when `Databases.Count >= limit`.
- Free plan with 1 existing database → any restore-as-new, PITR restore or branch is denied 409 before any producer call (`BackupService.cs:126-127`, `WholeDatabaseRecovery.cs:82-83`). This denial is correct product behavior, not an outage.
