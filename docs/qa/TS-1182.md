# TS-1182 — fresh 3-region database shows HEALTHY 0 / DIVERGED 1 / STOPPED 2 with minutes of "worst lag" and a stuck "Loading" regions panel

Date: 2026-11-03 · Scope: dashboard Home replication classification · Verdict: presentation bug in the dashboard over a producer route that TerraBase deleted.

## What was run

```sh
for h in api gru.api sjc.api fra.api; do
  curl -sS "https://$h.terrascale.tech/v1/projects/<id>/replication?range=24h" \
       -H 'authorization: Bearer <project-token>'
done
```

## What was seen

Every region answers:

```
HTTP/1.1 404
{"error":{"code":"unknown_route"}}
```

TerraBase commit `440e54abc` ("refactor(terrabase): remove legacy protocols, webhooks and leaderless replication", 2026-10-29) deleted the producer side of that route:

```
src/TerraBase/Features/Management/Usage/GetProjectReplicationEndpoint.cs   | 29 -
src/TerraBase/Features/Management/Usage/GetDatabaseReplicationEndpoint.cs  | 29 -
src/TerraBase/Features/Health/ReplicationHealth.cs                          | 61 -
src/TerraBase/Features/Health/ReplicationHealthEndpoint.cs                  | 30 -
```

Before that commit the endpoint's contract was (from its own summary text): *"Unknown or stale observations are **stopped with null lag** and divergence."* The dashboard's Home counted those rows verbatim (`CountStatus(regions, "stopped")`), so a fresh database whose regions had never reported rendered STOPPED counters, and "worst lag" came from stale `lagMs` samples carried by rows that had nothing real behind them. The regions panel separately retried its `@get` fetch through Datastar's default backoff (~10 attempts) and then stayed on the "Loading region health and latency…" placeholder forever, because a failed SSE fetch never applied a terminal state to the element.

The MagicOnion `IUsageService.GetReplicationAsync` call chain still exists in `src/TerraScale.TerraBase.Rpc/Usage/UsageService.cs`; it surfaces the deleted route's 404 as `TerraBaseNotFoundException`.

Live signup proof for this ticket was blocked at the time of investigation: `auth.terrascale.tech` `/terrascale/oauth/device` and `/terrascale/oauth/authorize` answer 503 (healthz OK), and `dash.terrascale.tech/login` answers 503, so no throwaway account could be created. `status.terrascale.tech/api/latency` reports every region "down" while each region's `/healthz` answers 200 — consistent with ts-auth's outage, not with TerraBase storage.

## Conclusion

1. The numbers were never engine state. The engine cause is the deleted TerraBase replication producer (`440e54abc`); the wrong classification was the dashboard trusting producer rows whose own contract marked unobserved regions as `stopped`. The dashboard now classifies a region with no observation as **Starting**, computes "worst lag" only from measured timestamps, and treats the deleted route (404 / `TerraBaseNotFoundException`) as an honest empty state ("TerraBase has not reported replication for this project yet") instead of an error or fabricated counters. Engine internals were untouched, per the ticket's constraint.
2. The stuck "Loading" regions panel was the dashboard's own Datastar `@get` retry policy. The fetch now uses `{retry: 'never'}` so a failed load ends in the server-patched error state with a "Retry regions" button.

Regression cover: `ReplicationHealthContractTests` (404 → unreported, unobserved regions → Starting), `HomeReportingJourneyTests.HomeClassifiesUnreportedReplicationRegionsAsStarting`, `HomeRegionsJourneyTests.OverviewRemainsUsableWhileScopedPublicRegionsAreBlocked` (retry-never attributes + Retry regions button).
