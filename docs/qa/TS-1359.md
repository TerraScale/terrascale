# TS-1359: verification codes not arriving at terrascale.tech addresses

## What was observed

- Since ~23:21Z on 2026-11-03, sign-up/sign-in at
  `https://auth.terrascale.tech/ui/terrascale/sign-up` answered HTTP 200
  ("Check your email") but no code reached the Purelymail INBOX for
  `mariogk+<tag>@terrascale.tech` after 20+ minutes of polling (two addresses,
  per the COS brief; the same window is recorded in issue #997's TS-1390
  comment at 01:13Z).
- The same flow to an external address (mail.tm) delivered in seconds, so
  ts-auth's provider submission and Cloudflare Email Sending were healthy.

## Root cause

Every verifiable "HTTP 200 'Check your email' but no code" report is explained
by ts-auth's **silent null paths** - requests that correctly never send mail
while still rendering the code step:

1. **Sign-in to an address no account owns.** `Passcodes.RequestAsync`
   returns null when no account owns the address (`Passcodes.cs:112-115`)
   and the outbox deletes the row without sending (`SignInMail.cs:274-279`),
   to prevent account enumeration. Crucially, plus-tags are NOT collapsed:
   `AuthStore.NormalizeEmail` only lowercases (`AuthStore.cs:184-188`) and
   `Users.NormalizeEmail` does no subaddressing, so `mariogk+tag@` is a
   distinct ts-auth identity from `mariogk@` even though Purelymail folds it
   into one mailbox. A **sign-in** (not sign-up) to a plus-tag that never
   completed sign-up therefore answers 200 and silently sends nothing -
   proven live below. TS-1390's failing probes (issue #997 comment, 01:13Z)
   were exactly this: `POST /ui/terrascale/sign-in` to two fresh
   `mariogk+glm-ts-1390*` tags, and the provider shows zero attempts for
   them because none were ever supposed to happen.
2. **More than 5 codes per address per hour.** `Passcodes.IssueAsync`
   returns null once `MaxIssuesPerWindow` (5 per UTC hour, per user or
   pending sign-up) is reached (`Passcodes.cs:326-332`) - silently, with the
   same 200 "Check your email". Repeated sign-up resends on one address
   inside an hour send nothing until the UTC hour rolls over, which matches
   "checked 20+ min, two addresses" reports that later work fine.

The 23:21:39Z-01:36:06Z hole with zero mail of any kind in the mailbox is
consistent with zero outbound attempts to terrascale.tech recipients in that
window (Cloudflare shows none, of any status). A Purelymail inbound stall in
the same window cannot be excluded - no independent inbound arrived to prove
otherwise - but there is no positive evidence for it either: zero bounces,
zero suppressions, zero deferred/retried terrascale.tech sends, SMTP
reception healthy from multiple vantage points afterward, and the first
fresh sign-up attempts after the window delivered in seconds. If Purelymail
did stall, it self-recovered without any action.

Changes that were checked and found NOT to be the cause: DNS (MX/SPF/DMARC/
DKIM unchanged since 2025-10/2026-10-21, MX still
`50 mailserver.purelymail.com.`, resolving and accepting SMTP from multiple
vantage points); no Cloudflare DNS record modified since 2026-10-29; no auth
code deployed in the window (last auth commit 98014b90c at 15:15Z, hours
before); GlitchTip shows no ts-auth errors; no Cloudflare suppression-list
or bounce activity (status totals 20:00Z-02:35Z: 93 delivered, 2 transient
`deliveryFailed` for the external ts-status probe, both retried
successfully); the scheduled probe failures since 10-30 were a different,
already-fixed problem (issue #994: mail.tm's maxxspace.com MX; #997 tracked
the 503s).

## Fix

Nothing was broken to fix at the time of investigation: both flows verify
live and correct, and no TerraScale-side fault is reproducible. What remains:

- The user-facing behavior in path 2 is a genuine UX trap worth a follow-up
  ticket: hitting the 5/hour issue limit (or signing in to an account-less
  plus-tag) shows the same "Check your email" as a real send, with the
  resend button silently doing nothing until the UTC hour boundary.
- The Purelymail API token (`~/.config/purelymail/api-token`, also stored as
  `dev-purelymail-api-token`) is currently **invalid** ("Token not valid" on
  every `/api/v0/` call with the documented
  `Purelymail-Api-Token` header), so the routing-rule/domain/quota checks
  this incident wanted could not be run against Purelymail; a new token
  needs the account owner's Purelymail login (user-only).
- The scheduled probe only tests an external inbox, and both silent null
  paths above are invisible to it; a terrascale.tech-recipient probe with a
  completed-sign-up address would cover the inbound leg end to end.
