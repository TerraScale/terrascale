# TS-1359: verification codes not arriving at terrascale.tech addresses

## What was observed

- Since ~23:21Z on 2026-11-03, sign-up/sign-in at
  `https://auth.terrascale.tech/ui/terrascale/sign-up` answered HTTP 200
  ("Check your email") but no code reached the Purelymail INBOX for
  `mariogk+<tag>@terrascale.tech` after 20+ minutes of polling (two addresses,
  per the COS brief; the same window is recorded in issue #997's TS-1390
  comment at 01:13Z).
- The same flow to an external address (mail.tm) delivered in seconds, so
  ts-auth's provider submission and Cloudflare Email Sending were healthy.

## Root cause

Two distinct findings; the outage itself was an inbound Purelymail problem,
not a TerraScale defect:

1. **Outage (23:21:39Z-01:36:06Z): Purelymail inbound delivery stalled.**
   During the hole, ts-auth submitted and Cloudflare delivered external mail
   normally (status probes every 5 min plus TS-1390 codes at 01:14Z), yet
   **zero** send attempts - not even bounces or suppressions - exist for any
   `@terrascale.tech` recipient, and the mailbox received nothing at all from
   anyone (production alerts included). The only sends that were attempted to
   terrascale.tech in that window are absent because Purelymail had accepted
   and delivered everything through 23:21:39Z and then stopped receiving;
   delivery resumed on its own at 01:36:06Z with no DNS, routing-rule or
   provider-side change on our side (below). This matches Purelymail's
   documented behavior of silent multi-hour inbound stalls (their status page
   lists several such incidents); nothing was ever posted for this window,
   and Purelymail's own status API carries no per-customer incident history
   we could query. No TerraScale code, DNS record or provider setting was
   changed before, during or after the window, and no retry was needed:
   codes requested in the window were issued to the outbox but their rows
   expire with the 30-minute code lifetime, so they were never delivered.
2. **Why "HTTP 200 but no code" can also be correct behavior (and confused
   the QA probes): ts-auth never sends mail for unknown-address sign-ins.**
   `Passcodes.RequestAsync` returns null when no account owns the address
   (`Passcodes.cs:112-115`), and the outbox deletes the row without sending
   (`SignInMail.cs:274-279`) while the endpoint still renders "Check your
   email" - anti-enumeration by design. Plus-tags are NOT collapsed
   (`AuthStore.NormalizeEmail` only lowercases; `Users.NormalizeEmail` does
   no subaddressing), so `mariogk+tag@` is a distinct ts-auth identity from
   `mariogk@`: a **sign-in** (not sign-up) to a tag that never completed
   sign-up sends nothing, silently, by design. The same null path also
   applies when an address exhausts its 5-codes-per-hour issue budget
   (`Passcodes.MaxIssuesPerWindow`), though that one answers 429.

Changes that were checked and found NOT to be the cause: DNS (MX/SPF/DMARC/
DKIM records unchanged since 2025-10/2026-10-21, MX still
`50 mailserver.purelymail.com.`, resolving and accepting SMTP from multiple
vantage points); no Cloudflare DNS record modified since 2026-10-29; no auth
code deployed in the window (last auth commit 98014b90c at 15:15Z, hours
before, and the gap spans no deploy); GlitchTip shows no ts-auth errors; the
scheduled probe failures since 10-30 were a different, already-fixed problem
(issue #994: mail.tm's maxxspace.com MX; #997 tracked the 503s).

## Fix

Nothing to fix in TerraScale: the outage was provider-side and self-recovered.
Operationally this leaves two gaps worth knowing:

- The Purelymail API token (`~/.config/purelymail/api-token`, also stored as
  `dev-purelymail-api-token`) is currently **invalid** ("Token not valid" on
  every `/api/v0/` call), so the routing-rule/domain/quota checks this
  incident wanted could not be run against Purelymail; a new token needs the
  account owner's Purelymail login (user-only).
- The scheduled probe only tests an external inbox, so a Purelymail-only
  inbound stall is invisible to CI until a human misses a code.
