# TS-1392: ts-ship never qualified the shipped dashboard commit

## What was observed

- `680e4ffb8` (TS-1388) shipped green through ts-ship on 2026-11-03, but no
  `dashboard/qualified-680e4ff…` release existed and live `dash.terrascale.tech`
  still reported the manually dispatched revision `847860419`.
- Every Images (GHCR) push run for later commits reported `deploy=false` in the
  `ready` gate: no `dashboard-release/dashboard` status on the exact SHA means
  nothing to deploy.

Commands:

```sh
grep -a -c prepare-deployment ~/.local/state/ts-ship/20261103T145035-92abe9cb.log   # 0
gh release list -R TerraScale/terrascale --limit 5 --json tagName,createdAt
curl -s https://dash.terrascale.tech/readyz -D- -o /dev/null | grep -i x-terrascale-revision
```

## Root cause

TS-1383's QA note (`docs/qa/TS-1383.md`) records a ts-ship
`@@TS_SHIP_PHASE dashboard-release` stage that qualified and tagged every green
dashboard commit, with a proof on `6c1f82ae0`. **That stage was never installed.**
Evidence:

- ts-ship on delta, mariogk-dev and beta was identical (`67a0d0de…`) and contained
  no `dashboard-release` phase; all 16 backup copies in `~/.local/bin` (including
  `ts-ship.glm-partial-20261103` from that morning) also lack it.
- No log in `~/.local/state/ts-ship/` ever invoked `scripts/dashboard/prepare-deployment.sh`;
  the 680e4ff ship log runs only build/test phases.
- `dashboard/qualified-6c1f82ae0…` and its success status exist because TS-1383 ran
  the qualifier manually on the dev host (release created 12:30:34Z, the commit's own
  timestamp), matching the pre-automation runbook, not an automated phase.

Two more claims from the same commit (`da156a1aa`) were also absent from ts-ship:

1. Dashboard release-workflow diffs (`dashboard-ci.yml`, `images-ghcr.yml`) did not map
   to the dashboard area: a workflow-only diff satisfied `monorepo_ci_suites`' ci
   self-check shortcut and shipped without any dashboard suite.
2. Carried dashboard Fast proofs were not discarded when the exact SHA lacked the
   release status, so a rebase could ship release-workflow changes unqualified.

The docs, the workflows-reference sync and the images-ghcr push-run gate were real;
only the ts-ship changes were never written to `~/.local/bin/ts-ship`.

## Fix

- `ts-ship` (delta + mariogk-dev + beta, identical SHA-256 `b003d3c8…`): after a green
  dashboard Fast, a new `@@TS_SHIP_PHASE dashboard-release` phase (900 s budget) runs
  `scripts/dashboard/prepare-deployment.sh` in the candidate checkout, publishing
  `dashboard/qualified-<sha>` and the `dashboard-release/dashboard` status before main
  is pushed — mirroring docs-release. The phase runs with `TS_SHIP_PHASE`/`TS_SHIP_MANIFEST`
  removed and the phased-dotnet wrapper directory removed from `PATH`, so the qualifier's
  own `dotnet publish` reaches the real CLI instead of the phase gate. Carried dashboard
  Fast proofs without the exact SHA's release status are discarded, like docs.
  `dashboard-ci.yml`/`images-ghcr.yml` diffs now map to the dashboard area in
  `areas()`/`upstream_affected()` and are excluded from the ci self-check shortcut.
  The remote preparation (pinned engine native download) now also runs for dashboard
  suites, whose isolated checkouts verify the native pins like the service areas.
- `scripts/dashboard/workflows-reference/ci.yml`: synced verbatim with the live
  `dashboard-ci.yml`. The copy still showed the pre-monorepo standalone design
  (including an `./.github/actions/dashboard-setup` step that does not exist in this
  repository), the same misleading-reference class TS-1383 fixed for `images-ghcr.yml`.

With the qualification status on the exact green main SHA, the Images (GHCR) push run
(`ready` waits for CI, `test`, `image`, release to every region, `verify-live.py`)
deploys automatically; no manual dispatch exists in the path.

## Proof

Shipped `72efb7b347ba4d1ea3ea7a0e72cc03825ac67bde` (2026-11-03) through the sanctioned path:
ts-ship dashboard Fast + sdk-dotnet Fast on the dev host, then the new `dashboard-release`
phase published `dashboard/qualified-72efb7b347ba4d1ea3ea7a0e72cc03825ac67bde` with both
success statuses by MarioGK before main moved; after the push, CI, Dashboard Fast, SDK
dotnet Fast and the Images (GHCR) push run all went green with
`ready: success → test: success → Publish and release: success` and no manual step; the
workflow's own `verify-live.py` passed. Live evidence:

```sh
curl -s https://dash.terrascale.tech/readyz -D- -o /dev/null | grep -i x-terrascale-revision
# x-terrascale-revision: 72efb7b347ba4d1ea3ea7a0e72cc03825ac67bde
```

The first run of the new phase also demonstrated the gate is fail-closed: the same-day
advisory GHSA-p3jp-9v83-76w9 (Brotli decoder out-of-bounds write, fixed in
`11.0.0-rc.3.26522.148`) flagged `Microsoft.DotNet.ILCompiler 11.0.0-rc.1` in the
`sdk/dotnet/scripts` file-based checker lock files, and the ship was refused
(`Dependency advisory scan failed: findings=2`) until the unused AOT default was dropped
from those scripts (`PublishAot=false`), removing the flagged package from the graph.
