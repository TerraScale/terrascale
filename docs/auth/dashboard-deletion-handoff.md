# Durable dashboard deletion handoff (TS-989)

Deleting a platform account directly through ts-auth must eventually remove dashboard-owned records even if no dashboard deletion operation or receipt exists. Auth retains its own deletion job as an outbox; dashboard polls through the SDK using its existing confidential client HTTP Basic credentials. Bearer tokens and deletion receipts grant no access to this API. No new credential is introduced.

The private service contract is included in auth's generated OpenAPI with `clientBasic` security:

- `GET /v1/{slug}/deletions` returns `{ "items": [{ "id": "<erasure ULID>", "scope": "account|organization|project", "subjectId": "<ULID>", "organizationId": null }] }`, at most 20 proofs per request. Only `slug=terrascale` exists. Account proofs have null organizationId; organization proofs use subjectId; project proofs require their owning organizationId.
- `POST /v1/{slug}/deletions/{id}/acknowledge` accepts `{ "scope": "account", "subjectId": "<ULID>", "organizationId": null }`. A matching existing proof returns 204, including repeated acknowledgements while retained. Invalid credentials return 401; another tenant, absent proof, wrong identity, live root, or retired proof returns 404. Concurrent job changes may return 409 and require retrying the same proof.

GET changes only delivery bookkeeping. A proof requires an existing, correctly keyed platform deletion job, a stable valid `ErasureId`, verified auth logical cleanup, a supported exact scope and an absent auth root. Root absence by itself proves nothing. Responses contain no email addresses, credentials, receipts or membership graphs and are marked `no-store`.

Each poll selects at most 20 candidates ordered by persisted `dashboardDeliveryTurn`, then TerraBase document ID. TerraBase orders missing fields before null, then numeric values; existing jobs without the field are visited first. Before validating or returning each candidate, auth conditionally increments its turn at the actual document ID and version through the SDK. This also rotates malformed or incorrectly bound records without trusting their claimed natural key or changing any proof, cleanup, acknowledgement or history fields. A lost CAS skips that candidate for this response. There are no retry scans, clock dependencies, new response fields or required dashboard cursors. With a retained finite backlog, repeated polls reach later proofs even when earlier proofs remain unacknowledged or fail validation. An empty batch can reflect rejected candidates and does not mean the retained backlog is empty; dashboard must continue polling. A crash after rotation can delay that candidate until a subsequent rotation, but cannot acknowledge or remove it.

Dashboard must durably verify its own exact scoped cleanup before acknowledging. An account proof authorizes cleanup of that account's dashboard records, not shared organizations; organizations and projects require their own proofs. Dashboard may acknowledge a proof after verifying no matching local records exist. If dashboard crashes before acknowledgement, the proof remains available and cleanup can be repeated.

The optional persisted `DeletionJob.DashboardVerifiedAt` defaults to null; `DashboardDeliveryTurn` defaults to zero. Delivery bookkeeping is never evidence of dashboard cleanup. Acknowledgement rereads and validates the exact proof and absent root, then conditionally updates that job version. It cannot acknowledge an arbitrary subject. Auth history erasure continues during dashboard outages: shared-file rewrites retain current live records, including the outbox job. Final job/fence retirement requires both the existing history/credential conditions and dashboard acknowledgement for platform jobs. Completed jobs waiting for acknowledgement are excluded from history batches so they do not starve other erasures. App-owned tenant jobs retain their existing retirement behavior.

This is an additive private API and storage-field change. It introduces no migration, alternate store, authentication bypass or physical-erasure guarantee for dashboard-owned data. Auth and dashboard each retain ownership of their own data.

The ordered query remains subject to TerraBase's field-sort admission limits (10,000 readable live records and 8 MiB JSON across the deletion-job collection, before the submitted filter); larger sets fail visibly rather than silently proving cleanup. Fast HTTP/storage regressions cover forty unacknowledged or malformed candidates ahead of five valid jobs, persisted progress across restart with a frozen clock, unchanged retained fields, and exact acknowledgement of the later proofs.
