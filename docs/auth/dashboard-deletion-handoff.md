# Durable dashboard deletion handoff (TS-989)

Deleting a platform account directly through ts-auth must eventually remove dashboard-owned records even if no dashboard deletion operation or receipt exists. Auth retains its own deletion job as an outbox; dashboard polls through the SDK using its existing confidential client HTTP Basic credentials. Bearer tokens and deletion receipts grant no access to this API. No new credential is introduced.

The private service contract is included in auth's generated OpenAPI with `clientBasic` security:

- `GET /v1/{slug}/deletions` returns `{ "items": [{ "id": "<erasure ULID>", "scope": "account|organization|project", "subjectId": "<ULID>", "organizationId": null }] }`, at most 20 proofs per request. Only `slug=terrascale` exists. Account proofs have null organizationId; organization proofs use subjectId; project proofs require their owning organizationId.
- `POST /v1/{slug}/deletions/{id}/acknowledge` accepts `{ "scope": "account", "subjectId": "<ULID>", "organizationId": null }`. A matching existing proof returns 204, including repeated acknowledgements while retained. Invalid credentials return 401; another tenant, absent proof, wrong identity, live root, or retired proof returns 404. Concurrent job changes may return 409 and require retrying the same proof.

GET changes only delivery bookkeeping. A proof requires an existing, correctly keyed platform deletion job, a stable valid `ErasureId`, verified auth logical cleanup, a supported exact scope and an absent auth root. Root absence by itself proves nothing. Responses contain no email addresses, credentials, receipts or membership graphs and are marked `no-store`.

Each poll issues one SDK query for at most 20 candidates in document ID order, continuing from a durable SDK `NextCursor`. Auth stores that opaque position in one record in its dedicated `dashboard_deletion_cursors` collection. Before validating or returning proofs, auth conditionally writes the page's next cursor at the cursor record's version (create-only on the first poll). A lost CAS returns an empty batch; dashboard retries on its next poll. The last page writes null so the following poll starts at the beginning. The SDK cursor binds the database, collection, filter, sort and projection, without a process, machine or clock dependency; auth does not decode it or expose it to dashboard.

Delivery leaves every candidate's JSON and version untouched, including malformed bindings and documents already at TerraBase's 4096-value limit. ID order avoids field-sort admission limits. Each poll performs one bounded query and one cursor CAS, with no retry scan. With a retained finite backlog, repeated polls reach later proofs even when earlier proofs remain unacknowledged or fail validation. An empty batch can reflect rejected candidates or a competing poll and does not mean the retained backlog is empty; dashboard must continue polling. A crash after the cursor CAS can delay that page until the next traversal, but cannot acknowledge or remove any proof.

Dashboard must durably verify its own exact scoped cleanup before acknowledging. An account proof authorizes cleanup of that account's dashboard records, not shared organizations; organizations and projects require their own proofs. Dashboard may acknowledge a proof after verifying no matching local records exist. If dashboard crashes before acknowledgement, the proof remains available and cleanup can be repeated.

The optional persisted `DeletionJob.DashboardVerifiedAt` defaults to null. Delivery bookkeeping is never evidence of dashboard cleanup. Acknowledgement rereads and validates the exact proof and absent root, then conditionally updates that job version. It cannot acknowledge an arbitrary subject. Auth history erasure continues during dashboard outages: shared-file rewrites retain current live records, including the outbox job. Final job/fence retirement requires both the existing history/credential conditions and dashboard acknowledgement for platform jobs. Completed jobs waiting for acknowledgement are excluded from history batches so they do not starve other erasures. App-owned tenant jobs retain their existing retirement behavior.

This is an additive private API, storage-field and auth-owned collection change. Provisioning and readiness require the new cursor collection. It introduces no migration, alternate store, authentication bypass or physical-erasure guarantee for dashboard-owned data. Auth and dashboard each retain ownership of their own data.

Queries retain TerraBase's normal execution and page-byte limits. Fast HTTP/storage regressions cover forty unacknowledged or malformed candidates ahead of five valid jobs, persisted progress across restart with a frozen clock, wraparound, exact retained JSON and versions, exact acknowledgement of later proofs, and traversal past a malformed 4096-value candidate that storage refuses to extend to 4097 values.
