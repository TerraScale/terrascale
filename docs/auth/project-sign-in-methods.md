# Project magic links and usernames

In **Authentication → Sign-in methods**, select **Magic links** and/or **Username sign-in** and save. These are per-project customer settings; platform accounts keep their existing sign-in methods.

The management API accepts `PUT /v1/{project}/settings` with `{"methods":{"magic_link":true,"username":true}}`. Omitted settings stay unchanged. The five SDKs expose both fields on project methods.

Magic links use the existing magic_link email template. The email contains a link and a six-digit code. The link and code expire ten minutes after issuance and share a single-use stored challenge; using either invalidates both. A new issuance replaces the previous one. An encrypted link carries the issuance ID, tenant, destination and hash of a random Secure, HttpOnly, SameSite=Lax browser cookie. Only the requesting browser can redeem it directly. Opening it elsewhere shows the email-code form and leaves the challenge available. The local second factor remains required. Unknown emails receive the same page and no message. Mail and attempt budgets are shared with ordinary sign-in.

Usernames are chosen at hosted sign-up when the project enables usernames. They contain 3–32 ASCII letters, digits, underscores or dots. Storage normalizes them to lowercase and a tenant-scoped unique index prevents duplicates, including concurrent sign-ups. Password sign-in accepts either the email or username, case-insensitively. Both aliases spend the same account password budget. Existing users can set or change their username on the hosted Security page after a recent sign-in. Reserved names admin, administrator, root, support, security, help, terrascale, system, owner and staff are refused. Sign-up checks availability under the IP attempt budget and reports “Username taken” both before sending mail and after a competing creation wins the unique index.
