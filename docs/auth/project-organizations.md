# Project organizations

Project organizations group a customer's end users inside one project. They are independent of TerraScale platform organizations, which own projects and billing.

All management operations use /v1/{project}/organizations. A platform sign-in token requires the project's viewer role for reads and admin role for changes. Project secret API keys require auth:read for reads and auth:write for changes; C41 records mutation outcomes. End-user tokens cannot manage organizations.

| Method | Path suffix | Behavior |
| --- | --- | --- |
| POST | /organizations | Create an organization and its initial admin |
| GET | /organizations | List with limit (1–100) and after |
| GET, PUT, DELETE | /organizations/{org} | Read, replace settings, delete |
| POST, GET | /organizations/{org}/memberships | Add a member, list members |
| PUT, DELETE | /organizations/{org}/memberships/{user} | Change role, remove |
| POST, GET | /organizations/{org}/invitations | Email an invitation, list |
| DELETE | /organizations/{org}/invitations/{invitation} | Revoke a pending invitation |
| POST, GET | /organizations/{org}/domains | Add a domain, list domains |
| POST | /organizations/{org}/domains/{domain}/verify | Check DNS TXT |
| DELETE | /organizations/{org}/domains/{domain} | Remove a domain |

The org parameter accepts the organization ULID or slug. The project always comes from the authorized route. Create and PUT bodies contain name, slug, image_url, public_metadata, private_metadata, max_members, and domain_join. Creation additionally requires admin_user_id, an active user in the same project, so every new organization starts with an admin. PUT replaces settings; omitted metadata becomes {}, and omitted image or member limit becomes null. Names have 1–128 characters. Slugs have 3–63 lowercase ASCII letters, digits or hyphens, with an alphanumeric first and last character, and are unique per project. Each metadata object is limited to 8192 UTF-8 bytes. Management responses include private metadata; hosted pages and tokens never expose it.

Membership bodies use user_id and role; roles are admin and member. Role updates use the member's user ID in the route. A conditional organization version serializes changes to member and admin counts in the same batch as the membership. Conflicting writers receive 409; the last admin cannot be removed or demoted, and max_members cannot be exceeded or reduced below current membership. Deleting a user atomically removes their memberships and emits membership deletion events. If the user was the last admin, the oldest remaining membership becomes an admin (ties use user ID), with an update event. An empty organization remains with zero members and zero admins; explicitly add an admin before inviting ordinary members or resuming domain joins. Organization deletion emits membership deletion and invitation revocation events in the same batch, then cascades its memberships, invitations and domains; outstanding invitation links and subsequent token refreshes fail.

Invitation bodies contain email, role and optional inviter_name (1–100 plain-text characters; controls, bidirectional formatting and markup are refused). Invitation email names the organization and the project’s branded app; inviter_name can name a person instead of the organization. The dashboard caller’s personal email and internal key name are never used. Only a SHA-256 hash of a 48-character CSPRNG token is stored in the invitation. The email links to /ui/{project}/organization-invitations?token=<token>. The hosted page sends signed-out users through the project's sign-in or sign-up, then asks them to accept. Same-origin POST and a live project session are required. The signed-in email must match; acceptance consumes the invitation and adds the membership atomically. Invitations expire after seven days. Joining through any path, or leaving, clears the user’s suggestion dismissal atomically with membership changes. Existing members retain their current role when accepting another invitation. Tokens are never returned by management APIs.

Only one organization per project may verify a domain; multiple organizations may hold unverified claims. Add returns record_name and record_value; publish that DNS TXT record before verification. The name is _terrascale-org.<domain> and the value is terrascale-org=<random verification token>. The domain_join setting is off, suggest or auto: during interactive authorization, verified email domains may offer joining or add a member. The user must have a verified email. Domain verification and organization versions are asserted when joining. Suggest mode offers Continue without joining, persisting a dismissal for that user and organization. A full auto-join organization never blocks authorization; a conflicting join re-reads once and then continues regardless of the outcome. A background worker rechecks verified domains every 24 hours. Three consecutive failed rechecks mark a domain unverified and emit organizationDomain.updated. Removing a domain prevents future joins and preserves existing memberships.

Authorize accepts organization=<id-or-slug>. A selected organization requires a current membership. Without one, a single membership is selected; multiple memberships show a hosted chooser. The prompt=none option returns interaction_required when choosing requires interaction. Access and ID tokens carry org_id, org_slug, org_role. Codes and refresh tokens retain the selected organization; redemption rereads its current membership, so role changes are reflected and removed memberships fail with invalid_grant. Switching requires a new authorization. Previously issued access tokens retain their bounded offline validity.

C42 outbox events are committed with each mutation: organization.created, organization.updated, organization.deleted, organizationMembership.created, organizationMembership.updated, organizationMembership.deleted, organizationInvitation.created, organizationInvitation.accepted, organizationInvitation.revoked, organizationDomain.created, organizationDomain.updated, organizationDomain.deleted. Data includes organization_id; user_id is the affected user for memberships, invitation ID for invitations, and organization ID for organization changes.

The dashboard's Authentication → Organizations section provides the organization list and details, members, invitations and domains. SDK surfaces are .NET Projects.*Organization*Async, JavaScript projects.organizations, Go User.*ProjectOrganization*, Python sync/async *organization* with models in auth_organizations, and Rust ProjectsClient::*organization*.

Sign-in proves each stored user’s email: email challenges verify it, social sign-in requires a verified provider email, and SSO requires the organization’s proven domain and refuses explicit unverified claims. There is no separate persisted email verification flag. Daily domain rechecks claim each due row through a version-checked one-minute lease and resolve at most four domains concurrently per worker. Resolver failures answer 503 dns_unavailable and do not count as missing TXT records.
