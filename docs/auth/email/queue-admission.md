# Hosted email queue admission

Hosted sign-in, sign-up (including existing accounts), and password-reset starts reserve a slot in the bounded authentication delivery queue before accepting the start. A full or stopping queue returns HTTP 503 with the standard JSON error envelope and code `email_queue_unavailable` before issuing a code or rendering the successful code-entry page. Known and unknown addresses reserve the same capacity and receive the same overloaded response; account lookup and issuance run on the worker after admission. The request's resolved tenant and selected email locale travel with the queued work.

Existing mail-start abuse budgets still apply first, including unknown addresses. An overloaded request spends those budgets, so an immediate retry can return 429 with `Retry-After`. The normalized-address budgets use bounded keyed folds and can conservatively share a bucket between different addresses. Capacity admission does not refund or bypass these protections. Cancellation observed before queue submission releases the reservation and submits no mail work. After acceptance, the background worker owns issuance and delivery independently of the HTTP caller.

Organization and project invitations reserve delivery capacity after authorization and rate limiting, before committing the invitation and its pending-address uniqueness claim. A known-full queue therefore returns 503 without leaving a pending invitation that would block the same create with `invitation_pending`. Transaction failures, conflicts and cancellation release the unused reservation. A successful commit consumes its reserved slot without a second capacity race. When no dashboard client is configured, the existing token-only invitation behavior remains; there is no configured dashboard accept page to email.

Queue admission, submission, release and shutdown are synchronized within the process. The authentication queue holds at most 256 queued or reserved deliveries plus one active worker. Shutdown refuses new reservations and allows already-reserved work to submit before completing the queue; draining remains bounded by the host shutdown timeout. Lockout notices keep their separate bounded queue and worker. Their best-effort overflow is logged and cannot consume authentication queue capacity or change a refused authentication response.

Admission proves only that this process accepted bounded work. It does not prove provider acceptance or inbox delivery. Issuance, rendering, configuration/storage failures and provider outcomes can still prevent delivery after HTTP success. No automatic retry is added, particularly for ambiguous provider sends. Provider admission and quotas remain separate from this process queue reservation.

The queue and its reservations remain process memory. A crash after an invitation transaction commits, or after an authentication start is accepted, can still lose the queued work. A lost storage commit acknowledgement can likewise leave a committed invitation even though the caller observed a failure and its unused reservation was released. A provider failure can also leave a pending invitation; this change does not add automatic resend or recover plaintext invitation tokens or codes from storage. Restart recovery and durable delivery require a separately reviewed design that preserves single-use secrets, tenant isolation, and conservative handling of ambiguous sends. No persistent plaintext codes or invitation tokens are introduced.

Fast integration regressions use isolated real auth hosts and TerraBase databases, a controllable sender in the test binary, and a genuinely saturated queue. They cover platform/project known-unknown overload parity, unchanged existing passcodes and pending-signup records across refusal, retained abuse limits, recovery after capacity frees, failed invitation reservation release, concurrent competition for the last slot, and retrying a refused invitation without a pending conflict. Deterministically pausing and cancelling an invitation before commit verifies its last-slot release; shutdown cases verify that existing reservations may submit or release while new starts are refused. These tests do not contact an external provider.
