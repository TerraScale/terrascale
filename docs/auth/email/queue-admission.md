# Hosted email queue admission

Hosted sign-in, sign-up (including existing accounts), and password-reset starts reserve a slot in the bounded authentication delivery queue before accepting the start. A full or stopping queue returns HTTP 503 with the standard JSON error envelope and code `email_queue_unavailable` before issuing a code or rendering the successful code-entry page. Known and unknown addresses reserve the same capacity and receive the same overloaded response; account lookup and issuance run on the worker after admission. The request's resolved tenant and selected email locale travel with the queued work.

Existing mail-start abuse budgets still apply first, including unknown addresses. An overloaded request spends those budgets, so an immediate retry can return 429 with `Retry-After`. The normalized-address budgets use bounded keyed folds and can conservatively share a bucket between different addresses. Capacity admission does not refund or bypass these protections. Cancellation observed before queue submission releases the reservation and submits no mail work. After acceptance, the background worker owns issuance and delivery independently of the HTTP caller.

Organization and project invitations reserve delivery capacity after authorization and rate limiting, before committing the invitation and its pending-address uniqueness claim. A known-full queue therefore returns 503 without leaving a pending invitation that would block the same create with `invitation_pending`. Transaction failures, conflicts and cancellation release the unused reservation. A successful commit consumes its reserved slot without a second capacity race. When no dashboard client is configured, the existing token-only invitation behavior remains; there is no configured dashboard accept page to email.

Admission is synchronized within the process: each replica holds at most 256 accepted-but-unclaimed or reserved deliveries. An accepted start or committed invitation is written to the durable `auth_mail_outbox` collection in ts-auth's TerraBase database before the response, the same write for known and unknown addresses. The row holds only what was asked (address, tenant, locale, purpose; for sign-up the password hash and pending token), sealed with AES-256-GCM under the master key and bound to the row id; no code exists yet. Shutdown refuses new reservations, lets reserved work submit, and delivers what it can within the host shutdown timeout; anything left stays in the outbox.

Each replica dispatches up to eight independent deliveries concurrently. New work wakes the dispatcher immediately, and each completion frees a slot without waiting for other provider calls. The recovery query filters out active leases and deferred retries before applying its limit, so a full batch of waiting rows cannot hide newer eligible mail. Delivery order is not guaranteed. Admission, provider quotas and conditional row ownership remain enforced.

The worker claims a row with a lease (2 minutes) by a conditional write, so one replica works it at a time and any replica takes over a row whose lease lapsed, which is how a crash or restart recovers accepted work. It issues the code, then stores the rendered values sealed in the row together with the issuance it belongs to. Right before sending it checks that the code still redeems: a code replaced by a newer request, redeemed, exhausted or expired is marked `suppressed` and never sent. Invitations and email change mail are sent only before their own expiry. The row is marked `sending` before the provider call. Provider acceptance ends it as `sent`, a permanent refusal as `rejected`. An explicit retryable refusal (no send happened) is retried with doubling backoff from 30 seconds, at most 5 attempts, then `failed`. An ambiguous outcome, a thrown send, or a row found still `sending` after its lease lapsed (the replica died mid-call) ends as `unknown` and is never resent. Finished rows drop their sealed payload; every row is deleted one day after creation.

Lockout notices keep their separate bounded in-memory queue and worker. Their best-effort overflow is logged and cannot consume authentication capacity or change a refused authentication response.

Admission and `sent` prove provider acceptance at most, not inbox delivery. Provider admission and quotas remain separate. A lost storage commit acknowledgement can still leave a committed invitation even though the caller observed a failure.

Fast integration regressions use isolated real auth hosts and TerraBase databases, a controllable sender in the test binary, and a genuinely saturated queue. They cover a replica taking over after another stopped mid-send (the accepted code is delivered, the interrupted send ends `unknown` and is not repeated), a code superseded or expired before its retry being suppressed, platform/project known-unknown overload parity, unchanged existing passcodes and pending-signup records across refusal, retained abuse limits, recovery after capacity frees, failed invitation reservation release, concurrent competition for the last slot, and retrying a refused invitation without a pending conflict. Deterministically pausing and cancelling an invitation before commit verifies its last-slot release; shutdown cases verify that existing reservations may submit or release while new starts are refused. These tests do not contact an external provider.
