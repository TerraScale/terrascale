# Customer request observations and allowance notifications

`GET /v1/projects/{project}/databases/{database}/logs` requires `databases:read` and resolves the database under the authorized project. A token scoped to another project or database receives 404. `status` accepts `2xx`, `3xx`, `4xx`, or `5xx`; responses use `Cache-Control: no-store`. An unavailable catalog or memory budget returns 503 rather than an empty history.

The response contains database identity and at most 100 recent request observations within 24 hours, ordered newest first. Each observation includes a ULID, UTC time, region, HTTP method, route template, response status, latency, committed document-operation count, and query indicator. Request URLs, document identities, query text, headers, bodies, and credentials are not retained. Document operations are not billing operation units. Slow query requests have `isQuery=true` and latency of at least 100 ms. Logs reads do not record themselves.

Recording is best effort: pending observations are bounded in memory and may be dropped at capacity or lost on a crash. Persisted observations replicate through the catalog. Filtering searches the retained recent window; `truncated` indicates the 100-record bound; `recordingLimited` reports capacity omissions on the responding server since startup. Expired observations are excluded from reads; physical pruning occurs when the database's pending observations flush.

The peer-only internal `GET /v1/usage/allowances` feed is provided by the authoritative usage service introduced in #493. It pages organizations from the replicated catalog and reports current UTC-month organization operation units across all projects, regions and nodes. Each started 4 KiB read or write counts once where served; replication is not billed. Consumers accept only the agreed `operation-units-4kib-global-v1` contract, supplied by the producer follow-up. Storage remains unavailable (`logicalBytes=null`, `storageContract=none`); storage notifications must remain suppressed until an authoritative cross-region measurement exists.

`POST /v1/{slug}/email/allowance` uses the dashboard's existing ClientBasic email authority. The request names an organization, current UTC month, metric, threshold (80 or 100), used amount, and allowance. ts-auth resolves current owners internally and returns delivery status only. Durable per-recipient claims prevent duplicate sends for the organization/month/metric/threshold. Explicit refusal can retry; ambiguous provider acceptance or a crash after claiming is unknown and is not automatically retried. Acceptance confirms Cloudflare acceptance, not inbox delivery. No new grant, owner-directory response, or credential distribution is introduced.
