# Process crash recovery

Database creation flushes the initialized database and wrapped key, publishes the key and syncs the directory hierarchy, then publishes the database and syncs its directory. Startup removes files with the explicit unpublished `.creating` identity. An interrupted creation is distinguished by that identity, never by a zero-length main file.

Deletion first flushes a `.deleting` marker and its directory, removes the database and syncs its directory, then removes its wrapped key, other sidecars and marker. It syncs those removals and any removed parent directories before completing. Startup completes deletion only when that marker proves deletion was requested. A missing main file without that marker leaves its key and log untouched.

A write intent left by an interrupted process triggers a database open, journal recovery and integrity check. A healthy copy whose incarnation is named by its intent is accepted. The intent writer retains its existing single canonical 26-character incarnation. The reader also understands a future source:replacement pair, requiring successful log replay and integrity checking before accepting either named incarnation. This release does not write that pair: a previous release rejects it while opening the catalog. Healthy rewrite ancestry is held only in process memory, with no predecessor recorded in the file. Consequently a crash after a rewrite rename can leave a replacement that the single-value intent cannot identify; that copy remains refused. A later release must introduce the paired writer after the reader has deployed across the rollback window. The rewrite path must not acquire a production caller before the paired intent writer ships; reviewers must verify that its only caller remains the crash harness.

A durable fault-in-progress intent (`run = 0`) immediately refuses that copy at live admission boundaries as well as after restart. Its incarnation stays canonical; a companion `_tb_fault_binding` row records a fingerprint of the immutable wrapped key as its creation identity. Before bootstrap has read the incarnation, the database location and this creation identity bind the intent. Once known, incarnation also identifies the copy independently of its file path. If damage precedes the first incarnation read, the validated creation fingerprint supplies the permanent fault record’s identity after restart; unavailable creation evidence stays pending. An all-zero unavailable fingerprint is a valid unresolved binding, never a permanent fault identity. When neither incarnation nor creation identity is known, the canonical intent uses the database location id; its unavailable binding keeps it pending, and the prior release can still parse the intent. A later incarnation cannot overwrite the marker. A different wrapped key at the same location cannot inherit the old intent as a permanent fault; the old evidence remains and refuses admission at that location until explicit database deletion forgets it. An unavailable or different creation identity keeps the marker pending without opening the owning database or faulting the different copy. A changed key at an uncleared location has no expiry. Operators see `terrabase_storage_proof_pending`, `terrabase_storage_proof_incomplete_total{reason="fault_identity_changed"}` (or `fault_identity_unavailable`), and the warning “A database recovery proof is incomplete and will retry” with that reason. Explicit deletion of the old database clears its intent, fault and binding records; ordinary catalog creation then uses a new database id. Restoring the original key can establish the old creation identity, but finishes its permanent fault rather than admitting it. Do not replace keys or edit ledger rows to bypass refusal. The marker is positive evidence that damage was already being recorded. Recovery completes its permanent fault row before considering any proof for that copy. A healthy proof cannot retire this marker or clear the fault; the marker can be retired only after the fault row is durable.

Recovery has three outcomes:

| Outcome | Evidence | Action |
| --- | --- | --- |
| PASSED | Full integrity returns `ok` and identity matches a named incarnation | Retire intent and admit the copy |
| DAMAGED | A completed integrity query returns a row other than `ok`, a completed check proves a different identity, or the main file is empty or missing after its WAL opens | Persist the bounded fault reason before retiring the intent; refuse all protocols |
| INCOMPLETE | Busy/locked, I/O/storage failure, key unavailable, timeout, interruption/cancellation, constraint or any other inability to complete the proof | Keep intent, record no permanent fault, return retryable unavailable, retry in the background |

Proofs copy the main file and WAL into reserved scratch space, unwrap the existing key without rewriting it, and open only the scratch database. They never delete, truncate, recreate or checkpoint the source database, log or key. Opening an existing recovery snapshot also rejects an empty/missing main before opening; it never repairs it by deletion. Scratch copies are disposable. Shutdown removes empty WAL files only from healthy copies; a faulted copy retains even an empty WAL. `terrabase.storage.faulted.databases` reports the current persisted fault count, including after restart; `terrabase.storage.proof.pending` reports pending databases and `terrabase.storage.proof.incomplete` counts incomplete attempts by bounded reason. At most four copies retry independently, with one claim per copy; copying and native checking hold no global ledger gate. The gate protects admission, claim registration and result bookkeeping, including I/O to the ledger’s own system and intent stores. Creation evidence is computed once outside the gate; commit revalidates the pending claim and immutable fault binding without reopening any tenant file. Each copy retries at exponential delays of 2, 4, 8, 16 and at most 32 seconds; shutdown stops them and retains unresolved intents.

Every exception while executing an integrity check is INCOMPLETE, including engine corruption codes 11 and 26: an unavailable or wrong key can produce the same errors. These exceptions use bounded reason `integrity_engine_corruption`; ordinary storage/I/O failures use `storage`, `busy_or_storage` or `io` as classified. An exception after some result rows also leaves the proof INCOMPLETE. A copy that keeps throwing remains pending and refused until an operator acts; retries have no terminal attempt count. Alert on sustained `terrabase_storage_proof_pending` and increases in `terrabase_storage_proof_incomplete_total{reason="integrity_engine_corruption"}`. Restore key/storage access or restore a backup into a new database; do not clear the intent to admit an unchecked copy.

A fault is never cleared automatically, including after a later successful proof. An operator has the database files, remaining log and wrapped key retained when fault publication completes, plus the persistent fault record with its reason. A checkpoint already running at detection may have finished backfilling and truncating the log before that publication. Supported recovery today is restoring a backup into a new database; that backup may not contain the most recent acknowledged writes. Preserve the originals for investigation before deleting the faulted database.

## Tenant-visible states

| State | HTTP SQL, metadata, shapes and exports | PostgreSQL | WebSocket SQL |
| --- | --- | --- | --- |
| Healthy | Normal responses | Normal queries | Normal result frames |
| Fault intent or permanent fault | `503 copy_faulted` before response headers | `57P03` with `copy_faulted`; new sessions receive a fatal error and disconnect, while established query/transaction operations receive an error | An authenticated upgrade can return HTTP `503 copy_faulted`; first-frame authentication sends an error and closes with policy violation; an established socket sends `copy_faulted` for the refused frame and stays open, refusing subsequent frames |
| Pending proof | `503 recovery_pending` before response headers; middleware supplies `Retry-After: 1` | `57P03` with `recovery_pending`; new sessions receive a fatal error and disconnect, established queries receive an error | An authenticated upgrade can return HTTP `503 recovery_pending`; first-frame authentication sends an error and closes with policy violation; an established socket sends `recovery_pending` and stays open; later frames can succeed after proof passes |
| Node failed closed | `503 copy_faulted` where a response can still be written; readiness fails | `57P03` with `copy_faulted` | Admission/error behavior follows copy faults |

A response or stream already in progress can terminate after bytes already delivered; those bytes cannot be withdrawn. A write with an uncertain commit can return `write_outcome_unknown` instead of a copy error and must not be replayed automatically. Pending refusal has no time bound while the proof cannot complete. Alert on sustained `terrabase_storage_proof_pending`, increases in `terrabase_storage_proof_incomplete_total` by bounded reason, and nonzero `terrabase_storage_faulted_databases`. An incomplete tenant proof does not make healthy copies or node readiness wait for that tenant's retries.

## File mutation boundaries

For one owning tenant copy, recording a fault and modifying its main file or log are mutually exclusive, and no file modification starts after the fault is recorded. Detection and publication are distinct: a checkpoint or truncation already running when another reader detects damage completes before the fault intent is written and refusal becomes visible. A per-copy barrier covers the final refusal check through completion of each native or filesystem mutation. Fault publication takes that same barrier before changing in-memory refusal or the durable intent. Different copies do not share this barrier, and neither its acquisition nor a tenant-file read holds the ledger gate.

The lock order is writer gate, copy barrier, revision lock for mutations; publication takes copy barrier, then ledger gate. The ledger gate never acquires a tenant barrier or writer gate. `EnterMutation` centralizes barrier acquisition and the final store refusal check. A synchronous scope can nest only on its owning thread; asynchronous publication and migration leases cannot nest. System/intent-store bookkeeping uses its separate system writers, whose failure refuses the node.

Each barrier holder has a 30-second fail-stop deadline, and acquisition also has a 30-second deadline. A stuck direct checkpoint cannot leave a successful fault-recording call waiting indefinitely: the watchdog terminates the process if the call does not finish. This is process termination, not cancellation of an unsafe native call or successful fault publication. Files and existing durable write intents remain for restart proofs; a fault whose publication never completed may not have a permanent fault row. Timer delivery and process termination depend on the runtime and operating system. Native root-statement interruption remains enabled to shorten normal cancellation, but the pinned direct-checkpoint ABI calls `core.checkpoint` outside a root statement and offers neither a stepped checkpoint nor an interrupt contract for that call. No native patch, ABI, artifact or pin changes in this fix.


| Operation outside a tenant transaction | Refusal |
| --- | --- |
| Session setup and bootstrap/schema migration | Store and session admission check intents, pending proofs and permanent faults; session open, setup and bootstrap hold the copy barrier, link refusal and interrupt root statements |
| Writer eviction and close checkpoint, with or without revision attachment | Queued work takes the copy barrier, checks availability immediately before checkpoint, and holds it through native completion; refusal cancellation still interrupts root statements |
| Revision attachment, catch-up and after-write checkpoint/truncation | Owning writer work holds the copy barrier around attachment, catch-up and after-write indexing/checkpointing; native truncation retains its final connection refusal check |
| Idle CDC trimming, tap acknowledgement/truncation and rewind | Writer work holds the copy barrier and checks availability inside the queued operation, with native interruption; refused stores are skipped; rewind writes through gated transactions |
| Rewrite source checkpoint, sidecar removal and canonical rename | Source-open and source-checkpoint scopes hold the copy barrier; replacement holds it across sidecar removal, rename and directory syncs, with the final refusal check inside the scope |
| Direct tenant format migration and checkpoint | Ledger read admission includes intents and takes a cancellable copy lease; migration then acquires the copy barrier outside the ledger gate, rechecks refusal and holds it through migration, checkpoint and close |
| Creation, copy/fork, restore and log replay target initialization/checkpoint | Targets are fresh unpublished files; copy sources are gated. Canonical publication and failed-publication orphan-key cleanup take the copy barrier without waiting under the creation lock and recheck ledger refusal; busy barriers refuse publication. Detached backup/replay/snapshot scratch is independent of the owning files |
| Graceful native connection close and empty-WAL shutdown cleanup | Owning pooled sessions always deinitialize without graceful checkpoint; terminal copy sources also refuse graceful close. Empty-WAL cleanup takes the copy barrier and rechecks the store after disposal |
| Startup unpublished-creation/rewrite/proof scratch cleanup | Deletes only named unpublished scratch; creation cleanup never deletes a canonical main or WAL. It may remove an orphan published key only when no canonical main or WAL exists |
| SYSTEM/intent-store format preparation | Required startup bootstrap; its failure prevents startup. Tenant migration remains behind its ledger lease |
| Replica-cache apply/checkpoint/rebuild | Separate disposable cache files; source pages use gated owning-copy replication. These files are not the faulted owning copy's main or WAL |
| Explicit database deletion and restart completion of `.deleting` | Deliberate exception: deletion removes owning files and forgets fault, intent and binding rows |

There is no autonomous vacuum of owning files. SQL-issued schema/maintenance work follows transaction admission and interruption. Size reads and fsync do not rewrite content.

## Not covered

An upload of a backup segment or snapshot that completes just as a fault is recorded stays in object storage under its final key. Restore discovers segments by listing keys, so it can use that object even though the shipper recorded no success for it. Checks before upload and before recording success remain, and refusal interrupts source reads and prevents a read observed after refusal from reaching a new upload. An upload already in flight can finish despite cancellation; this PR does not provide complete reader or publication protection. Closing this window needs a publication record checked by restore, in the follow-up **restore uses only segments the shipper recorded as published**. The backup object format and restore reader are unchanged.

Connections explicitly use WAL journaling. Point-in-time rewind commits with full synchronization. Change capture without a backup tap can discard completed transactions while respecting active shape, replica and rewrite retention floors. A sequential idle pass visits databases on disk every 30 seconds, including unopened databases after restart, and skips busy writers. Each database trims at most 16,384 rows and 64 MiB per visit (one oversized row may exceed the byte allowance); the retained-row gauge reports progress. A live backup tap or a backup/rewrite anchor prevents the idle pass from discarding its history.

The local crash probe runs the built service with generated credentials and isolated temporary data:

```sh
export PATH="$HOME/.local/bin:$HOME/.local/share/mise/shims:$PATH"
export DOTNET_ROOT="$HOME/.local/share/mise/dotnet-root" DOTNET_PROCESSOR_COUNT=4
nice -n 19 python3 e2e/env/engine-crash.py /path/to/main-build/terrabase.dll
```

It requires Linux, a C compiler, curl with HTTP/2, and the Release build of TerraBase. It kills a node after an acknowledged write, during key publication and during database deletion, then restarts the real service and checks the retained rows and file pairs. The filesystem probe pauses the service at a completed operating-system call before sending SIGKILL. This verifies process-crash behavior; it does not emulate a power failure.

The probe starts the previous build on an isolated copy of every directory left by a killed process before this build recovers it. The previous build may fault a tenant copy according to its existing policy; the assertion here is that the node starts without rejecting the intent value. The rewrite probes seed a stale canonical intent at the existing pre-writer checkpoint, after quiescence has drained normal operations, so successful retirement cannot erase the recovery case before the kill. The post-rename case explicitly verifies refusal with the retained single-value writer. The probe also measures three restarts with 20 databases of about 200 MB and four of about 1 GB, records replay separately from integrity work, and verifies that idle history drains after restart without tenant requests. Additional cases verify a tap opened before a fault returns no bytes afterward and its shipping token is cancelled, a kill after the fault marker flush but before the fault row commit remains permanently refused across two restarts, and thrown integrity codes 11/26 retain intents without fault rows and expose their bounded reason across restart. Direct tenant migration refuses both faulted and pending copies, and the ledger cancels registered unpooled copy readers when fault recording begins. They also verify both HTTP and PostgreSQL refusal and unchanged files for a permanent fault, locked-file and injected-I/O incomplete proofs, 24 unreadable keys across restart, and a zero-length main with its WAL after a kill. All processes and temporary data are removed on exit.

Idle draining was observed after restart without tenant writes or opens: 60,000 retained rows fell through 43,616, 27,232, 10,848 and 1 across four 30-second passes. The final gauge was 2, including the healthy database's retained row.

## Recovery measurements

Each set of three local Linux x64 restarts used 20 main files of 213,561,344 bytes and four of 1,063,346,176 bytes (8.525 GB total), with 1 MiB BLOB rows and no secondary indexes on the payload table. Each sample committed another 16 MiB update per database with automatic WAL actions disabled, left all 24 intents open, and killed the process. WAL files totaled 0.714, 1.429 and 2.143 GB. Times include four logical processors at nice 19 on a shared machine. The harness reserves 24 GB of disk headroom below the filesystem’s 80% limit.

| Run | Recovery phase (s) | Launch to ready (s) | Open and replay (s) | Replay (s/WAL GB) | Integrity (s) | Integrity (s/main GB) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Isolated proof 1 | 34.127 | 38.582 | 2.622 | 3.670 | 16.506 | 1.936 |
| Isolated proof 2 | 30.640 | 34.245 | 1.788 | 1.252 | 16.031 | 1.881 |
| Isolated proof 3 | 44.211 | 47.827 | 2.878 | 1.343 | 19.046 | 2.234 |

The replay timer covers opening the isolated database copy and reading its incarnation, which forces journal recovery. The integrity timer covers the full integrity query. Key unwrapping, isolated file copying, queueing, fault-ledger commits and intent retirement remain in the recovery-phase total. Cache eviction was requested with per-file DONTNEED on only the harness's database and WAL files after each measured kill; no global cache was dropped on this shared host, and fully cold device caches are not claimed.

Startup recovery stays sequential under the creation lock and publishes SYSTEM after one proof attempt per intent. Readiness waits for SYSTEM and the intent journal to open and bootstrap, fault counts and startup proofs to be processed, catalog initialization/verification, platform seed completion, and the normal writable-storage readiness probe. A clustered node with NATS and peers also waits for a known regional owner, a started home-push service and ready home leases. An INCOMPLETE tenant proof does not wait for its background retries before SYSTEM is published or readiness can succeed; that tenant alone stays unavailable. SYSTEM or intent-journal failure still prevents startup. For a planning envelope of 120 databases and 6 GB of main files, with per-database WAL depths covered by these samples, the measured projection is under 198 seconds: 6 × 2.234 s/GB integrity + 120 × 0.565 s maximum open/replay + 5 × 22.287 s isolated-copy/ledger/key overhead + 4.455 s startup overhead. A threefold margin rounds upward to a 600-second planning allowance, below the 1,800-second readiness allowance. Only this measured envelope has that planning allowance: 120 databases, 6 GB and the sampled journal depths. There is no runtime size guard. This is no guarantee for arbitrary file sizes, journal depths, storage speeds, index-heavy schemas or host contention. If a node cannot finish its startup proofs within the release system’s 1,800-second start budget, the release system rolls it back. The operator preserves the data, inspects startup proof timings, pending/fault metrics and disk/key availability, remedies the unavailable resource or restores affected databases from backup into new databases, and retries the release once startup fits the budget. Do not delete evidence or clear a fault to force readiness.

The rollback build was main commit `0d36af3218af15daebddd944cbd492fb469ded8f`. It started successfully on all nine isolated crash-directory copies in each full run, including both rewrite kill points, creation, deletion and all three large-file samples. The main build's existing policy can fault copies after an unclean exit; rollback proof here concerns node startup and readable intent values. A stale single-value intent after a rewrite rename remains the explicitly deferred writer-release case.

The earlier local run took 640.753 seconds, including 89.163 seconds for its admission and incomplete-proof cases; all nine rollback snapshots were retained. This predates the additional fault-marker, tap and integrity-exception cases and is not a timing claim for the current harness.

The separate `engine crash recovery` job runs this harness when engine, driver, harness or their build/workflow inputs change. It reuses the service artifact and builds the PR base revision (the previous push revision on main) separately for rollback checks. It runs alongside the journey shards with its own 25-minute allowance. Either the journey selector or the engine selector runs the reusable workflow. A selected engine job must succeed: the reusable selection guard and `all-green` reject a selected job or workflow that skipped, failed or was cancelled. An unselected engine job may skip. Unrelated changes skip this job. All isolated baseline source and crash data are removed on exit.

## Fault-recording isolation audit

Opened stores cache the wrapped-key fingerprint read at initial load. Recording first reuses an existing fault binding or that store identity; it reads a tenant key only when neither is known, outside both the ledger gate and publication barrier. An unreadable identity in that last case produces a location-bound intent with unavailable creation evidence, keeping only that location refused. Recovery reports it pending until its evidence can be established or explicit deletion clears the location.

Node-wide fail-closed paths were audited:

- `RecordAsync`: creation evidence and deletion/file-existence checks moved before the gate; per-copy identity read failures retain a refused intent. Its remaining catch surrounds only system/intent-ledger reads and commits.
- `FlagAsync`: uses the store’s cached creation identity; its remaining catch covers ledger persistence only.
- `RecordCopyFaultAsync`: removed its blanket node-wide catch; ledger storage failures are classified by the ledger itself.
- `EndOperationAsync`: removed the blanket node-wide retirement catch, which could escalate failures while recording tenant damage; retirement itself accesses only the intent store.
- Rewrite rename durability failure: marks and records the affected copy; no longer fails healthy copies closed.
- Background recovery: tenant recovery and creation-evidence failures return incomplete proofs; the remaining scheduler catch reports inconsistent/unavailable ledger bookkeeping.
- Unknown first-open identities: permanent rows use the creation identity validated by the proof; all-zero unavailable bindings are parsed as unresolved evidence and stay pending. This prevents an identity sentinel written by the recorder from later being treated as node-wide ledger corruption.
- System-copy damage and `InSystemAsync` storage/inconsistency failures remain node-wide because the fault authority itself is unavailable.

Every await while holding the ledger gate was audited:

- Read admission and settle: only fault-row reads from the opened system store; system initialization is resolved before the gate.
- Fault recording and flagging: intent/binding writes, permanent-row reads/writes and intent retirement, all in system/intent stores. No key read or tenant file-existence check remains inside.
- Write-intent admission, retirement and explicit forgetting: only intent, binding and fault rows plus the persisted fault count.
- Retry claim registration: no I/O. Retry result commit: only ledger revalidation and result persistence through `CompleteProofAsync`; the duplicate `FaultIntentProofAsync` call was removed.
- `CompleteProofAsync` awaits only the intent-row check, permanent-fault read/write, result deletion and fault-intent retirement. A changed immutable binding produces an incomplete result rather than recomputing creation evidence under the gate.

No await inside the gate performs tenant-file or network I/O. The ledger’s own storage remains a shared authority and its I/O can delay its users.

## Open-cost measurements

Three Linux x64 local samples used the same startup-hook loop on the original PR head and this fix: dispose one opened tenant store, time its first open, then 1,000 cached engine opens and 1,000 incarnation-aware admission checks used at SQL/PostgreSQL boundaries. Times are milliseconds per open; the host was shared, so the samples describe this run rather than a latency SLA.

The settled store now supplies its cached fault row and creation identity for repeated admission. Copy barriers are forgotten on explicit deletion, while existing leases retain their own instance until they finish.
