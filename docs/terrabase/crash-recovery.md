# Process crash recovery

Database creation flushes the initialized database and wrapped key, publishes the key and syncs the directory hierarchy, then publishes the database and syncs its directory. Startup removes files with the explicit unpublished `.creating` identity. An interrupted creation is distinguished by that identity, never by a zero-length main file.

A missing main file is never proof that a database was deleted: a lost mount, a partial restore, an operator move or a disk fault leave the same picture, and the wrapped key is the only way to read the data and every copy encrypted with it. Startup therefore never deletes a key because its main file and write-ahead log are absent. A key with no main file, no write-ahead log and no deletion marker, with or without an interrupted creation of the same database beside it, is renamed in its directory to `.<database>.<nonce>.retained-key` with a fresh nonce, never over an existing file, and the directory is synced. The engine logs a warning naming both files and `terrabase.storage.retained_keys` reports how many retained keys the last start found. No lookup, creation, recovery, deletion or audit path treats a retained key as a database key or removes it, a new database with the same id can be created beside it, and the unregistered-file audit counts it as an unrecognized file. Removing it is an operator decision. The only key TerraBase deletes without a deletion request is the one a failed publication moved into place itself in the same process when the database rename did not happen: that key was created for this publication and encrypted only its unpublished `.creating` file, which the same cleanup removes and which backups and replicas never read.

Deletion first flushes a `.deleting` marker and its directory, removes the database and syncs its directory, then removes its wrapped key, other sidecars and marker. It syncs those removals and any removed parent directories before completing. Startup completes deletion only when that marker proves deletion was requested. A missing main file without that marker never deletes its key or log.

A write intent left by an interrupted process triggers a database open, journal recovery and integrity check. A healthy copy whose incarnation is named by its intent is accepted. The intent writer retains its existing single canonical 26-character incarnation. The reader also understands a future source:replacement pair, requiring successful log replay and integrity checking before accepting either named incarnation. This release does not write that pair: a previous release rejects it while opening the catalog. Healthy rewrite ancestry is held only in process memory, with no predecessor recorded in the file. Consequently a crash after a rewrite rename can leave a replacement that the single-value intent cannot identify; that copy remains refused. A later release must introduce the paired writer after the reader has deployed across the rollback window. The rewrite path must not acquire a production caller before the paired intent writer ships; reviewers must verify that its only caller remains the crash harness.

A durable fault-in-progress intent (`run = 0`) immediately refuses that copy at live admission boundaries as well as after restart. Its incarnation stays canonical; a companion `_tb_fault_binding` row records a fingerprint of the immutable wrapped key as its creation identity. Before bootstrap has read the incarnation, the database location and this creation identity bind the intent. Once known, incarnation also identifies the copy independently of its file path. If damage precedes the first incarnation read, the validated creation fingerprint supplies the permanent fault record’s identity after restart; unavailable creation evidence stays pending. An all-zero unavailable fingerprint is a valid unresolved binding, never a permanent fault identity. When neither incarnation nor creation identity is known, the canonical intent uses the database location id; its unavailable binding keeps it pending, and the prior release can still parse the intent. A later incarnation cannot overwrite the marker. A different wrapped key at the same location cannot inherit the old intent as a permanent fault; the old evidence remains and refuses admission at that location until explicit database deletion forgets it. An unavailable or different creation identity keeps the marker pending without opening the owning database or faulting the different copy. A changed key at an uncleared location has no expiry. Operators see `terrabase_storage_proof_pending`, `terrabase_storage_proof_incomplete_total{reason="fault_identity_changed"}` (or `fault_identity_unavailable`), and the warning “A database recovery proof is incomplete and will retry” with that reason. Explicit deletion of the old database clears its intent, fault and binding records; ordinary catalog creation then uses a new database id. Restoring the original key can establish the old creation identity, but finishes its permanent fault rather than admitting it. Do not replace keys or edit ledger rows to bypass refusal. The marker is positive evidence that damage was already being recorded. Recovery completes its permanent fault row before considering any proof for that copy. A healthy proof cannot retire this marker or clear the fault; the marker can be retired only after the fault row is durable.

Recovery has three outcomes:

| Outcome | Evidence | Action |
| --- | --- | --- |
| PASSED | Full integrity returns `ok` and identity matches a named incarnation | Retire intent and admit the copy |
| DAMAGED | A completed integrity query returns a row other than `ok`, a completed check proves a different identity, or the main file is empty or missing after its WAL opens | Persist the bounded fault reason before retiring the intent; refuse all protocols |
| INCOMPLETE | Busy/locked, I/O/storage failure, key unavailable, timeout, interruption/cancellation, constraint or any other inability to complete the proof | Keep intent, record no permanent fault, return retryable unavailable, retry in the background |

Proofs copy the main file and WAL into reserved scratch space, unwrap the existing key without rewriting it, and open only the scratch database. They never delete, truncate, recreate or checkpoint the source database, log or key. Opening an existing recovery snapshot also rejects an empty/missing main before opening; it never repairs it by deletion. Scratch copies are disposable. Shutdown removes empty WAL files only from healthy copies; a faulted copy retains even an empty WAL. `terrabase.storage.faulted.databases` reports the current persisted fault count, including after restart; `terrabase.storage.proof.pending` reports pending databases and `terrabase.storage.proof.incomplete` counts incomplete attempts by bounded reason. At most four copies retry independently, with one claim per copy; copying and native checking hold no global ledger gate. The gate protects admission, claim registration and result bookkeeping, including I/O to the ledger’s own system and intent stores. Creation evidence is computed once outside the gate; commit revalidates the pending claim and immutable fault binding without reopening any tenant file. Each copy retries at exponential delays of 2, 4, 8, 16 and at most 32 seconds; shutdown stops them and retains unresolved intents.

Every exception while executing an integrity check is INCOMPLETE, including engine corruption codes 11 and 26: an unavailable or wrong key can produce the same errors. These exceptions use bounded reason `integrity_engine_corruption`; ordinary storage/I/O failures use `storage`, `busy_or_storage` or `io` as classified. An exception after some result rows also leaves the proof INCOMPLETE. A copy that keeps throwing remains pending and refused until an operator acts; retries have no terminal attempt count. Alert on sustained `terrabase_storage_proof_pending` and increases in `terrabase_storage_proof_incomplete_total{reason="integrity_engine_corruption"}`. Restore key/storage access or restore a backup into a new database; do not clear the intent to admit an unchecked copy.

A fault is never cleared automatically, including after a later successful proof. An operator has the database files, remaining log and wrapped key retained when fault publication completes, plus the persistent fault record with its reason. A checkpoint already running at detection may have finished backfilling and truncating the log before that publication. Supported recovery today is restoring a backup into a new database; that backup may not contain the most recent acknowledged writes. Preserve the originals for investigation before deleting the faulted database.

## Tenant-visible states

| State | HTTP SQL, metadata, shapes and exports | PostgreSQL | WebSocket SQL |
| --- | --- | --- | --- |
| Healthy | Normal responses | Normal queries | Normal result frames |
| Fault intent or permanent fault | `503 copy_faulted` before response headers | `57P03` with `copy_faulted`; new sessions receive a fatal error and disconnect, while established query/transaction operations receive an error | An authenticated upgrade can return HTTP `503 copy_faulted`; first-frame authentication sends an error and closes with policy violation; an established socket sends `copy_faulted` for the refused frame and stays open, refusing subsequent frames |
| Pending proof | `503 recovery_pending` before response headers; middleware supplies `Retry-After: 1` | `57P03` with `recovery_pending`; new sessions receive a fatal error and disconnect, established queries receive an error | An authenticated upgrade can return HTTP `503 recovery_pending`; first-frame authentication sends an error and closes with policy violation; an established socket sends `recovery_pending` and stays open; later frames can succeed after proof passes |
| Node failed closed | `503 copy_faulted` where a response can still be written; readiness fails | `57P03` with `copy_faulted` | Admission/error behavior follows copy faults |

A response or stream already in progress can terminate after bytes already delivered; those bytes cannot be withdrawn. A write with an uncertain commit can return `write_outcome_unknown` instead of a copy error and must not be replayed automatically. Pending refusal has no time bound while the proof cannot complete. Alert on sustained `terrabase_storage_proof_pending`, increases in `terrabase_storage_proof_incomplete_total` by bounded reason, and nonzero `terrabase_storage_faulted_databases`. An incomplete tenant proof does not make healthy copies or node readiness wait for that tenant's retries.

## File mutation boundaries

For one owning tenant copy, recording a fault and modifying its main file or log are mutually exclusive, and no file modification starts after the fault is recorded. A per-copy barrier covers each modification from its final refusal check through completion of the native or filesystem call: writes, checkpoints and truncation, session open and setup, bootstrap and format migration, rewrite source checkpoint, sidecar removal and rename, publication and the failed-publication cleanup of its own key, and empty-log cleanup at shutdown. Recording a fault makes the copy refused in memory at once and then writes the durable fault intent (`run = 0`) to the intent store before it waits for the copy barrier. Writing the intent does wait for the ledger gate and for the intent store's writer; a busy writer is retried with backoff (1 to 32 seconds) until the write succeeds. The intent lives in the ledger's own store, so writing it modifies nothing of the copy, and from the moment it is durable a restart refuses the copy until the fault is settled. A crash before the intent is durable leaves no fault evidence: for damage found by a read nothing was modified, the damage is still on disk and the next read that reaches it records it again; for damage found by a write the write recorded its write intent before it modified the copy, so the restart checks the copy before it is admitted. Publication then takes the same barrier and writes the permanent fault row once it holds it. A modification already inside native or filesystem code when damage is detected therefore completes (a checkpoint can still backfill and truncate the log), the row is written after it, and any modification that acquires the barrier later fails its refusal check without touching the files. A flag raised by an operation that saw damage writes only the intent, without waiting for the barrier; the operation records the row when it ends. Different copies never share a barrier.

The lock order is writer gate, then copy barrier, then revision lock, then ledger gate. Fault recording writes the intent under the ledger gate, releases it, waits for the barrier, then takes the ledger gate again for the row; the ledger gate never waits for a barrier or writer gate, and no code holding it enters a store operation. `CopyMutationBarrier` is the only acquisition point (`EnterMutation` and `EnterMutationAsync` for store work, `PublishFaultAsync` for fault publication, `TryEnter` for creation and the failed-publication cleanup of its own key). A synchronous scope can nest only on its owning thread. Session open, bootstrap and the copy-source open of copy, fork and backup wait for the barrier asynchronously before they take an I/O thread, so a busy copy never holds shared I/O workers; a modification waiting on the barrier waits only for that copy's modification in flight.

Reader session opens take the barrier too: opening a connection to an existing copy can recover its log, and session setup runs statements against the copy's files, so an open is treated as a modification that must not interleave with fault publication. Growing a copy's reader pool therefore waits behind a write statement or checkpoint in flight on that copy; an open session reads without the barrier, and other copies are not affected.

Refusing the copy cancels its operations, and the registered native interrupt stops their root statements, so the wait is in practice the remainder of a checkpoint or filesystem step, bounded by the size of the log or file. Fault publication waits for the modification in flight as long as it takes; the process never stops for it. The copy is already refused in memory and durably, so nothing new can start on it. The wait runs in the background, outside the I/O admission of the operation that found the damage: once the intent is durable, recording returns, and that operation releases its admission slot, its writer gate and its operation scope as it ends. A publication that waits holds only that copy's ledger records and nothing other copies need; while the intent write itself is retried against a busy intent store, the operation that found the damage keeps its admission slot (one slot per copy whose fault is being made durable). When the wait passes the configured query budget plus 30 seconds (35 seconds with the default budget), the node logs once, with the copy, that the publication is still waiting for a modification in flight and adds one to `terrabase_storage_fault_publication_late_total`, then keeps waiting. A process that stops during the wait, for any reason, leaves the durable fault intent: the restart turns it into a permanent fault row (it does not prove the copy healthy and admit it). A deletion that completes during the wait removes the intent and the barrier with the rest of the copy's ledger records, and the waiting publication then writes no row. Healthy modifications have no deadline of their own. The pinned direct-checkpoint ABI calls `core.checkpoint` outside a root statement and offers neither a stepped checkpoint nor an interrupt for that call, so no native patch, ABI, artifact or pin changes in this fix.


| Operation outside a tenant transaction | Refusal |
| --- | --- |
| Session setup and bootstrap/schema migration | Store and session admission check intents, pending proofs and permanent faults; session open, setup and bootstrap hold the copy barrier, link refusal and interrupt root statements |
| Writer eviction and close checkpoint, with or without revision attachment | Queued work takes the copy barrier, checks availability immediately before checkpoint, and holds it through native completion; refusal cancellation still interrupts root statements |
| Revision attachment, catch-up and after-write checkpoint/truncation | Owning writer work holds the copy barrier around attachment, catch-up and after-write indexing/checkpointing; native truncation retains its final connection refusal check |
| Idle CDC trimming, tap acknowledgement/truncation and rewind | Writer work holds the copy barrier and checks availability inside the queued operation, with native interruption; refused stores are skipped; rewind writes through gated transactions |
| Rewrite source checkpoint, sidecar removal and canonical rename | Source-open and source-checkpoint scopes hold the copy barrier; replacement holds it across sidecar removal, rename and directory syncs, with the final refusal check inside the scope |
| Direct tenant format migration and checkpoint | Ledger read admission includes intents and takes a cancellable copy lease; migration then acquires the copy barrier outside the ledger gate, rechecks refusal and holds it through migration, checkpoint and close |
| Creation, copy/fork, restore and log replay target initialization/checkpoint | Targets are fresh unpublished files; copy sources are gated. Canonical publication and the failed-publication cleanup of its own key take the copy barrier without waiting under the creation lock and recheck ledger refusal; busy barriers refuse publication. Detached backup/replay/snapshot scratch is independent of the owning files |
| Graceful native connection close and empty-WAL shutdown cleanup | Owning pooled sessions always deinitialize without graceful checkpoint; terminal copy sources also refuse graceful close. Empty-WAL cleanup takes the copy barrier and rechecks the store after disposal |
| Startup unpublished-creation/rewrite/proof scratch cleanup | Deletes only named unpublished scratch; creation cleanup never deletes a canonical main or WAL. It never deletes a key: a published key with no canonical main or WAL beside an interrupted creation, and a tenant key at a location that has no main file, no WAL, no deletion marker and no creation in progress, are both renamed to a retained `.<database>.<nonce>.retained-key` file and counted |
| SYSTEM/intent-store format preparation | Required startup bootstrap; its failure prevents startup. Tenant migration remains behind its ledger lease |
| Replica-cache apply/checkpoint/rebuild | Separate disposable cache files; source pages use gated owning-copy replication. These files are not the faulted owning copy's main or WAL |
| Explicit database deletion and restart completion of `.deleting` | Deliberate exception: deletion removes owning files and forgets fault, intent and binding rows |

There is no autonomous vacuum of owning files. SQL-issued schema/maintenance work follows transaction admission and interruption. Size reads and fsync do not rewrite content.

## Not covered

An upload of a backup segment or snapshot that completes just as a fault is recorded stays in object storage under its final key. Restore discovers segments by listing keys, so it can use that object even though the shipper recorded no success for it. Checks before upload and before recording success remain, and refusal interrupts source reads and prevents a read observed after refusal from reaching a new upload. An upload already in flight can finish despite cancellation; this PR does not provide complete reader or publication protection. Closing this window needs a publication record checked by restore, in the follow-up **restore uses only segments the shipper recorded as published**. The backup object format and restore reader are unchanged.

Connections explicitly use WAL journaling. Point-in-time rewind commits with full synchronization. Change capture without a backup tap can discard completed transactions while respecting active shape, replica and rewrite retention floors. A sequential idle pass lists databases on disk every 30 seconds, including unopened databases after restart, and skips busy writers. It does not open a copy it knows from memory has nothing to do: an open copy whose change history was observed empty, an unopened copy whose last visit left it empty and that has not been opened since, and a copy with a pending proof or durable fault intent. A refused copy is logged once per change of its refusal, not on every pass. A copy that the pass itself opened has its writer closed again through the normal eviction path (checkpoint under the copy barrier, then its idle sessions closed), so the pass does not leave every database's connections open; the store object, about 25 KiB of managed memory, stays resident until deletion. With 1,000 idle databases on a shared Linux x64 host (two local samples), the first pass after a restart opened 849 to 860 of them and took 23 to 31 seconds, left 5 or 6 connections open (66 without the eviction) and raised resident memory by 213 to 261 MiB with a peak of 430 to 440 MiB; every later pass opened no database and took 5 to 19 ms. Each database trims at most 16,384 rows and 64 MiB per visit (one oversized row may exceed the byte allowance); the retained-row gauge reports progress. A live backup tap or a backup/rewrite anchor prevents the idle pass from discarding its history.

The local crash probe runs the built service with generated credentials and isolated temporary data:

```sh

export DOTNET_ROOT="$HOME/.local/share/mise/dotnet-root" DOTNET_PROCESSOR_COUNT=4
nice -n 19 python3 e2e/env/engine-crash.py /path/to/main-build/terrabase.dll
```

It requires Linux, a C compiler, curl with HTTP/2, and the Release build of TerraBase. It kills a node after an acknowledged write, during key publication and during database deletion, then restarts the real service and checks the retained rows and file pairs. The filesystem probe pauses the service at a completed operating-system call before sending SIGKILL. This verifies process-crash behavior; it does not emulate a power failure.

The probe starts the previous build on an isolated copy of every directory left by a killed process before this build recovers it. The previous build may fault a tenant copy according to its existing policy; the assertion here is that the node starts without rejecting the intent value. The rewrite probes seed a stale canonical intent at the existing pre-writer checkpoint, after quiescence has drained normal operations, so successful retirement cannot erase the recovery case before the kill. The post-rename case explicitly verifies refusal with the retained single-value writer. The probe also measures three restarts with 20 databases of about 200 MB and four of about 1 GB, records replay separately from integrity work, and verifies that idle history drains after restart without tenant requests. Publication cases verify that a held native checkpoint orders the durable intent before its release and the fault row after it; that a checkpoint held past the publication bound leaves the node ready and serving other copies over HTTP and PostgreSQL, with the copy refused and its intent durable, and that a kill during that wait restarts with the copy permanently faulted; that a barrier held without a write intent at detection, then a kill, also restarts refused; that a deletion completing while publication waits leaves no fault row and a healthy same-id creation; that kills at the main-file and marker removal of a deletion restart deleted and forgotten; and that a memory budget saturated by tenant reservations neither blocks fault recording or proof retries nor fails the node closed. Additional cases verify a tap opened before a fault returns no bytes afterward and its shipping token is cancelled, a kill after the fault marker flush but before the fault row commit remains permanently refused across two restarts, and thrown integrity codes 11/26 retain intents without fault rows and expose their bounded reason across restart. Direct tenant migration refuses both faulted and pending copies, and the ledger cancels a registered direct migration reader: a recorded fault cancels it once publication holds the copy's barrier, so a migration already holding the barrier completes first, and a flag cancels it when the durable intent is written. They also verify both HTTP and PostgreSQL refusal and unchanged files for a permanent fault, locked-file and injected-I/O incomplete proofs, 24 unreadable keys across restart, and a zero-length main with its WAL after a kill. All processes and temporary data are removed on exit.

Idle draining was observed after restart without tenant writes or opens: 60,000 retained rows fell through 43,616, 27,232, 10,848 and 1 across four 30-second passes. The final gauge was 2, including the healthy database's retained row.

## Recovery measurements

Each set of three local Linux x64 restarts used 20 main files of 213,561,344 bytes and four of 1,063,346,176 bytes (8.525 GB total), with 1 MiB BLOB rows and no secondary indexes on the payload table. Each sample committed another 16 MiB update per database with automatic WAL actions disabled, left all 24 intents open, and killed the process. WAL files totaled 0.714, 1.429 and 2.143 GB. Times include four logical processors at nice 19 on a shared machine. The harness reserves 24 GB of disk headroom below the filesystem’s 80% limit.

The replay timer covers opening the isolated database copy and reading its incarnation, which forces journal recovery. The integrity timer covers the full integrity query. Key unwrapping, isolated file copying, queueing, fault-ledger commits and intent retirement remain in the recovery-phase total. Cache eviction was requested with per-file DONTNEED on only the harness's database and WAL files after each measured kill; no global cache was dropped on this shared host, and fully cold device caches are not claimed.

Startup recovery stays sequential under the creation lock and publishes SYSTEM after one proof attempt per intent. Readiness waits for SYSTEM and the intent journal to open and bootstrap, fault counts and startup proofs to be processed, catalog initialization/verification, platform seed completion, and the normal writable-storage readiness probe. A clustered node with NATS and peers also waits for a known regional owner, a started home-push service and ready home leases. An INCOMPLETE tenant proof does not wait for its background retries before SYSTEM is published or readiness can succeed; that tenant alone stays unavailable. SYSTEM or intent-journal failure still prevents startup. For a planning envelope of 120 databases and 6 GB of main files, with per-database WAL depths covered by these samples, the measured projection is under 258 seconds: 6 × 2.984 s/GB integrity + 120 × 0.663 s maximum open/replay + 5 × 30.763 s isolated-copy/ledger/key overhead + 6.458 s startup overhead. A threefold margin rounds upward to an 800-second planning allowance, below the 1,800-second readiness allowance. Only this measured envelope has that planning allowance: 120 databases, 6 GB and the sampled journal depths. There is no runtime size guard. This is no guarantee for arbitrary file sizes, journal depths, storage speeds, index-heavy schemas or host contention. If a node cannot finish its startup proofs within the release system’s 1,800-second start budget, the release system rolls it back. The operator preserves the data, inspects startup proof timings, pending/fault metrics and disk/key availability, remedies the unavailable resource or restores affected databases from backup into new databases, and retries the release once startup fits the budget. Do not delete evidence or clear a fault to force readiness.

The rollback build was main commit `35a3b2af9ed65b62f0b2ca0885086deb8a193367`. The subsequent rebase changed no TerraBase or native code in that baseline. It started successfully on all nine isolated crash-directory copies in each full run, including both rewrite kill points, creation, deletion and all three large-file samples. The main build's existing policy can fault copies after an unclean exit; rollback proof here concerns node startup and readable intent values. A stale single-value intent after a rewrite rename remains the explicitly deferred writer-release case.

The earlier local run took 640.753 seconds, including 89.163 seconds for its admission and incomplete-proof cases; all nine rollback snapshots were retained. This predates the additional fault-marker, tap and integrity-exception cases and is not a timing claim for the current harness.

The separate `engine crash recovery` job runs this harness when engine, driver, harness or their build/workflow inputs change. It reuses the service artifact and builds the PR base revision (the previous push revision on main) separately for rollback checks. It runs alongside the journey shards with its own 25-minute allowance. Either the journey selector or the engine selector runs the reusable workflow. A selected engine job must succeed: the reusable selection guard and `all-green` reject a selected job or workflow that skipped, failed or was cancelled. An unselected engine job may skip. ## Shutdown keeps fault evidence

After any shutdown, clean or not, a copy that was refused in memory is either durably faulted or checked at the next start. A clean shutdown stops the background proof retries, drains admitted operations, then writes every outstanding fault intent once while nothing else uses the intent store, and only then stops the fault retries. When it clears this run's write intents, it keeps those of every copy that has a fault intent in memory, a fault being recorded or flagged, or a fault on its open store, so a copy whose fault intent could still not be written is checked before it is admitted. A deletion marks its location as being deleted under the ledger gate when it forgets the ledger records and clears the mark only after the deletion marker file is removed (startup clears it after completing an interrupted deletion); while the mark is set, fault recording, flags and proof completion for that location write nothing. For fault recording and restart proofs only, a location with no main file and no write-ahead log counts as deleted whatever marker or key files remain: no fault is recorded for it and a pending write proof passes. No file, key, catalog row, replica or backup is deleted on that rule.

## Fault-recording isolation audit

Opened stores cache the wrapped-key fingerprint read at initial load. Recording first reuses an existing fault binding or that store identity; it reads a tenant key only when neither is known, outside both the ledger gate and publication barrier. An unreadable identity in that last case produces a location-bound intent with unavailable creation evidence, keeping only that location refused. Recovery reports it pending until previously bound evidence can be established or explicit deletion clears the location. If no creation identity was available to bind, restoring a key cannot establish that missing historical evidence; preserve the originals and restore into a new database, then explicitly delete the old one. The affected database returns `recovery_pending`; the pending metric and incomplete-proof warning are aggregate signals, not a per-database inventory.

Node-wide fail-closed paths were audited. Only failures that mean the ledger's own storage is unreadable or inconsistent fail the node closed: `InvalidDataException`, `UnauthorizedAccessException`, an `IOException` other than a memory-budget refusal, and SQLite I/O or corruption codes 10, 11 and 26 from the system or intent store. A busy system writer, a full I/O queue or a full memory budget is never a reason.

- `InSystemAsync`: the single place where ledger storage failures fail the node closed, with the classification above.
- `RecordAsync`: opening the system store fails closed only for the classification above. The intent write and the row write each retry a busy store with backoff (1 to 32 seconds) until they succeed; meanwhile the copy stays refused in memory. The barrier wait and the row write run in the background after the intent is durable; a failure there is logged and leaves the copy refused with its intent, which the next start turns into a permanent fault. Other failures of the intent write propagate to the caller without failing the node.
- `FlagAsync`: retries a busy store the same way; it catches only an unusable ledger, already failed closed by `InSystemAsync`, so the operation's own error is not replaced.
- Background proof retries: a busy store leaves the proof pending and backs off. A retry fails the node closed only for an unusable ledger; any other failure of one retry is logged, leaves that proof pending with a longer backoff, and the loop keeps retrying every other pending proof.
- `RecordCopyFaultAsync` and `EndOperationAsync`: no node-wide catch; ledger storage failures are classified by the ledger itself.
- Rewrite rename durability failure: marks and records the affected copy; no longer fails healthy copies closed.
- Unknown first-open identities: permanent rows use the creation identity validated by the proof; all-zero unavailable bindings are parsed as unresolved evidence and stay pending.
- System-copy damage remains node-wide because the fault authority itself is unavailable.

The ledger's bookkeeping does not draw from the node memory budget, which tenants can fill. It holds a few kilobytes of its own state: each statement reads or writes at most one fault, intent or binding row (three 26-character ids, an incarnation and a reason of at most 256 characters), writes are serialized by the ledger gate and the system writer, and startup recovery reads intents in pages of 128 rows.

Explicit deletion removes the files except the `.deleting` marker, then forgets the copy's ledger rows and barrier, then removes the marker. A start that finds a marker without a main file removes the remaining files, forgets the copy's ledger rows when the system store opens, and only then removes the marker, so a crash at any step ends deleted and forgotten.

Rolling back to a build older than this one turns every remaining write intent, including this build's pending proofs, into a permanent fault. That is safe, but a copy that was only pending becomes faulted. A fault is never cleared in place: after a rollback, keep the copy's files, restore its latest backup into a new database, then explicitly delete the faulted database, which removes its fault row; a later creation at the same id is healthy.

Every await while holding the ledger gate was audited:

- Read admission and settle: only fault-row reads from the opened system store; system initialization is resolved before the gate.
- Fault recording and flagging: intent/binding writes, permanent-row reads/writes and intent retirement, all in system/intent stores. No key read or tenant file-existence check remains inside.
- Write-intent admission, retirement and explicit forgetting: only intent, binding and fault rows plus the persisted fault count.
- Retry claim registration: no I/O. Retry result commit: only ledger revalidation and result persistence through `CompleteProofAsync`; the duplicate `FaultIntentProofAsync` call was removed.
- `CompleteProofAsync` awaits only the intent-row check, permanent-fault read/write, result deletion and fault-intent retirement. A changed immutable binding produces an incomplete result rather than recomputing creation evidence under the gate.

No await inside the gate performs tenant-file or network I/O. The ledger’s own storage remains a shared authority and its I/O can delay its users.

## Open-cost measurements

Three Linux x64 local samples used the same startup-hook loop on the original PR head and this fix: dispose one opened tenant store, time its first open, then 1,000 cached engine opens and 1,000 incarnation-aware admission checks used at SQL/PostgreSQL boundaries. Times are milliseconds per open; the host was shared, so the samples describe this run rather than a latency SLA.

The settled store now supplies its cached fault row and creation identity for repeated admission. Each open still checks live fault/pending refusal, cancellation and file presence; recording faults updates the cached row, and initialization settlement revalidates ledger generation. First load still fingerprints the immutable wrapped key. No process-wide key or admission cache outlives an opened store. Copy barriers are forgotten on explicit deletion, while existing leases retain their own instance until they finish.
