# Inspect one existing erasure

The deletion receipt capability authorizes `GET /v1/terrascale/account/deletion/history` on ts-auth. Use the same protected `X-TerraScale-Deletion-Receipt` header as the logical deletion status route. An optional `organization` query must name a candidate organization bound to that receipt. The response contains only `erasureId`, the immutable `requestedAt`, and auth cleanup progress. It contains no account identifier, email, natural-key fence, document contents or credentials. The receipt expires normally; this route grants no ongoing access after expiry. A missing or retired job returns 404, which does not certify physical completion.

With that erasure id, FR1 can read `GET /admin/history-erasures/{erasure}` on each TerraBase internal listener using the existing peer credential through a protected header file. The public listener returns 404 and the internal listener rejects requests without the peer credential. The response gives one catalog snapshot's status, expected/current holders, final cuts, completed rewrite receipts and backup barrier metadata. Settlement tokens are never returned. Both readers send `Cache-Control: no-store` and neither advances cleanup, settlement, rewrites or backup verification. An unsupported/uninitialized catalog returns 503 without initializing it; a missing record returns 404, not completion.

For generation lineage, independently authenticate the generation certificate with the existing service reader. Check its generation and initial position-zero snapshot binding, its incarnation equals the completed rewrite's `target`, and its offset is at least the rewrite's `offset`. Use `system` for SYSTEM and `residue` for the auth file. A listing, timestamp, HTTP 200 or matching file name is insufficient. Backup retention and all-holder retirement remain separate acceptance barriers. Keep operational evidence limited to these metadata fields and never publish header files, receipt capabilities, keys or whole auth documents.
