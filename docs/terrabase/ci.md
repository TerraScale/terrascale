# CI and releases

`.github/workflows/ci.yml` runs on every pull request, merge-group check and push to main. The repository is public and every job runs on GitHub-hosted `ubuntu-latest`; the old `CI_RUNNER` variable has been removed. Its one required check, `test`, passes when every area job that ran passed. The area jobs run in parallel. Each exports its `build-<area>` layer after whitespace format, Release compilation with analyzers as errors, static checks and service publication, then runs Fast without caching test results. Fast, Slow, preview and production images reuse that compiled layer with identical build arguments.

| Job | Stage | Runs on a pull request when these change |
|---|---|---|
| `libs` | `test-libs` | libs, `src/TerraScale.CLI`, `benchmark/dotnet`, shared files |
| `auth` | `test-auth` | auth (`src/TerraScale.Authentication*`, its tests, `docs/auth`, `scripts/auth`), `src/TerraBase`, libs, shared files |
| `terrabase` | `test-terrabase` | TerraBase (`src/TerraBase*`, its tests, `scripts/terrabase`), libs, shared files |

Shared files are the root build files (`Dockerfile`, `Makefile`, `Directory.*`, `TerraScale.slnx`, `global.json`, `NuGet.config`, `.editorconfig`, `BannedSymbols.txt`) and `ci.yml`; the `changes` job holds the exact filters. A pull request that touches none of them (docs only) runs no area job. Pushes to main, merge-group checks and `workflow_dispatch` run every area. Test hosts retain an eight-CPU .NET and GC heap budget across runner types; production images retain automatic Fly CPU discovery. Only push-to-main area builds write their scoped GitHub Actions caches (`libs`, `auth`, `terrabase`); PRs, merge-group checks, Slow, previews and runtime-image builds restore only. NuGet restore lives in a separate layer keyed by project, lockfile and MSBuild manifest contents, so application-source changes reuse packages while dependency changes run locked restore again. The native E2E job caches NuGet packages using every repository and SDK lockfile. `dotnet tool restore` is used only by local `make dev` (Aspire); CI uses SDK commands and does not install unused development tools. Runtime images copy the already published executable, without another restore or publish. Test stages always execute even when compilation is cached. Newer PR updates cancel superseded PR tests. Main and merge-group runs are never cancelled by newer commits; freshness checks skip superseded deployments before mutation. The newest main must still pass Fast for its exact tree; if it fails, no replacement rollout starts. The `test` job always runs and fails when any area job failed or was cancelled, so it reports on every pull request even when every area was skipped.

- Reproduce it locally with `make docker-test`, which builds the `test` stage: all three areas in parallel (needs `../ts-dotnet`; ts-auth's tests start the TerraBase built from the same tree). CI is the gate: no local test/check run is required before pushing or opening a PR (user decision 2026-10-14).
- Fork pull requests receive no SDK, storage or Fly secrets. Because Fast needs the private SDK checkout, their `test` check fails explicitly until the changes run on a branch in this repository; skipped area jobs cannot qualify a fork for merge. Secret-bearing PR jobs run only for branches in this repository.
- Heavy suites (the slow suites, and the 1M-document strict tests and benchmarks once CI runs them) run in independent, non-blocking `slow (auth)` and `slow (terrabase)` jobs (`--target test-slow-auth` / `test-slow-terrabase`, eight-heap test hosts); a failure in one never prevents the other suite from running. They wait for their area builds to become available, including after a Fast failure. Both run only on pushes to main, on `workflow_dispatch`, and on pull requests labelled `full-ci`; `make test-slow` runs them locally. The combined Docker target `test-slow` exports `auth/{log,exit}` and `terrabase/{log,exit}`. TerraBase Slow requires the bucket-scoped `TIGRIS_CI_CREDENTIALS` repository secret, mounted through BuildKit as `tigris-ci`; missing credentials fail instead of skipping the real-storage test. The durable private bucket is `ts-terrabase-ci` in org `terrascale`. Each invocation prefixes all objects, including `_system` keys, with a fresh ULID and deletes only that prefix after shutdown. No org-level storage-create token reaches CI. For local Slow, load `~/.config/terrascale/tigris-ci.env` privately; for Docker Slow, pass `--secret id=tigris-ci,src=<credential-file>`. Only main opens `slow-failure` issues, including when a build produces no results; every failed test is reported. Adding the label starts a new run (`pull_request` `labeled`); note that adding *any* label re-runs CI and cancels the running check for that pull request.
- Deploys (push to main, job `deploy`, only the newest main, one rollout at a time): the `images` matrix runs after this run's Fast gate, copies the cached published TerraBase and ts-auth executables into runtime images, and pushes each once with its scoped Fly token. The rollout reuses those images, with TerraBase first and ts-auth after it. `scripts/fly/current-main.sh` skips a superseded run before image builds and rechecks main after Fast; API failures block deployment. A superseded rollout does not run live E2E. The final `deploy-status` job fails current main if its quality gate, deployment or live E2E fails or is skipped; API errors also fail the guard. Deploy requires `images` and `test` from the same workflow run; it never polls or accepts a different run's Fast result. The Dockerfile's `terrabase` and `ts-auth` stages are the self-contained release executables on `runtime-deps:11.0-resolute-chiseled` (no shell), pushed to `registry.fly.io/<app>:<sha>`. `scripts/fly/deploy.sh` rolls each app (`ts-terrabase`, then `ts-auth`; config in `src/TerraBase/fly.toml` and `src/TerraScale.Authentication/fly.toml`) to gru, sjc and fra in that order, checking `/healthz` and `/backupz` on each region's new machine (`fly-force-instance-id`) and the commit it runs, and writes each region's elapsed time and UTC start/end timestamps to the job summary. A failed check stops the rollout. For TerraBase a storage-format gate runs first (see below). Secrets: one Fly deploy token per app (`FLY_TOKEN_TS_TERRABASE`, `FLY_TOKEN_TS_AUTH`).
- PR previews (job `preview`, after `test` passes): `scripts/fly/preview.sh` runs app `ts-pr-<n>` (org `terrascale-previews-515`, token `FLY_TOKEN_PREVIEWS`) as a two-region TerraBase cell, because a TerraBase write is acknowledged only once a peer in another placed region holds it. gru runs both images as one shared 2 CPU / 1 GB multi-container machine that stops when idle and starts on a request; sjc runs a TerraBase-only shared 1 CPU / 512 MB replica with `autostop: "off"`, so it keeps running until the preview is deleted, and serves no ts-auth route. Each machine has its own 1 GB volume: two machines and two volumes per preview. `app` creates whichever of the two volumes is missing; `machine` creates or updates one machine per region. `app` rejects unexpected volumes before creating missing volumes; `machine` rejects unexpected machines or volumes and requires both regional volumes before changing machines. On a cache miss, preview builds the full checked area layer even when its area job was path-skipped. Each container receives only its own secret mappings. ts-auth runs only on gru and its normal startup provisions its issuer and preserves existing keys. Both TerraBase `/readyz` checks, each pinned to its machine with `fly-force-instance-id`, then ts-auth's `/readyz`, including auth storage and signing-key bootstrap, must pass before the workflow comments `https://ts-pr-<n>.fly.dev` on the PR. A readiness failure remains failed and collects the failing machine's buffered logs with the existing preview token; public output contains only fixed readiness causes, known exception types, HTTP status codes and integer parsing counts, never raw messages, stacks or secret values. The parser accepts flyctl’s multiline JSON entries; its counts distinguish an empty buffer, an unsupported application log shape and logs with no matching readiness events. `previews.yml` deletes it when the PR closes. Its hourly sweep also deletes closed-PR previews and orphan buckets, and expires open previews older than 24 hours. Every deletion shares that PR’s creation concurrency group. Close cleanup cancels the same PR’s preview job before deletion; other PRs’ cleanup runs independently. A late-starting preview reads the current PR state and creates resources only while the PR is open.
- Other packages are not published automatically. Build an artifact you need with its `make` target, for example `make auth-publish`.

## Storage format and the storage train

TerraBase never migrates a data directory: a build refuses a directory written by another storage format. The format is
`StorageFormat.Id` (`src/TerraBase/Engine/Sqlite/StorageFormat.cs`): the hand-bumped `StorageFormat.Version`, then the
first 12 hex digits of the schema digest. A directory records it in its lock file on create; `/healthz`, `/readyz` and
`/backupz` report it as `storageFormat`, and `terrabase --storage-format` prints the format an image writes.

- Rollout gate: before any update, `scripts/fly/deploy.sh` compares the new image's format with every serving region's
  `/healthz`, pinned with `fly-force-instance-id`. Any different or unversioned format fails before mutation. Equal
  formats roll out automatically. An unavailable region can still be repaired by its new image, but a failed deploy or
  live check stops the rollout. Automatic deployment never invokes `volume-reset.sh` or wipes data.
- Approved cluster reset: one executor first waits for the format-changing main push run to complete and verifies its
  format refusal caused no deployment. Hold all main merges and push-run retries until recovery completes; check that
  no main CI push run is queued or running before each regional reset. Stop auth writers and all old TerraBase machines,
  then stage **every** old TerraBase machine on the approved image with `--skip-start` before starting any new-volume
  clone. The target executable refuses old-format volumes even if Fly autostarts an old machine, preventing old-peer
  refill. The sole executor runs `scripts/fly/volume-reset.sh <app> <region> --image <target>` in gru, sjc and fra, with
  snapshots and pinned health/readiness/backup checks. After all three reset regions are healthy, retry that same run's
  failed deploy job so normal deployment, auth and E2E finish. This retains automatic deployment without a deploy switch.
  The marker `ops/fly/greenfield-no-customer-data` must contain `storage-format=<StorageFormat.Id>` matching the target
  executable; another version or schema digest needs separate approval. Remove the marker only after gru, sjc and fra
  have all completed the approved reset and the normal rollout passes. Each regional reset records its snapshot ID.
- Formats: 2 was SQLite (Microsoft.Data.Sqlite); 3 is Turso (T1); 4 drops the change feed and history tables (R2c-2). A format-3 build refuses a format-2 data directory at
  start with `data directory has storage format 2-…; this build writes 3-…`; there is no conversion.
- Storage train: a pull request that changes what is on disk bumps `StorageFormat.Version` and carries the label
  `storage-format`. One that touches a storage file without changing what is on disk carries `storage-format-unchanged`.
  The `test` job enforces this (`scripts/terrabase/storage-format-check.sh`, which also holds the storage file list kept by
  the storage owners); it reads the labels live, so after labelling re-run the failed job (`gh run rerun <run> --failed`).
- Batch approved storage changes into one format bump before a coordinated cluster reset. Hold main merges and retries
  during that reset. Deploy jobs share one concurrency group to prevent overlap. A new main push leaves an active rollout running; only the newest exact-tree Fast-qualified main starts a replacement after the shared deploy group is free. The replacement fixes forward through every region with the same storage and live-health gates.
