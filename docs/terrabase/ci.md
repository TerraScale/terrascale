# CI and releases

`.github/workflows/ci.yml` runs on every pull request, merge-group check and push to main. The repository is public and every job runs on GitHub-hosted `ubuntu-latest`; the old `CI_RUNNER` variable has been removed. Its one required check, `test`, passes when every `fast` area job that ran passed. The area jobs run in parallel. Each exports its `build-<area>` layer after whitespace format, Release compilation with analyzers as errors, static checks and service publication, then runs Fast without caching test results. Slow and the ghcr images reuse that compiled layer in the same job.

| Job | Stage | Runs when these change |
|---|---|---|
| `libs` | `test-libs` | libs, `src/TerraScale.CLI`, `benchmark/dotnet`, `scripts/ci`, shared files |
| `auth` | `test-auth` | auth (`src/TerraScale.Authentication*`, its tests, `docs/auth/*.yaml`, `scripts/auth`), libs, shared files; in merge groups also `src/TerraBase` (its tests start that TerraBase) |
| `terrabase` | `test-terrabase` | TerraBase (`src/TerraBase*`, its tests, `scripts/terrabase`), libs, shared files |

Shared files are the root build files (`Dockerfile`, `Makefile`, `Directory.*`, `TerraScale.slnx`, `global.json`, `NuGet.config`, `.editorconfig`, `BannedSymbols.txt`) and `ci.yml`; the `changes` job holds the exact filters. Pull requests compare with their base, merge-group checks with the queue base and pushes to main with the previous main; a change that touches none of them (docs only) runs no area job. `workflow_dispatch` runs every area. On pushes to main the `main` job replaces `fast`: the merge group already ran Fast on that exact tree, so `main (auth)` and `main (terrabase)` build once, write the area cache, publish `ghcr.io/terrascale/{terrabase,ts-auth}:<sha>` and `:main` (linux/amd64 + linux/arm64, digests in the job summary) and run Slow. libs has no `main` job and restores the `terrabase` cache. Test hosts retain an eight-CPU .NET and GC heap budget across runner types; production images retain automatic Fly CPU discovery. Only the `main` jobs write their scoped GitHub Actions caches (`auth`, `terrabase`); PRs and merge-group checks restore only. NuGet restore lives in a separate layer keyed by project, lockfile and MSBuild manifest contents, so application-source changes reuse packages while dependency changes run locked restore again. The native E2E job caches NuGet packages using every repository and SDK lockfile. `dotnet tool restore` is used only by local `make dev` (Aspire); CI uses SDK commands and does not install unused development tools. Runtime images copy the already published executable, without another restore or publish. Test stages always execute even when compilation is cached. A newer push cancels the older run of the same pull request; merge-group, main and dispatched runs each have their own group and are never cancelled. The `test` job always runs and fails when any area job failed or was cancelled, so it reports on every pull request even when every area was skipped.

- Reproduce it locally with `make docker-test`, which builds the `test` stage: all three areas in parallel (needs `../ts-dotnet`; ts-auth's tests start the TerraBase built from the same tree). CI is the gate: no local test/check run is required before pushing or opening a PR (user decision 2026-10-14).
- Fork pull requests receive no SDK or storage secrets. Because Fast needs the private SDK checkout, their `test` check fails explicitly until the changes run on a branch in this repository; skipped area jobs cannot qualify a fork for merge. Secret-bearing PR jobs run only for branches in this repository.
- Heavy suites (the slow suites, and the 1M-document strict tests and benchmarks once CI runs them) run as non-blocking steps after the build in their area's job (`--target test-slow-auth` / `test-slow-terrabase`, eight-heap test hosts); a failure marks the step, never the job or `test`, and one area never stops the other. They run on pull requests that touch their area (user decision Q-MAIN-GREEN) and in the `main` jobs; merge-group checks run Fast only. `make test-slow` runs them locally. The combined Docker target `test-slow` exports `auth/{log,exit}` and `terrabase/{log,exit}`. TerraBase Slow requires the bucket-scoped `TIGRIS_CI_CREDENTIALS` repository secret, mounted through BuildKit as `tigris-ci`; missing credentials fail instead of skipping the real-storage test. The durable private bucket is `ts-terrabase-ci` in org `terrascale`. Each invocation prefixes all objects, including `_system` keys, with a fresh ULID and deletes only that prefix after shutdown. No org-level storage-create token reaches CI. For local Slow, load `~/.config/terrascale/tigris-ci.env` privately; for Docker Slow, pass `--secret id=tigris-ci,src=<credential-file>`. Only main opens `slow-failure` issues, including when a build produces no results; every failed test is reported. Labels never start or cancel a run.
- Deploys: CI does not deploy. The `main` jobs publish `ghcr.io/terrascale/{terrabase,ts-auth}:<sha>` and `:main` for each area a push to main changed, and ts-orch (TerraScale/ts-orchestrator) deploys them. PR previews are parked until ts-orch runs them.
- Other packages are not published automatically. Build an artifact you need with its `make` target, for example `make auth-publish`.

## Storage format and the storage train

TerraBase never migrates a data directory: a build refuses a directory written by another storage format. The format is
`StorageFormat.Id` (`src/TerraBase/Engine/Sqlite/StorageFormat.cs`): the hand-bumped `StorageFormat.Version`, then the
first 12 hex digits of the schema digest. A directory records it in its lock file on create; `/healthz`, `/readyz` and
`/backupz` report it as `storageFormat`, and `terrabase --storage-format` prints the format an image writes.

- Formats: 2 was SQLite (Microsoft.Data.Sqlite); 3 is Turso (T1); 4 drops the change feed and history tables (R2c-2). A format-3 build refuses a format-2 data directory at
  start with `data directory has storage format 2-…; this build writes 3-…`; there is no conversion.
- Storage train: a pull request that changes what is on disk bumps `StorageFormat.Version` and carries the label
  `storage-format`. One that touches a storage file without changing what is on disk carries `storage-format-unchanged`.
  The `test` job enforces this (`scripts/terrabase/storage-format-check.sh`, which also holds the storage file list kept by
  the storage owners); it reads the labels live, so after labelling re-run the failed job (`gh run rerun <run> --failed`).
- Batch approved storage changes into one format bump before a coordinated cluster reset. Hold main merges and retries
  during that reset.
