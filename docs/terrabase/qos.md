# Organization quality of service

Resource admission belongs to the organization and is shared across its projects, databases and credentials. The runtime reads the catalog plan rather than trusting a client-selected plan. Replication and system maintenance retain process safety limits even when commercial quotas do not apply. Platform database requests are not charged request admission: their request admission, queue weights, storage admission, quota decisions and engine limits retain the platform policy. In particular, storage admission remains unlimited and does not acquire the organization storage gate.

## SQL work and memory

SQL statements share the request execution budget in `Features/Sql/SqlLimits.cs`. The native engine enforces query cancellation and value-length bounds. Statement, body, row, byte and transaction-growth limits are in the [SQL contract](sql/native-sql.md). Admission, authorization and the SQL sandbox run before customer work executes.

Request/result buffers reserve process and organization memory before allocation. A reservation lasts until the owned buffer or response is released, including cancellation and error paths. Native allocations and physical I/O are not fully measured by managed reservation estimates. See [memory admission](memory.md) and [shared-process tenancy](shared-process-tenancy.md).

Storage work retains tenant ownership through queues and callbacks. Scheduling is bounded and fair across organizations, but cannot promise hard latency isolation for an already-running native call or a stalled device. Cancellation drains the owned reader and operation gate before releasing resources.

## SQL sessions

Postgres and SQL WebSocket sessions share one organization allowance per process, across credentials, projects and databases. The allowance is twice the plan's concurrent-request limit: 8 for Free, 16 for Starter, 32 for Pro and Team, and 128 for Enterprise. Each process also admits at most 4,096 connections, including connections relayed to another node. At most 2,048 slots may be relays, reserving half the ceiling for locally served sessions. Relay shutdown allows 2 seconds for the close handshake before aborting both sockets and awaiting both forwarding pumps. After authentication, relays and local sessions consume the same organization allowance on the entry process. Forwarded SQL sessions also take the allowance on the home process until their session is disposed. Postgres and frame-authenticated WebSocket sessions share pre-authentication admission: at most 128 concurrent attempts per client address, held until session admission. The bound equals the largest organization session allowance, so one address behind NAT or a serverless egress can warm a full pool at once; the 4,096-connection process ceiling still bounds the total. An attempt above it receives fatal SQLSTATE `53300` (Postgres) or `tenant_busy` with WebSocket close code 1008, both with the message `too many concurrent connection attempts from this address`. One deadline covers the password or auth frame and subsequent credential, tenant and placement validation: five seconds for WebSocket and ten for Postgres. Verified platform traffic bypasses these session and pre-authentication allowances and their accounting; its existing request admission and process safeguards still apply. Header-authenticated WebSocket requests perform HTTP credential, tenant and placement validation before this scope; their session handler enters the same address allowance afterward. Internal forwarded SQL sessions authenticate with the peer credential and use bounded opening frames rather than the public client-address allowance. A Postgres connection from the edge reads its PROXY header first, within the same ten-second handshake bound, so the allowance is charged to the client address it names rather than the edge. Postgres relay establishment shares the proxy's five-second request budget with destination discovery, through the ready response; after it, outgoing writes have a 30-second no-progress allowance. The connection's TCP acknowledged-byte counter renews it even while a flush is still blocked, so bytes already queued in that flush count as progress. A reader can take as long as needed while writes continue making progress; a blocked write with no progress for the allowance closes the session. This applies to local and relayed Postgres answers and to the WebSocket transport, including answers to forwarded SQL sessions. HTTP response minimum data rates are disabled on these session transports because their own progress allowance governs stalled sends. WebSocket keep-alive sends unsolicited pongs without an acknowledgement deadline, so a control frame queued behind an answer cannot abort an active reader. Postgres API-key sessions refresh their internal authorization grant and remain subject to key revocation; the expiry of a cached exchange token does not expire the API key's session. Cancellation drains forwarding before releasing admission. A Postgres connection above the allowance receives fatal SQLSTATE `53300`; a WebSocket receives `tenant_busy` and closes with policy violation, and an unfinished WebSocket authentication closes with policy violation. Browser authentication succeeds only after session admission.

A session with no message in flight and no open transaction disconnects after 30 minutes without a complete protocol message. Client pools should retire or validate idle connections in under 30 minutes. Once a message starts arriving, its deadline is its start plus 30 seconds plus the bytes received divided by 16 KiB/s. Both protocols and the frames a replica region forwards to the home re-evaluate that deadline as bytes arrive, allowing a sustained upload while cutting a byte-at-a-time trickle. WebSocket ping/pong traffic does not count as activity. Executing a statement does not consume either waiting period. While a transaction is open, only the wait for the next client message is bounded by the smaller of five seconds idle in transaction and the remaining five-second total transaction limit. Total age starts at logical BEGIN on a monotonic clock, including BEGIN without a statement; local-to-home promotion preserves that start. Once bytes start arriving, the message-progress deadline replaces the transaction limit. Completing a message and expiring its wait are one decision: either it is processed to the end with the existing statement and request budgets, or the connection closes and its transaction is rolled back. No transaction timer cancels statement execution, authorization, routing, quota acquisition or commit.

There is no hard wall-clock lifetime for a transaction: it can outlive its waiting limit while a statement or commit is in flight, subject to the existing execution budgets. Receiving a message that continues past the total limit is also allowed by the message-progress budget. A client closed for transaction expiry never receives success for that transaction; a client whose commit message was accepted receives the commit's real result when its answer is observed, even after the transaction limit. The entry relays enforce their own input idle and message-progress waits and suspend transaction waiting while a request is executing. A forwarded call includes the origin's remaining duration; the home applies it only at its own next frame wait. A receiver without that duration starts its own five-second limit at receipt. Old builds ignore the extra field and retain their own transaction behaviour; a mixed deployment does not provide the new commit guarantee end to end.

When a forwarded commit or autocommit write has been sent and its answer is lost, the client receives `write_outcome_unknown` (SQLSTATE 08007, HTTP 503), independent of transaction age. The session closes: WebSocket close reason `write_outcome_unknown`, or a fatal PostgreSQL error whose message states that the session is closed. It may have committed: read back the expected data before repeating a non-idempotent write. Lost answers for reads and statements inside an open transaction retain the existing unavailable/transport behaviour. An old server relaying a home answer preserves the unfamiliar error code and message but maps it through its unknown-code defaults: SQLSTATE 0A000 and HTTP 400, rather than 08007 and 503. A WebSocket answer still carries the string code. Do not assume an old intermediary provides the new error mapping or safe retry guidance. Disconnects and failed startup return admission only after session cleanup.

Relayed answers use the same progress rule as input. Once an answer starts arriving, its deadline is its start plus 30 seconds plus the bytes received divided by 16 KiB/s. Before the first answer byte, the entry waits at most ten minutes while the destination keeps acknowledging HTTP/2 keep-alive pings; a destination that leaves a ping unanswered for five seconds is treated as lost. This is a generous waiting ceiling, not a bound on home execution: statement work has a budget, but queue waits and durable commit I/O have no hard wall-clock upper bound. Giving up the wait closes the session without cancelling the home's accepted execution or commit. A close drain is bounded by its two-second closing budget from the start of closing. A stalled read or non-committing answer retains the unavailable response; a published committing request has an unknown outcome. A relay keeps at most 256 requests awaiting an answer per session; while that many are outstanding it stops reading the client's input and resumes as answers are delivered, so a pipelined batch of any size runs as it does at the home and is never closed for its size. A relayed Postgres session keeps its request admission from its first extended-protocol or simple-query message until ReadyForQuery, so a busy organization is refused only between batches and the relay never answers a Sync the home has not seen.

Session metrics expose `terrabase_qos_active_sessions`, `terrabase_qos_relay_sessions`, `terrabase_qos_preauthentication_sessions` and the maximum organization utilization in `terrabase_qos_organization_session_utilization`. `terrabase_qos_session_admissions_total` and `terrabase_qos_preauthentication_admissions_total` count admitted customer sessions and authentication attempts; verified platform traffic does not increment them. `terrabase_qos_session_refusals_total` counts `organization_cap`, `process_ceiling`, `relay_ceiling` and `preauthentication_allowance` by the bounded `kind` label, without organization labels.

Enterprise uses finite runtime ceilings: 2,000 requests/second, a 4,000-request burst, 64 concurrent requests, a 5-second query timeout, 20 million query work units, 400,000 scan rows, 128 MiB scanned bytes, 1 TB storage, 1,000 databases, 100 million monthly writes and 1 billion monthly SQL reads. Engine time replenishes at 8 seconds/second with a 60-second burst. These runtime safety ceilings do not change billing allowances. General SQL VM work is not yet reported by the native driver; the work ceiling currently covers instrumented catalog scans and FTS, alongside the existing execution timeout.

## Storage

SQL writes take the organization quota lease before the database writer. The transaction checks net used-page growth and persists SQL storage accounting atomically. Failed statements and rolled-back work cannot publish a larger unchecked database. Branch and restore publication retain the same quota and identity checks through registration or rollback. A sibling database whose copy is faulted or awaiting its recovery proof counts the last logical size this process measured for it. Without one, it neither causes nor hides a breach: growth that fits even with the sibling's file bytes is admitted, growth that exceeds the quota without the sibling is refused with `storage_quota`, and growth that only the sibling's unknown size would decide, including a sibling whose file is missing, receives the retryable `storage_accounting_busy`.

Storage accounting, physical file bytes, replica copies and backup retention are distinct quantities. A node-local check is not proof of an atomic global physical-disk quota. Disk work also passes [bulk disk admission](disk-admission.md).

## Responses and monthly caps

Preserve the existing rate, concurrency, memory and storage refusal contract, including `Retry-After` where supplied. Never bypass validation to make a request fit. Enterprise plans still observe statement, transaction and process safety bounds.

SQL reads are free with plan fair use; shape reads are free and unmetered. Committed writes count toward the monthly write allowance and cap. Replication does not add billable units. The published pricing catalog and [operation allowance contract](operation-allowance.md) define the current values; do not duplicate a stale plan table here.

A push stream that returns NATS error 10074 is not retried, because the stream wants more replicas than the cluster has.
