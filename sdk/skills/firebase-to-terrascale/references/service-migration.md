# Storage, Functions and client replacement

Read the relevant section after completing the inventory and identity plan.
All examples are migration patterns; use the exact deployed project's documented
API/SDK version and prove each integration in rehearsal.

## Cloud Storage to TerraScale file storage

1. Inventory bucket/object names, generations, size, content type, metadata,
   retention requirements and every reference in documents or client code.
   Record Firebase download-token URLs separately; they are capabilities, not IDs.
2. Freeze uploads, overwrites and deletions during the final copy. Download each
   selected object generation into a private staging directory. For an audited
   bucket with no concurrent writers, this copies the current objects:

   ```sh
   gcloud storage cp --recursive "gs://$FIREBASE_STORAGE_BUCKET" "$STAGING_DIR"
   ```

   This does not migrate rules, ACLs, generations, retention policies or Firebase
   download URLs. Use a manifest to avoid basename collisions and verify the
   source generation has not changed. See
   [gcloud storage cp](https://cloud.google.com/sdk/gcloud/reference/storage/cp),
   [Firebase downloads](https://firebase.google.com/docs/storage/web/download-files).
3. Gate the destination on the [file storage release prerequisite](https://docs.terrascale.tech/guides/file-storage).
   The docs say rollout and live transfer/authorization verification are pending.
   If this project's file API is unavailable, retain Cloud Storage and its rules
   until a complete byte-copy and access rehearsal succeeds.
4. Create target buckets on the backend with unrestricted project credentials.
   Select the immutable metadata owner pointer, for example `/userId`, and set
   independent owner/role read and write grants. A database-restricted credential
   cannot manage project files. Never expose the project credential to a client.
5. Resolve each Firebase UID through the identity map, then upload with metadata
   containing the mapped subject at the bucket owner pointer. Existing Firebase
   role fields in metadata do not create trusted target roles.
6. Store `(source bucket, object name, generation) -> (bucket ID, file ID, SHA-256)`
   in a private durable manifest. The IDs are generated by the target API.
7. Compare source and downloaded target bytes and preserve required business
   metadata separately. Change app references using the manifest, then exercise
   owner, different user, privileged role and unauthenticated access.

TerraScale files and metadata are immutable; replacing one creates a new file.
Maintain a logical alias in SQL for `avatars/<uid>` rather than pretending an
upload overwrites a path. Switch the alias only after completion, and delay old
file deletion until rollback retention expires. Files must contain 1 byte–100 MiB,
metadata is limited to 16 KiB, and file and database storage share the plan
allowance. Empty files or larger objects require a changed representation or
retained object storage. Source: [file storage](https://docs.terrascale.tech/guides/file-storage).

For custom transfers, follow the documented sequence exactly: create an upload
with size and base64 SHA-256, PUT the bytes with returned headers, then complete
before the five-minute capability expires. Do not send app credentials to signed
URLs, follow redirects, or log those URLs. Download capabilities last 60 seconds.
If using the SDK, verify its installed storage API matches the guide; the
[SDK reference](https://docs.terrascale.tech/guides/sdks) warns that published JS
and current source differ.

The `public` grant means **all authenticated project end users**, not anonymous
access. Firebase public URLs cannot be carried across unchanged. For anonymous
website assets, retain the selected public asset host or implement a deliberate
server delivery layer; do not publish a project token. Existing signed downloads
retain their short lifetime after most policy changes. Source:
[owner, public and role grants](https://docs.terrascale.tech/guides/file-storage#owner-public-and-role-grants).

## Cloud Functions to TerraScale Functions

Classify each source function before porting its code:

| Firebase trigger/workload | Replacement plan |
| --- | --- |
| HTTPS `onRequest` | Backend validates/authenticates requests, then invokes a target function |
| Callable `onCall` | Explicit app endpoint replaces callable protocol, auth context and error mapping |
| Scheduled function | UTC cron if the work fits the documented runtime and SQL binding |
| Firestore document create/update/delete | Make the side effect part of the authorized mutation workflow, or write an outbox row in the same SQL batch and process externally |
| Storage finalize/delete | Record an upload-completion/deletion job through the app workflow; retain source event handling while Cloud Storage remains |
| Auth create/delete/blocking hooks | Move business actions into explicit identity workflows or retain a separate identity event worker |
| Pub/Sub, task queue, long jobs, non-JS runtime | Retain an appropriate external worker; do not describe HTTP invocation as an event subscription |

The public [Functions guide](https://docs.terrascale.tech/guides/functions)
documents one JavaScript file, `handler(event)`, an HTTPS or cron trigger and a
database-local `sql` binding. It does not document Firebase event hooks, npm
dependency installation, Firebase Admin runtime or callable protocol support.
Avoid assuming Node filesystem, process, network or secret bindings exist.
Keep integrations needing those facilities in a verified external service.

Port a bounded SQL-only operation, for example:

```js
async function handler(event) {
  const rows = await sql.query(
    "SELECT id, title FROM tasks WHERE workspace_id = ? AND done = 0 ORDER BY id LIMIT 50",
    [event.body.workspaceId],
  );
  return { status: 200, body: rows };
}
```

This assumes the backend has already authorized `workspaceId` and the caller;
it is not a public end-user authorization example. Invocation needs read access,
and the function's SQL uses its own authority. Route privileged operations
through the authorizing backend. Source: [Functions](https://docs.terrascale.tech/guides/functions).

Deploy with the documented `PUT /v1/projects/{project}/databases/{database}/functions/{name}`
body `{source, cron?}`, and call `POST .../functions/{name}/invoke` from the server.
Use a UTF-8 source file and a JSON encoder such as `jq --rawfile`; do not build
JSON with string concatenation or put credentials in arguments. Read logs and
stats after rehearsal. Limits include 256 KiB source, 32 functions per database,
10 s runtime including SQL, 32 MiB memory, 1 MiB request/response and 256 SQL calls.
Source: [Functions deployment and limits](https://docs.terrascale.tech/guides/functions).

For event replacements, assign a stable event ID, atomically record a job with
the business mutation, and checkpoint completion. External effects need their
own idempotency key; a SQL transaction cannot roll back a sent email. Firebase
Firestore events are delivered at least once and may arrive out of order, so
retain equivalent protections when replaying source events:
[Firestore function events](https://firebase.google.com/docs/functions/firestore-events).

## Client reads, listeners and offline behavior

Replace each Firebase operation as a behavior, not a renamed method:

| Source behavior | Target implementation decision |
| --- | --- |
| Document `get`, collection query | Parameterized SQL with explicit IDs, projection, filters, sort and bounded pagination |
| `set`, `update`, batch, transaction | Backend-authorized mutations; map field deletion, increments and array operations deliberately |
| `onSnapshot` | Verified live table shape, or backend query plus bounded refresh |
| `docChanges`, `fromCache`, pending writes | App-derived UI states; no documented identical metadata contract |
| Persistent local cache / offline queue | App-managed cache and conflict protocol, or online-only writes |
| RTDB `onValue`, presence, `onDisconnect` | App refresh/live rows and a separately designed heartbeat/expiry workflow |

Live shapes send a table snapshot then committed changes; shape filters and
column selections are documented. They are not arbitrary Firestore collection
or join subscriptions. A UI assembling several tables must define how it merges
their streams or refreshes a joined backend query. Read rules authorize rows;
a shape's `where` filter is not an access boundary. Sources:
[SQL live shapes](https://docs.terrascale.tech/concepts/sql#live-shapes-and-rules),
[end-user data access](https://docs.terrascale.tech/guides/end-user-authentication#data-access-for-your-users).

The SQL guide marks React/Svelte live examples as requiring the next JS release;
the JavaScript quickstart matches source while npm 0.0.17 is the previous API.
Choose and pin a verified supported installation or use backend SQL refresh
until the required published client is available. An SQL WebSocket transaction
session is not itself a data-change subscription. Sources:
[JavaScript quickstart](https://docs.terrascale.tech/getting-started/javascript),
[SQL transactions](https://docs.terrascale.tech/concepts/sql#transactions).

Firebase's offline cache and queued writes have specific semantics, including
last-write-wins for multiple changes to a document:
[offline persistence](https://firebase.google.com/docs/firestore/manage-data/enable-offline).
The cited TerraScale guides do not document a compatible durable offline cache
and write queue. For an offline requirement, define private per-user cache
storage, schema versions, clear-on-sign-out behavior, mutation IDs, expected row
versions, replay order, tombstones and a user-visible conflict resolution policy.
Reauthorize every queued mutation on reconnect. Verify reload, prolonged loss,
revoked access and stale edits before claiming parity; otherwise require online
mutation and show its state accurately.

Hosting, FCM and Remote Config remain independently deployed dependencies until
their replacements pass real app flows. A SQL configuration table can store
settings but does not recreate Firebase targeting, experiments, fetch caching
or push notifications. Keep source SDK initialization only for the services
retained in the inventory, then repeat the repository searches before cleanup.
