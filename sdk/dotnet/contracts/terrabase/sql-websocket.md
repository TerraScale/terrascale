# SQL WebSocket contract

Generated by scripts/sdk/export-sql-contracts.py from src/TerraBase/Features/Sql/SqlSocketEndpoint.cs.

Upgrades to a WebSocket (subprotocol terrascale.sql.v1 when offered). Authenticate with the same bearer credential and sql:read scope as sql/execute, in one of two ways: an Authorization header on the upgrade, or, where the client cannot set headers (browsers), {"type":"auth","token":"…"} as the first frame within 5 seconds, answered by a result frame. The credential never goes in the URL. The credential is checked again before every frame; a revoked credential or a lost scope closes the socket with 1008. Frames are JSON text of at most 1 MiB (the auth frame at most 16 KiB), answered in order. {"id":1,"type":"execute","statements":[{"sql","args","named"}]} runs 1 to 256 statements exactly as sql/execute does: outside a transaction they run as one transaction, all or nothing; inside one they run in it. {"id":2,"type":"begin"}, {"type":"commit"} and {"type":"rollback"} open and end a transaction of at most 5 seconds; after a failed statement the transaction only accepts rollback, and commit rolls it back. Answers echo the id: {"id","type":"result","results":[{"columns","rows","rows_affected","last_insert_rowid"}],"transaction"} or {"id","type":"error","error":{"code","message","statement","sqlstate"},"transaction"} with the same codes and SQLSTATEs as sql/execute and the Postgres wire; transaction tells whether a transaction is still open. A refused auth frame answers an unauthorized or forbidden_scope error and closes with 1008. An SDK needs no knowledge of the database region. A region that does not hold the database authenticates the client before proxying to a region that holds it, which authenticates again. This adds one inter-region round trip (about 170 ms between the current regions) and passes request admission at both regions. A region that holds the database serves supported reads locally; writes follow the SQL router, and a socket that wrote reads its own writes. A writer move closes a pinned session with 1012 and rolls back its open transaction. If the proxy leg drops while a commit is in flight, its outcome is unknown; the proxy never replays it. Binary frames close the socket with 1003, oversized frames with 1009, a restarting server closes it with 1001 and a regional writer handoff with 1012, after which the client reconnects. A client that keeps sending after the 1012 instead of answering it gets no answer to those frames and stays connected until the node stops; close the socket when you read a 1012. While that handoff holds the region's ingress, and on a node that was drained for a handoff (the old writer after the hold, or a follower drained for retirement) until that node stops, an upgrade answers 503 with Retry-After: 1. After a 1012, or a 1001 within the server's 2-second shutdown drain, the server still sends every answer queued before the close and runs no frame that arrives later; after a close for a client fault (1003, 1008, 1009, 1011) a client that does not answer within 2 seconds is disconnected.

Only a received rollback answer or a lost transaction with no committing request sent establishes rollback.

A committing request that may have left the client without a received answer fails with write_outcome_unknown or the existing commit-uncertain error; every later call fails the same way. The session closes without retry or reconnect.

Unless no byte can be proven to have left the client, treat the request as sent.

Losing a read or non-committing statement inside an open transaction retains transaction-lost behavior.
