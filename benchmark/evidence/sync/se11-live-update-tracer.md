# SE-11 end-to-end client live-update tracer — packet record

Status: implementation record for the SE-11 packet (issue #13),
2026-08-27. Authority: the SE wave capstone — the client live-update
tracer across the full stack (ticket #13's scope). Worktree
`terrabasev2-se11`, branch `fleet/se11-2`, based on `develop` @
`24c593c`. Sibling SDK checkouts consumed read-only (never edited,
never pushed): TerraScale.TypeScript @ `cde6918`, TerraScale.DotNet @
`21d21aa`.

## What this packet is

One scripted, deterministic scenario family that runs BOTH embedded
SDK cores — the TypeScript `terrascale.sync.v2` session (the sibling
TerraScale.TypeScript checkout's built `dist`, imported read-only) and
the .NET `TerraScaleSyncV2Client`/`Session` (the sibling
TerraScale.DotNet checkout, project-referenced read-only) — against the
real Rust engine process (a TBEP `SyncDeliveryHost` over UDS, built
from this repository's `crates/terrabase-tbep` into a throwaway cargo
project under the run's temp directory, exactly the SE-08
`EngineHarness` pattern; no repository Rust code is touched) and the
real C# API host (`host/TerraBase.Api`, run as a process over loopback
HTTP with a script-supervised engine socket).

A commit lands through either SDK's mutation surface, the engine
journals it, the backbone fans out the content-free trigger, the
engine's Loro delivery layer serves the byte-budgeted delta, the C#
host forwards it over `terrascale.sync.v2`, and both SDK cores apply
it — no polling anywhere (every delta arrives through the
trigger-driven or snapshot path).

Correctness evidence only — no performance claim. No numbers below are
timings; every byte count is a deterministic wire fact.

## Where the code lives

| Path | Role |
| --- | --- |
| `tracer/ts/tracer.mjs` | The TS-core tracer: one node process embedding the real SDK session, driven by a scripted plan, emitting a uniform JSONL observation log. |
| `tracer/dotnet/TerraScale.Tracer/` | The .NET-core tracer: the same contract over the real TerraScale.DotNet client. |
| `scripts/se11/run.py` | The orchestrator: builds the throwaway engine and the C# host, supervises the topology, drives both tracers and the scripted backend writer, asserts every scenario, and writes one receipt per scenario under `evidence/sync/se11/`. |
| `evidence/sync/se11/*.md` | The per-scenario receipts (regenerated by each run; committed here from the qualifying run). |

The tracer processes speak only to the loopback host URLs the
orchestrator assigns and use backend-context fixtures
(`X-TB-Principal`/`X-TB-Tenant`) — the local-boundary model of
PD-2026-08-26-11: no authentication surface is exercised or claimed.
Payloads stay opaque (the wrapped-codec decision); the tracers record
payload byte identities (SHA-256 digests and lengths), never payload
contents. No secrets, no live systems, no pushes.

## Reproducing from a fresh checkout

Requirements on the reproducing host: the pinned Rust toolchain
(1.97.1) with this repository's offline cargo cache, the workspace
.NET SDK, node >= 24, python3 (stdlib only). The sibling checkouts
must be present at the standard TerraScale workspace layout (or
pointed at with `TERRASCALE_TS_SDK` / `TERRASCALE_DOTNET_SDK`);
the TypeScript checkout needs its `dist` built (it ships built on
develop), and the .NET tracer restores from the local package cache.

```bash
git worktree add .worktrees/terrabasev2-se11 -b fleet/se11-2   # from develop
cd .worktrees/terrabasev2-se11
python3 scripts/se11/run.py            # builds engine + host + tracer, runs all six scenarios
python3 scripts/se11/run.py --scenario s1-golden-path   # one scenario
```

Each run creates a fresh temp run directory (loopback ports assigned
per run, UDS sockets under the run directory) and rewrites the
receipts under `evidence/sync/se11/`. The sibling-repo commit hashes
each receipt names are the exact checkouts the run consumed.

## The scenarios and what each asserts

All six receipts live in `evidence/sync/se11/` with their full check
tables; the summary:

1. **s1-golden-path** — the fresh-session and repeated-change golden
   vectors replayed through the real stack. The vector's journal seeds
   the engine through the real write path; both SDK sessions open
   fresh and adopt the server's snapshot at exactly the vector's
   checkpoint (`{storage_sequence: 3, ends: [[1, 6]]}`) with
   **byte-identical payload bytes** (451 bytes, digest match against
   the vector's recorded hex). The established-docs journal and the 8
   repeated changes are then driven one commit at a time (alternating
   SDK writers), and both cores' observed transition sequences — kind,
   storage sequence, version-vector ends, payload digest — are
   asserted **identical** across 25 transitions. The repeated-change
   budget row is re-derived from observation (1 124 delta bytes for
   the 8 repeated changes vs 2 772 snapshot bytes of the established
   state), every batch fits the 8 192-byte delivery budget, and the
   trigger notification is asserted content-free on the wire.
2. **s2-drop-resume** — the SDKs' connection endpoint (the host
   process) is killed mid-stream; the engine process and its journal
   survive. The TS session climbs its documented reconnect ladder to
   the terminal `failed` state and re-setups from its durable
   checkpoint; the .NET session runs its documented re-setup path.
   Both cores observe every committed update (final checkpoint
   sequence 5), zero duplicate application, and the stale session
   identity is answered truthfully by the fresh host registry.
3. **s3-slow-consumer** — a real stalled consumer (a raw SSE reader
   with a 4 KiB receive window that simply stops reading) under a
   400-commit flood: the host's bounded queue sheds, the shed is
   counted in `/v1/metrics`, the missed range is recovered by the
   documented boundary reconnect, the oversize single-commit row of
   the slow-consumer vector is observed (one over-budget batch,
   `commits == 1` on the .NET surface), and both fast consumers lose
   nothing (401/401 commits, zero duplicates) while the slow one shed.
4. **s4-tbep-link-loss** — the engine process (the TBEP link
   endpoint) is killed with the host supervising it: the open stream
   closes with the resume-able `engine-generation-lost` frame, the
   host restarts a fresh engine generation within its policy, and the
   pre-loss durable checkpoint — ahead of the fresh in-memory
   generation — is answered by the typed refusal on both cores (the
   TS core records `engine_failure: checkpoint end 6 is ahead of the
   server end 0`). Recovery runs through fresh setup and snapshot
   adoption; every commit made to the surviving generation is observed
   by both cores.
5. **s5-region-route-change** — two regions (two engine + host pairs
   on distinct loopback ports, serving instances 1 and 2). Both SDK
   sessions live on region a, the route changes, and each carries its
   durable checkpoint to region b — the region-route-change vector's
   client half (checkpoint continuity; nothing re-delivered behind the
   acknowledged position). All four committed updates are visible
   through region b, and the post-route write applies byte-identical
   payloads on both cores.
6. **s6-multi-region** — the writer's nearest region is a (the TS
   core), the reader's nearest region is b (the .NET core). A write
   through region a becomes visible through region b's own delivery
   path; the replication lag is asserted as a storage-sequence
   distance (region-b lag 1 before the link pump, 0 after — never a
   latency claim); the convergence observation names both regions; the
   mirror direction is demonstrated (a .NET write through b visible
   through a); and the at-least-once identity of mutations is proven
   (a re-submitted key answers the recorded receipt and advances
   nothing).

## Findings recorded for the named owners (not fixed here — outside this packet's write scope)

1. **A cross-repo refusal-body defect blocks the .NET SDK's internal
   recovery paths.** The C# host serializes every plain typed refusal
   with `"resyncRequired": null` (`ErrorDto.ResyncRequired` is
   nullable and not conditionally omitted), and
   `TerraScale.DotNet`'s error parser calls `GetBoolean()` on the
   element (`TerraScaleSyncV2Client.HostFailureAsync`), throwing
   `InvalidOperationException: The requested operation requires an
   element of type 'Boolean', but the target element has type 'Null'.`
   on every non-resync refusal (410 `session-ended`, 500
   `engine-failure`, ...). The .NET session's internal re-open and
   resync paths therefore die on the first plain refusal instead of
   classifying it. The TS core parses the same body null-safely. Both
   owners (SE-08 host DTO, SE-10 client parser) can fix their half;
   the tracer records the defect's exact surface in the s2/s4
   receipts and never works around it by rewriting observed traffic —
   the .NET recovery in these scenarios runs its documented re-setup
   path instead.
2. **The engine's serving core is in-memory only** (SE-14's
   `SyncDeliveryHost`): an engine-generation loss loses the committed
   journal, and a client's durable checkpoint ahead of the fresh
   generation is answered by the typed
   `checkpoint-ahead-of-server` refusal (surfaced as `engine_failure`
   over the host today). s4 records this exactly; durable storage
   wiring is the engine-backed integrator action.

## Honest limits, stated

- The composed vectors in s1 share the `op-00000N` operation-id
  namespace; the tracer namespaces the composed identities
  (`op-est-*`, `op-rep-*`) because a collision is a correct idempotent
  replay (answered with the recorded receipt, no new commit, no
  push) — that behavior is itself demonstrated in s6's retry row.
- The TS core's observation surface carries no per-batch commit count
  (it applies opaque payloads); the cross-core identity diff
  therefore compares kind, storage sequence, version-vector ends, and
  payload byte identity, and the .NET-side commit counts are asserted
  in the budget rows.
- The TS core's SSE reader enforces a 4 096-unit line bound; under the
  s3 flood a large backbone batch event trips it, the stream
  reconnects, and the missed range re-delivers — recorded in the s3
  observations as normal operation of the documented bound.
- The `region_route_change` protocol frame (the vector's advisory
  control frame) has no emission point on the host's HTTP surface
  today; s5 drives the vector's client half exactly (checkpoint
  carried to the new region, acknowledged there, nothing re-delivered
  behind it), and the receipt says so.
