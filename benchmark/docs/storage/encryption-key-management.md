# Encryption-at-rest key management decision record (GAP-S2, ticket #82)

Status: **PROPOSED for parent ratification** — this is the
parent-commissioned, decision-only packet that unblocks the #82
implementation. Nothing here is implemented, nothing here changes the
storage format, and no parity row moves: every decision below is labeled
PROPOSED and stays a proposal until the parent records it. The
implementation packet (exclusive recovery lane, serialized with #43/#45)
owns every format-level consequence and must not start from this record
alone — it starts from the parent's ratification of it.

Owner: GAP-S2 (#82), the parent-owned key-management decision the charter
names as the blocker on #82 ("#82 blocked by the parent-owned
key-management decision", GOAL.md D4 of the 2026-08-26 gap-closure
record) and the packet the ledger commissioned ("the GAP-S2 #82
key-management decision packet (parent-commissioned, decision-only)").

Coordinates: PB-5011 `storage-encryption`
(`parity/contracts/replication-storage.json`, risk `critical`, V2 status
`unresolved`, compatibility text "V2 cryptography, key management, and
rotation policy are unresolved"), GAP-S1 (#81,
`docs/storage/gaps1-storage-compaction.md` — its never-rewrite and

ADR-0005 D-5 (dependency posture), PD-2026-08-26-11 (local backend-only

## Problem

V2 has no encryption-at-rest. One open Engine owns one location holding
six durable artifacts — `wal`, `ledger`, `history`, `retained`,
`roots/<id>.root`, `manifest`, plus the `format` header
(`src/storage/file.rs:89-92`) — and every byte of every one of them is
plaintext on disk. PB-5011 requires that encrypted storage and backup
behavior exist with secret-safe recovery evidence, and its risk record
names the two failure modes that make this a decision-first ticket:
"Encryption changes can cause unrecoverable data loss or secret
disclosure if key failure and recovery behavior are not explicit."

The parent owes five decisions before any code: where the key comes from,
how it rotates, what key granularity the format can actually support,
where in the framing encryption hooks, and whether the cipher comes from
a vetted crate or the engine's std-only posture. This record proposes all
five with evidence.

## What V1 ships (evidence, not obligation)

Recorded honestly from the pin (`fa99b925`, the commit PB-5011 cites).
V1's shape is the reference for what "encrypted storage" meant, not a
requirement to copy it.

**Key source: a local server master key with explicit precedence.**
`SecretProtection.LoadMasterKey` tries, in order: an external executable
(`Security.MasterKey.Exec` + arguments), then a key file
(`Security.MasterKey.Path`), then a default `$HOME/.terrabase/secret.key`
created on first use
([v1:src/TerraBase.Server/ServerWide/SecretProtection.cs::LoadMasterKey],
lines 40-137; config entries at
[v1:src/TerraBase.Server/Config/Categories/SecurityConfiguration.cs],
lines 132-149). The default file is opened with only
user-read/user-write permission bits (`S_IRUSR | S_IWUSR`, lines 66-69),
flock'd, fsync'd with its directory, and regenerated by
`randombytes_buf` only when its size is not a key size — an empty or
wrong-size file is treated as never-valid (lines 111-137). Failure is
fatal with an explicit message: losing this key loses access to all
encrypted information (lines 163-167).

**Key wrapping: the master key is a KEK.** V1 never encrypts data with
the bare master key and never stores a per-database key in plaintext.
`Secrets.Protect` derives a subkey with `crypto_kdf_derive_from_key` and
wraps the secret with `crypto_aead_xchacha20poly1305_ietf_encrypt`
([v1:src/TerraBase.Server/ServerWide/SecretProtection.cs::Protect],
lines 174-213). Per-database secret keys are stored wrapped in the
server store's `SecretKeys` tree
([v1:src/TerraBase.Server/ServerWide/ServerStore.cs::PutSecretKey],
lines 1795-1832); the server store's own key is itself wrapped on disk
as `secret.key.encrypted` and unwrapped at open (lines 663-686, with a
fail-closed `CryptographicException` naming the `rvn offline-operation
put-key` escape hatch). Keys are delivered through an operator-authorized
endpoint that validates exactly 256 bits and `sodium_memzero`es both the
base64 text and the raw buffer
([v1:src/TerraBase.Server/Documents/Handlers/SecretKeyHandler.cs::PutKey];
[v1:src/TerraBase.Server/ServerWide/ServerStore.cs::PutSecretKey],
lines 1722-1745). Overwrite is refused by default because it would lose
access to the encrypted database (lines 1795-1800).

**Data path: per-page and per-transaction AEAD under the database key.**
Each database has one `MasterKey`
([v1:src/TerraBase.Server/Documents/DocumentDatabase.cs::MasterKey],
line 357; `IsEncrypted` at line 611; an encrypted database without a key
fails at [v1:src/TerraBase.Server/Documents/DocumentDatabase.cs::EnsureValidSecretKey],
lines 244-260; the key is zeroed on dispose, lines 1227-1237), and index
storage is encrypted with the same key
([v1:src/TerraBase.Server/Documents/Indexes/Index.cs], line 762). The
pager wraps the inner pager with `CryptoPager` when a key is present
([v1:src/TerraBase.Voron/StorageEnvironmentOptions.cs], lines 880 and
1148; `StorageEncryptionOptions` at lines 1384-1404).
`CryptoPager.EncryptPage` derives a per-page subkey from the master key
with `crypto_kdf_derive_from_key` keyed by the page number under context
`"TerraBase!"`, generates a random nonce, and writes a detached
XChaCha20-Poly1305 tag into the page header
([v1:src/TerraBase.Voron/Impl/Paging/CryptoPager.cs::EncryptPage],
lines 495-540; context at line 105). The journal does the same per
transaction, with subkey id = transaction id under context `"Txn-Acid"`
([v1:src/TerraBase.Voron/Impl/Journal/WriteAheadJournal.cs::EncryptTransaction],
lines 2005-2040; context at line 2003).

**Integrity: the AEAD tag subsumes the checksum.** This is the most

## D1 — Key source (PROPOSED)

Four alternatives were evaluated. The recommendation is the first.

**A. Engine-process-local key file, 0600, path from engine config —
RECOMMENDED (PROPOSED).** The engine process reads its key-encryption key
(KEK) from a file it opens at startup: path supplied through engine
startup configuration (the same channel that supplies the location
today — `EngineConfig::durable` builds from a caller-supplied path,
`src/engine/mod.rs:227`; the supervised engine process already receives
its socket path as a process argument, the SE-08 harness at
`cli/TerraBase.Cli.Tests/EngineHarness.cs`), default
0600 creation on first use with fsync of file and directory, and
fail-closed open when the file exists but cannot be parsed. This is
V1's `MasterKeyPath` + default-`secret.key` shape
([v1:src/TerraBase.Server/ServerWide/SecretProtection.cs::LoadMasterKey])
with the exec variant dropped (below). Under PD-2026-08-26-11 D1 the
engine/host surface is strictly local, binds loopback/UDS, and has no
authentication surface — so the only trust boundary the engine can
actually own is its process identity plus filesystem permission bits. A
0600 file is exactly that boundary, needs no new wire surface, no
Platform availability, and survives engine restarts under the same
supervisor.

**B. Environment-supplied key material — rejected.** The process
environment is a broader disclosure surface than a 0600 file: it is
readable through `/proc/<pid>/environ` by anything running as the same
user, inherited by every child process, and routinely captured into
crash dumps, incident reports, and service-manager unit files. V2 also
has no environment secret channel today — the only key V2 handles
arrives through a typed operation field, not the environment
(`EncryptionKey::from_material`, `src/backup/schedule/codec.rs:395`).
Nothing in the local backend-only surface needs it.

**C. Platform/backend-supplied per-tenant DEKs wrapped by a local KEK —
the designated successor, not the first step.** This is V1's actual
architecture transplanted (local master key wraps per-database secret
keys, `ServerStore.PutSecretKey` above), and PD-2026-08-26-11 D1 makes
it architecturally natural later — "the backend supplies tenant context
and the engine enforces isolation." But no key-supplying operation
exists in TBEP today, no Platform key service exists in this deployment,
and delivering key material over the unauthenticated local UDS channel
buys nothing over the engine reading its own 0600 file: the same local
principal can read both. **PROPOSED:** design for it without building
it — D2's envelope means the KEK never encrypts data, so a future
Platform DEK channel drops in beside the key file without a format
change. The parent should treat this alternative as the recorded
successor, triggered when a Platform key service is actually specified.

**D. External KMS — unavailable in this deployment (fact of the
environment, recorded).** No KMS exists in this deployment. There is no
key-management service, no HSM, and no secrets manager reachable from
the engine; the networked-engine QUIC binding is itself deferred "until
a networked-engine need is recorded" (PD-2026-08-26-11 D1). Any KMS
integration would be Platform-side (external authentication policy is a
Platform concern per the same record), not engine-side. Recorded as an
environment fact so the parent does not re-derive it.

**Also PROPOSED as part of D1:** the KEK never encrypts stored data —
it only wraps epoch data keys (D2). `Security.MasterKey.Exec` (an
external key-providing executable) is deliberately **not** proposed: it
adds a process-execution surface at engine startup with no consumer in
this deployment. The parent may add it later as a config variant; it
does not interact with any other decision here.

## D2 — Rotation: epoch-key envelope encryption (PROPOSED)

**PROPOSED: epoch-key envelope encryption.** A new epoch key wraps data
keys; old epochs stay readable forever; re-encryption is an optional,
explicit, later operation — never required for correctness, never
required for readability.

- **Epoch identity** is a monotonically increasing integer recorded in
  the framing and in the manifest (identifier only — D3). Every frame
  carries the epoch identifier of the data key that sealed it.
- **Old epoch keys are retained** as long as any artifact cites their
  epoch. Deleting an epoch key is a deliberate, recorded, irreversible
  act equivalent to deleting the data it sealed — mirrored from V1's
  stance that losing the key loses the data
  ([v1:src/TerraBase.Server/ServerWide/SecretProtection.cs], lines
  163-167) and its overwrite refusal
  ([v1:src/TerraBase.Server/ServerWide/ServerStore.cs], lines
  1795-1800).
- **Rotation cadence is caller-driven.** The engine runs no timers (the
  standing PD-2026-08-26-11 D2 / GAP-S1 in-band pattern): a caller asks
  for a new epoch at a storage-sequence boundary, the engine wraps a
  fresh data key under the KEK, records the epoch, and writes
  subsequent frames under it.

**In-place re-encrypt — rejected, with evidence.** Rewriting every
artifact under a new key contradicts the shape V2 storage actually has:

1. Roots are immutable and never rewritten. Every `Written`/`Synced`
   commit writes a full-table root file; superseded roots are never
   removed, and GAP-S1's D2 defines what a maintenance pass may rewrite
   and what it never touches (`docs/storage/gaps1-storage-compaction.md`).
   Re-encryption would have to rewrite every root file that ever
   existed, or admit a mixed-key location anyway — at which point the
   epoch machinery already exists and in-place adds nothing.
2. The operation ledger is a never-rewrite artifact by decision
   (GAP-S1 D6: it is the replay-identity anchor and compaction never
   rewrites it). An in-place re-encrypt either rewrites it — violating
   that decision — or leaves it under the old key forever, which is the
   epoch model wearing a different name.
3. A whole-location rewrite runs under the storage lock with a window in
   which recovery needs both keys, and a crash mid-rewrite needs a
   second recovery path. GAP-S1's kill-point discipline exists precisely
   to avoid a second recovery path.
4. There is no parity pull: V1 ships no rotation at all (evidence
   above). In-place re-encrypt would be new complexity with no V1
   behavior to match.

**Optional background re-encryption** (rewriting old epochs under the
current epoch key to retire old keys) is **deferred** to a future
GAP-S1-style in-band pass with its own crash-safety record — owner: the
parent, assigned when a retention or compliance requirement names a key
age. Nothing in this record depends on it.

## D3 — Locality, granularity, and secret safety (PROPOSED)

**Key material never enters the repository, artifacts, receipts, logs,
or parity data (PROPOSED, and already the standing rule for the one key
V2 handles).** BK-04's record is the in-repo precedent to extend: key
material is caller-supplied per operation, never stored, zeroed on drop,
redacted in Debug, and never enters artifact bytes or status
(`src/backup/schedule/codec.rs:383-435`, the `# Secrets` section of
`src/backup/schedule/mod.rs:33-42`). V1's audit serialization omits the
key while the operational one carries it
([v1:src/TerraBase.Client/Documents/Operations/Backups/BackupEncryptionSettings.cs::ToAuditJson])
and V1 zeroes key buffers on every path that touches them. For the
storage-at-rest keys this packet PROPOSES the same four rules plus two
more:

- **The storage manifest records key EPOCH IDENTIFIERS only — never key
  material, never wrapped keys, never the key file's path.** The
  manifest today records `(sequence, root id)`
  (`src/storage/root.rs:322-368`) and GAP-S1 D7 permits rebuilding it by
  scanning; anything key-shaped must not live in a file recovery may
  regenerate.
- **Wrapped data keys live in their own append-only key-record file
  beside the manifest** (name owned by the implementation packet), each
  entry an epoch identifier plus the data key wrapped under the KEK —
  exactly V1's separation of `secret.key.encrypted` and the `SecretKeys`
  tree from the data files. That file joins GAP-S1 D2's never-rewrite,
  never-delete list, and the loss-of-last-copy rule mirrors V1's
  fail-closed open.
- **Key-record durability ordering (added by the integrator from the
  gate findings; binding on the implementation packet):** a wrapped
  epoch key must be DURABLE in the key-record file (entry appended AND
  fsynced, with the file's directory synced on first creation) BEFORE
  any frame citing that epoch is durable. A crash between the two leaves
  frames whose key is permanently absent — a fail-closed open
  indistinguishable from data loss, which is exactly the availability
  hazard the ordering rule exists to make unrepresentable. The
  key-record file also carries its own torn-tail rule: a torn trailing
  entry (crash mid-append) truncates to the last verified entry at open
  — the WAL's fail-closed stance does NOT apply here, because a torn
  key-record tail endangers only the not-yet-referenced epoch key it was
  appending, never an already-published frame; a mid-file damaged entry
  still fails closed.

**Per-database versus per-tenant granularity — PROPOSED: one data key
per location per epoch; per-tenant keys are deferred.** Evidence for why
the format cannot honestly offer per-tenant keys today:

- One open Engine owns one location and one database
  (`EngineConfig::durable(location)`, `src/engine/mod.rs:227`;
  `FileStorage::open(&location)` at line 554). Tenants live inside that
  location as a component of the storage key, not as separate files.
- The durable artifacts are not tenant-partitioned. A root table is one
  `BTreeMap<StorageKey, Document>` spanning every tenant in the
  location (`src/storage/root.rs:57-61`); the storage key orders by
  tenant, then collection, then identifier inside that shared map
  (`src/storage/codec.rs:117-134`); WAL frames, ledger records, history
  records, and retained facts are all location-wide framed streams.
  Per-tenant key granularity would require per-tenant framing
  boundaries the format does not have — a format redesign, not a key
  count.
- **Interaction with tenant isolation (stated honestly):** isolation is
  enforced by the engine's typed key space and authorization
  (PD-2026-08-26-11 D1: "the backend supplies tenant context and the
  engine enforces isolation"), not by ciphertext domains, so one
  location-wide data key does not weaken isolation. What it does mean:
  a single disclosed location data key exposes every tenant's ciphertext
  in that location at once. The mitigation is alternative C — a Platform
  channel supplying per-tenant DEKs wrapped by the local KEK — which
  D2's envelope accommodates without a format change (the framing's key
  identifier widens from "epoch" to "epoch + optional tenant domain").
  **Deferred** until a Platform key service is specified; owner: the
  parent, with the Platform team.

**Key domains stay separated (PROPOSED).** Storage-at-rest epoch keys,
backup bundle keys (BK-04), and any future replication-channel keys are
distinct domains with distinct derivation labels. The backup key never
decrypts the location and vice versa; the location key never travels
with a backup bundle. Wrapping a backup bundle's per-operation key under
the storage KEK is a separate later decision, not assumed here.

## D4 — Where encryption hooks the storage format (PROPOSED; the format
decision is the implementation packet's)

Every framing boundary in the location, with what an encrypted epoch
would change. All spellings below are PROPOSED anchors for the
implementation packet, not decisions.

| Artifact | Framing today | Encryption hook (PROPOSED) |
| --- | --- | --- |
| `wal` | `[type u8][len u32][FNV-1a u64][payload]`, 13-byte header (`src/storage/wal.rs:17-28`, append at 122-145) | Per-frame AEAD under the frame's epoch: epoch id + nonce + tag in the header, ciphertext payload; the FNV-1a checksum is dropped for encrypted frames (see below) |
| `ledger` | `[len u32][FNV-1a u64][payload]`, 12-byte header (`src/storage/ledger.rs:18-27`, append at 157-190) | Same treatment; the ledger is never rewritten (GAP-S1 D6), so old records keep their epoch |
| `history` | Publication-history records (`src/storage/ledger.rs:393-396` and following) | Same treatment as the ledger |
| `retained` | `[len u32][FNV-1a u64][payload]` fact/bound records (`src/storage/retained.rs:120-178`) | Same treatment; retained facts must remain verifiable by the GAP-R02/GAP-S1 consumers after decryption |
| `roots/*.root` | `ROOT_MAGIC` + FNV-1a over the body (`src/storage/root.rs:19`, 278, 300-320) | Body AEAD-sealed under the root's epoch; magic and identity stay cleartext |
| `manifest` | `MANIFEST_MAGIC` + FNV-1a + `(sequence, root id)` (`src/storage/root.rs:22`, 322-368) | **Not sealed.** Adds the current epoch identifier (D3: identifier only) |
| `format` | `TBV2FORMAT` + u64 version 1 (`src/storage/file.rs:37-40`, 756-780) | The gate: an encrypted location bumps the format version; `FormatMismatch` on open is the existing refusal |

Three interactions the implementation packet must decide, PROPOSED here
as directions only:

1. **AEAD tags subsume the FNV-1a checksum per epoch.** V1's precedent is
   explicit: with encryption on, the transaction hash is zeroed and the
   AEAD tag is the integrity check
   ([v1:src/TerraBase.Voron/Impl/Journal/WriteAheadJournal.cs], lines
   1949-1977 and 259). The FNV-1a checksum decision itself is recorded
   and unchanged for unencrypted frames: it "detects corruption; it is
   not a cryptographic digest and never crosses a public seam"
   (`docs/storage/w3-storage-engine.md:47-50`, collision limit at
   247-253). An encrypted frame's tag replaces its checksum — never
   both, matching V1's "no need to do it twice."
2. **Torn-tail classification must survive.** Recovery distinguishes a
   torn trailing frame (truncate and open) from mid-file corruption
   (refuse to open) by checksum failure position
   (`src/storage/wal.rs:191-235`). With AEAD, a tag failure at the
   trailing position must still mean torn tail and anything else must
   still fail closed as `WalCorruption::MidFileCorruption`. Decryption
   failure and structural damage must not become distinguishable error
   channels beyond that (BK-04's fail-closed single-failure shape is the
   in-house pattern).
3. **Root identity stays plaintext-derived.** `StorageRootId` is
   `sequence` + the FNV-1a of the plaintext body in hex
   (`src/storage/root.rs:262` and 317), it is the file name, and the
   manifest and GAP-S1's root-scan fallback match on it. Sealing the
   body must not change the identity derivation, or the recovery
   fallback breaks. Consequence, disclosed: the identity remains a
   plaintext-correlation artifact — already a recorded non-claim for
   collision resistance (`docs/storage/w3-storage-engine.md:247-253`),
   and unchanged by this packet.

**Recovery interaction (PROPOSED, flagged for the parent).** GAP-S1 D7's
fallback scans for the newest *verifying* root when the manifest is
damaged. Under encryption, verification requires the epoch key. This
record PROPOSES that open fails closed when the key file or a needed
epoch key is missing — the V1 behavior
([v1:src/TerraBase.Server/ServerWide/ServerStore.cs], lines 663-686) —
and that no unencrypted "recovery mode" exists. Whether operators need a
metadata-only open without keys is open question Q3.

## D5 — Dependency audit: vetted crate versus std-only posture (PROPOSED,
conditional)

The engine crate has **zero dependencies** today: the root `Cargo.toml`
declares no `[dependencies]` at all, ADR-0005 D-5 records that "the
engine's storage, WAL, engine, replication, and streaming modules remain
zero-dependency," and BK-04's record states the workspace "forbids
external dependencies" as the reason its cipher is an in-crate
composition that "claims nothing about vetted-cipher strength"
(`docs/backup/schedule.md:44-60`). Any crate added for storage
encryption lands directly in that zone. This packet cannot and does not
amend an ADR — so both options are recorded and the parent picks.

**Option 1 (RECOMMENDED, PROPOSED, conditional on a parent-ratified
ADR-0005 D-5 amendment): `chacha20poly1305` 0.11.0 (XChaCha20-Poly1305).**

- **V1 algorithm parity:** V1's data path is
  `crypto_aead_xchacha20poly1305_ietf_*` for pages, transactions, and
  key wrapping (citations in the V1 section). XChaCha20-Poly1305 with a
  192-bit nonce is the exact family, and the crate ships it
  (`chacha20poly1305::XChaCha20Poly1305`, registry source at
  `chacha20poly1305-0.11.0/src/lib.rs` line 14).
- **License and closure audit (receipts below):** adding
  `chacha20poly1305` 0.11.0 and `aes-gcm` 0.11.1 to a scratch crate and
  resolving the full closure yields 25 packages. Every one is
  `MIT OR Apache-2.0` / `Apache-2.0 OR MIT` **except** `r-efi` 6.0.0
  (`MIT OR Apache-2.0 OR LGPL-2.1-or-later`): the LGPL option is not on
  the `deny.toml` allowlist. `r-efi` is already in the workspace lock
  (pulled by `getrandom` 0.3.4 and 0.4.3) and was already named in the
  SE-02 closure audit as "permissive at choice"
  (`docs/spike/se02-base-engine-spike.md:56`) — so the disposition is a
  recorded exception the parent must ratify, not a new license.
- **Bans discipline (`deny.toml [bans] multiple-versions = "deny"`):**
  the closure needs `chacha20` 0.10.2 and `cpufeatures` 0.3.1; the
  workspace lock already pins `chacha20` 0.10.1 (via `rand` 0.10.2) and
  `cpufeatures` 0.3.0. Both are version conflicts the integrator must
  resolve in lockstep — a `Cargo.toml`/`Cargo.lock` action (protected
  files; see collision actions).
- **Net-new to the workspace:** 17 crates (`aead`, `aes`, `aes-gcm`,
  `block-buffer`, `chacha20poly1305`, `cipher`, `cmov`, `cpubits`,
  `crypto-common`, `ctr`, `ctutils`, `ghash`, `hybrid-array`, `inout`,
  `poly1305`, `polyval`, `universal-hash`). All RustCrypto-family except
  the `libc`/`cfg-if`/`getrandom`/`typenum` shared plumbing already in
  the lock. The constant-time tooling in the closure (`cmov`, `ctutils`,
  `cpubits`) comes from the same RustCrypto/utils repository as
  `zeroize`, which the workspace already locks at 1.9.0 — so enabling
  the crates' optional `zeroize` feature adds no new version.
- **Maintenance (crates.io registry, receipts below):** both crates live
  in the RustCrypto/AEADs repository; `chacha20poly1305` created
  2016-10-06, latest 0.11.0, updated 2026-08-05, ~77M downloads;
  `aes-gcm` created 2019-08-16, latest 0.11.1, updated 2026-08-21, ~144M
  downloads; the shared `aead` trait crate updated 2026-06-17.
- **Why conditionality is honest:** adding the engine's first runtime
  dependency reverses a recorded posture, makes the engine build depend
  on the registry cache or vendoring (the C# engine harness currently
  builds `--offline`), and touches protected files. That bundle belongs
  to the parent, not this packet.

**Option 2 (fallback, PROPOSED only if the parent upholds zero-deps):
extend the in-crate composition.** Generalize BK-04's
HKDF-SHA256/HMAC-SHA256/counter-mode encrypt-then-MAC construction
(algorithm id `hkdf-sha256-hmac/sha256-ctr-v1`,
`src/backup/schedule/codec.rs:61`, key handling at 383-435) into the
storage framing with per-epoch domain separation and a nonce-uniqueness
discipline. Zero new dependencies and no protected-file edits — but it
is a non-standard composition with no third-party review, it is **not**
V1's algorithm, and it inherits BK-04's recorded non-claim verbatim: no
vetted-cipher-strength claim. For backup bundles that non-claim is a
bounded risk; for the entire database at rest it is the thing PB-5011's
`critical` risk row is about. That asymmetry is why Option 1 is the
recommendation.

`aes-gcm` 0.11.1 (AES-256-GCM) was audited alongside and is a viable
substitute if the parent prefers hardware-accelerated AES; it is not
V1's algorithm family, so it is recorded as an alternative, not the
recommendation. Its closure is the same 25-package set above.
