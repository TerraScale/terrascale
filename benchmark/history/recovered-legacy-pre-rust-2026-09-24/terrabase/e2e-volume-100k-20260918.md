# End-to-end volume qualification — 100k documents (2026-09-18)

One process, one host, durable `StorageEngine` (WAL with synchronous flush per
committed batch). 100,000 documents (~430 B bodies) written in committed
batches of 1,000, verified by exact read-back (body deep-equality plus
version), captured by one full backup plus one incremental backup (8
publications), restored twice (full boundary and interior PITR cut), and
verified again document-by-document on reopened engines. All four
verifications reported 100,000/100,000 exact matches.

Run with:

```text
nice -n 19 dotnet bench/TerraBase.Benchmarks/bin/Release/net10.0/TerraBase.Benchmarks.dll \
  --workload e2e-volume --documents 100000 --batch-size 1000 --updates 8 \
  --seed 1337 --output bench/receipts/<run>
```

Receipts: `bench/receipts/e2e-volume-100k-20260918/` (final numbers below).

## Fixes required to complete the run

The 100k qualification initially failed; each failure was a real defect,
fixed at the root:

1. **Native backup qualification was broken on current main.** Backup capture
   requires an explicit durable replication journal identity
   (`InitializeJournalIdentityAsync`), added 2026-09-17; both benchmark
   workloads now initialize it on the source engine. Before the fix,
   `CreateFullBackupAsync` threw
   `DurableReplicationJournalMigrationRequiredException` for every fresh
   engine.
2. **Interior PITR restores were impossible** (regression from 2026-09-17):
   `StorageEngineRestoreTarget.MaterializeGenerationUnsafe` requires a
   complete authority at the restore plan's final boundary, but the backup
   source attached an authority only to the terminal log entry. The source now
   emits one delta authority per publication entry, so any interior cut still
   materializes the physical authority chain and the true commit frontier
   (`StorageEngineBackupSource.CapturePublicationAuthoritiesAsync`).
3. **A fresh source instance could not take an incremental backup.** The
   commit-to-physical cursor fallback treated the commit sequence as a
   physical journal cursor, which diverges once journal identity or receipt
   rows exist. The source now resolves the base cut from the replay index
   (`ResolveBasePhysicalCut`).
4. **`RestoreToTimeAsync` threw after a successful interior PITR restore.**
   The release-intent validation compared the chain-tip boundary against the
   plan's final boundary; the restore result now reports the boundary it
   actually restored (`BackupManager.ExecuteRestoreAsync`).

## Efficiency changes

- `FileSystemBackupObjectStore.PutCoreAsync` returns metadata from the digest
  computed during the streamed upload instead of re-reading and re-hashing the
  object it just wrote.
- `StorageEngineRestoreTarget.CommitAsync` validates the materialized frontier
  once per commit (the previous path re-serialized the snapshot artifact and
  replayed the WAL three times, all under one path gate where no state can
  change between checks).
- `StorageEngine.ScanSnapshotAsync` binary-searches a per-snapshot sorted
  identifier index instead of re-filtering and re-sorting the entire document
  state on every 256-document page (the backup snapshot read was
  O(pages × documents) with a full sort per page).
- Restore materialization batches 4,096 records per atomic WAL frame instead
  of 512, cutting per-frame fsyncs by 8× with the same fault semantics.

## Limits

- Single process, single host, local filesystem object store: no S3/OCI
  network transfer, multi-region recovery, or provider latency is qualified.
- Timings are from one run each on a shared-tenancy VM host; treat the deltas
  as directional, not a controlled benchmark.
- The PITR cut applies one of eight incremental publications; deeper chains
  were exercised by `native-restore` qualification (8 entries, five samples).
