Today `Storage::commit_batch` takes one `Mutex<Inner>` guard and calls `Inner::commit`. It encodes a complete frame in `prepare_commit`, checks retry dedup, may checkpoint, checks read/write conflicts, reserves mutable-version and dedup bytes/items, checks SSD headroom, then appends and syncs the WAL before publishing `visible`. It cannot expose a fully admitted final receiver batch before the separate inbox marker sync. The journal itself writes up to 512-KiB chunks followed by a synced marker, with `needs_recovery` on uncertain failure. A receiver that syncs the marker first and only then calls ordinary `commit_batch` can encounter an otherwise avoidable conflict, quota failure or mutable-allocation refusal after inbox durability. Conversely, applying first would lose the replay source after a crash.

`Inner::commit` now rechecks clock and durable expiry floor after preparatory checkpoints and immediately before WAL append; `retained_lookup_contract::checkpoint_during_commit_rejects_token_expired_after_initial_check` covers the previous bug. The post-sync `decode_wal_frame(...)?` remains a direct error return at the observed source identity. Treat **every** post-sync error, including future decoder errors, as `Poisoned`/reopen work. `canonical_digest` hashes the frame with its shard-local commit-sequence bytes zeroed, allowing an unchanged retry to return its original receipt; changing operations conflicts. The retained-frame lookup is separate and must still supply exact original WAL bytes to a document retry.

## Proposed public boundary and ownership

```rust
pub enum PreparedBatchOutcome<'s> {
    Ready(PreparedBatch<'s>),
    AlreadyCommitted(CommitReceipt),
}

impl Storage {
    pub fn prepare_batch<'s>(
        &'s self,
        snapshot: ReadSnapshot,
        transaction_id: TransactionId,
        mutations: &[Mutation],
    ) -> Result<PreparedBatchOutcome<'s>, StorageError>;
}

impl PreparedBatch<'_> {
    pub fn commit(self) -> Result<CommitReceipt, StorageError>;
    pub fn encoded_len(&self) -> usize;
}
```

`PreparedBatch<'s>` owns the `MutexGuard<'s, Inner>`, the **owned, exact encoded frame** and canonical digest, the original transaction ID and next commit sequence, estimated mutable/directory sizes, checked WAL position/headroom, and every reservation needed to finish: frame and operation-view bytes, mutable-version bytes and item slots, dedup bytes and item slot, plus any fallibly prepared insertion capacity. The `mutations` slice is borrowed only during `prepare_batch`; changing or dropping the caller's slice afterward cannot change the frame. `PreparedBatch` has no clone or public constructor and is deliberately not transferable across an `await`. The receiver constructs, uses and drops it inside one bounded blocking closure; a `std::sync::MutexGuard` need not be `Send` because it never leaves that closure. The outcome's lifetime ties `Ready` to the borrowed `Storage`, without requiring a borrowed mutation lifetime.

`prepare_batch` holds the storage guard from its first state inspection until returning either an owned `Ready`, an unlocked `AlreadyCommitted`, or an error. Keep the current decision order: validate snapshot, token window and exact WAL format/size; calculate the canonical digest with the sequence normalized; return the original receipt on a live matching dedup entry and `IdempotencyConflict` on a different batch; then perform any needed checkpoint, latest-key conflict check, permit/item/capacity work and final disk/headroom check. Recheck deadline and durable floor after any checkpoint. A previously committed same-ID batch must not acquire a new sequence or be rejected solely by a later key conflict; an expired/pruned token is still governed by the existing floor/clock contract. A preparatory checkpoint may durably publish **older** state and advance the expiry floor, but `Ready` creation or `Drop` never appends this target frame or advances its visible sequence.

For `Ready`, all deterministic capacity, duplicate-key, conflict, max-operations, 1-MiB-value, 2-MiB-complete-frame, mutable/index and disk-quota checks occur before the caller may sync an inbox marker. Continue to use the sole `tb-format` WAL encoder and decode/validate the exact frame before the marker boundary. Reserve byte and **item** charges for the full guard lifetime; prefer fallible preallocation of post-sync structures. The observed `prepare_commit` reserves frame bytes plus an operation-view estimate, and `reserve_commit_permits` reserves mutable and dedup bytes/items; preserve those charges. Because a 2-MiB frame can still require later allocation for keys/values and tree nodes, either prepare owned updates before sync or prove all post-sync allocation failures force recovery rather than an unpoisoned return. `AlreadyCommitted` is a raw retry result, never evidence of an applied D5 identity.

`PreparedBatch::commit(self)` alone may append the final frame. With its guard still held, recheck transaction expiry against **both** the clock and durable expiry floor immediately before append, after the inbox call has returned. An in-process checkpoint cannot advance the floor while `Ready` owns `MutexGuard<Inner>`; a legal preparatory checkpoint may already have advanced it, and the clock can advance while the guard waits through inbox sync. Preserve the immediate recheck as a local invariant and defense against future changes to the guard boundary. Confirm the WAL position/length still matches the prepared head; a mismatch is corruption and no ACK. Then write and sync the complete encoded frame, apply its exact operations, install the dedup entry and advance `visible`. Before the first write, errors release the guard and permits with no target append. From the first potentially partial WAL write through sync and post-sync in-memory apply, an I/O or validation failure poisons the shard; no subsequent writer is served until reopen scans the WAL and reconciles the result. The crash hook after WAL sync/before apply remains meaningful. Dropping a `Ready` without `commit` releases reservations and the guard and **does not append**; `Drop` must not perform I/O or publish a target batch.

`Storage::commit_batch` should delegate to this same prepare/consume path, returning `AlreadyCommitted` directly, so raw-key callers and receiver use one set of retry, expiry and WAL rules. Do not infer network or replicated applied progress from the raw `CommitReceipt.frontiers`: it reports this local shard's stages, while the receiver's AppliedAck must be derived from recovered D5 identity. `Storage` remains a generic raw engine and does not know D0, D1, D5, membership, schemas or the inbox.

## Journal handoff, lock order and cancellation

The document owner first stages/reuses D6, computes the final exact D1+D0+D5 mutations and takes a **post-stage** snapshot under its exclusive shard writer gate. The receiver prepares that frozen raw batch. Only on `Ready` may it call the already certified `ReplicaReceiver::append_certified` (or its scoped journal seam) to sync the exact inbox marker. On a journal error, drop `Ready`: no target final frame has been appended; an uncertain marker is reconciled on journal reopen. On marker success, consume `Ready`; return AppliedAck only after the committed D5 can be established. If `AlreadyCommitted` occurs, compare the document-shard D5 against the offered EventId/digest/epoch/configuration before any applied claim; raw transaction-ID equality is insufficient. On an expiry after marker sync, leave a durable-but-unapplied inbox group and replay with a fresh receiver-local raw token after reopening or retry, never reuse the sender's D3 token as authority.

Enforce one process-wide acquisition order: **document writer gate → document `Storage::Inner` → per-origin journal owner → journal `Storage::Inner`**. No journal recovery, duplicate path, catalog path, request handler or maintenance task may acquire the document gate while holding a journal lock. A recovery path can read an owned bounded journal group and release the journal lock before taking the document gate, or take locks in the stated order. The existing `ReplicaReceiver::append_certified(&mut self)` must be called only after target preparation in the blocking closure; a runtime mutex around that receiver must not be taken first. Avoid an `await` while any of these locks or permits are held. Bounded group size, a bounded blocking pool and pressure metrics are required because marker fsync may hold the document writer for a material interval.

Cancellation before the blocking closure starts commits nothing. Once it starts, cancellation of the network future must not discard or interrupt the owned blocking operation; it resolves marker/target sync or records a recoverable uncertainty, and a disconnected client gets no unproved ACK. A crash after marker sync but before target WAL sync leaves D5 absent and the exact journal group replayable; a crash after target WAL sync recovers D1/D0/D5 atomically. On startup, replay all marked, unapplied groups before serving local or remote document writers. Journal durability alone never advances applied prefix. Stage disk reservations and immutable D6 orphans are a document-layer prerequisite; this raw API reserves only its **one final batch**, not all prior D6 stage groups or the separate inbox's physical free space.

The storage seam is not complete merely because a unit test compiles; its real applied caller is a later gate.

The one architecture choice is how to prevent target-state drift while the separate inbox fsyncs. **Use the held raw guard for the first applied slice.** Releasing the lock would require a separately durable reservation/version-CAS and renewed capacity proof after marker sync; none exists in this source. The guard trades throughput and possible lock wait for a small, reviewable correctness boundary. A future measured implementation may replace it without changing D5 or the crash contract. Physical ENOSPC can still occur after preflight on a shared device; poison/reopen and withhold AppliedAck, leaving the marked group for replay. This is a capacity and availability limit, not permission to acknowledge an unapplied event.
