## Product boundary and decisions

TerraBase owns its Rust storage and replication algorithms. The optimized workload is primary-key access, selective indexes, short ordered scans, and small atomic mutations over versioned documents. SSD supplies the synced WAL, mutable pages, scratch, and a bounded verified cache. S3-compatible storage holds immutable segments, log chunks, manifests, snapshots, and retained history and is on the normal read and recovery path. RAM never holds a full decoded database or index mirror. HDD is an optional future placement target, not a current dependency. These are direct requirements of GOAL §§1, 3–4, 6.

The initial physical baseline is a single-writer-per-shard, append-only SSD WAL, a byte-budgeted encoded mutable table, and checksummed immutable sorted segments with block indexes and sparse lookup metadata. A shard owner serializes publication of a transaction batch, checks conflicts, writes its complete batch and commit marker, syncs the WAL for local durability, and then exposes the new commit sequence to readers. This is a **starting implementation hypothesis**, not a measured claim that a ZoneTree-inspired layout wins. Bf-Tree-inspired mini-pages, selective caching, and buffered updates are a second required candidate. Both and a combined layout must be researched at pinned upstream revisions and compared with durability enabled, including all maintenance, memory, and remote costs (GOAL §§6, 10). Physical alternatives implement the same visibility and recovery contract; a copied cache is never another authoritative version.

Local transactions use a stable read snapshot and commit-time validation of the read/write set. Atomicity and constraint/index/change-record updates cover one shard in the first executable increment. A complete supported product must declare exactly which cross-key, cross-shard, and cross-region operations are atomic. Strong global uniqueness and serializable multi-shard commits require an explicit coordinated metadata/transaction protocol; leaderless quorum counts do not establish them. Until implemented, the API must reject such requests instead of silently weakening them (GOAL §§6–7). Snapshot isolation is the proposed first local isolation level; serializable behavior is a separate qualification choice and cannot be advertised on this basis.

Leaderless writes are only for explicitly declared convergent types and conflict policies. Their durable event identity is independent of a document's 16-byte ULID, transaction sequence, and wall clock. Merge operations must be associative, commutative, and idempotent; causality, deduplication, tombstones, and retire/rebootstrap rules are persisted. A logical version may enter the transaction engine via a convergent merge, but that does not turn eventual or causal convergence into SQLite-equivalent ACID semantics (GOAL §§7–8).

## Proposed workspace and dependency direction

Names are design-level boundaries. The coordinator may use smaller modules initially, but should preserve these ownership and dependency rules.

| Crate | Responsibility and public boundary | Depends on |
| --- | --- | --- |
| `tb-core` | Validated fixed-width IDs, shard/epoch/commit/cursor types, `AckProfile`, typed errors, memory/disk admission permits, limits, clock/fault hooks | Standard library and small audited primitives |
| `tb-format` | Explicit-endian, versioned, length-checked and checksummed WAL, segment, manifest, snapshot, document, and LZ4 batch envelopes; compatibility readers | `tb-core` |
| `tb-storage` | Owned shard state, local WAL and sync, conflict validation, MVCC, ordered segment read/merge, checkpoint and reclaim; no S3 or gRPC concrete client | `tb-core`, `tb-format` |
| `tb-object` | Narrow immutable object API, `object_store` adapter, manifest publisher, verified range reader, cache, archive and GC | `tb-core`, `tb-format` |
| `tb-replication` | Convergent merge, durable outbox/inbox and cursors, repair, membership epochs, placement and bootstrap state machines; its private inbox uses a dedicated `tb-storage` instance | `tb-core`, `tb-format`, `tb-storage` |
| `tb-protocol` | Checked-in versioned `.proto` contracts, tonic/prost generated bindings, mTLS, bounded gRPC streams and negotiated LZ4 application batch envelope | `tb-core`, `tb-format`, `tb-replication` |
| `tb-server` | Configuration, profile enforcement, scheduling and budgets, orchestration of engine/object/replication, readiness and Prometheus-compatible metrics | Above crates |
| `tb-api` | Typed document/query/mutation and subscription contracts, authorization, generated schema interfaces | Engine-facing contracts, not private physical layout |

Avoid making `tb-storage` and `tb-object` depend on each other. Put `ImmutableObjectStore` and `ManifestPublisher` traits in an engine-facing contract module (`tb-core` or a small `tb-storage-api` if core would become bloated); the server wires concrete implementations. Keep the write path's data structures concrete. `tb-server` is the first real caller of storage, object, and protocol adapters. Versioned `.proto` source belongs in this repository; benchmark datasets, drivers, VM definitions, profiles, results, and receipts belong only in `../ts-benchmark` (GOAL §§2, 10; AGENTS.md).

The initial dependency selection should use one TLS/cryptography provider across internal gRPC and external Rustls/Reqwest/ObjectStore clients. For the proposed pins, [`reqwest` 0.13.5 with `rustls`](https://docs.rs/reqwest/0.13.5/reqwest/), [`object_store` 0.14.2 with `aws`](https://docs.rs/object_store/0.14.2/object_store/), and [`tonic` 0.14.6 with `tls-aws-lc`](https://docs.rs/tonic/0.14.6/tonic/) converge on AWS-LC; choosing Tonic's Ring alternative would add another crypto provider. The application therefore needs a documented exception for AWS-LC's C code and cc/CMake build toolchain; the storage and replication algorithms remain Rust. The exact resolved `aws-lc-sys` version is pending Cargo.lock and must not be inferred from current package metadata. [`rustls-platform-verifier` 0.7.0](https://docs.rs/rustls-platform-verifier/0.7.0/rustls_platform_verifier/) on Linux uses a system CA bundle and does not perform revocation checking; member mTLS must load explicit trusted roots, and container external HTTPS needs CA certificates. Pin features and supported platforms and inspect the resolved transitive native components with `cargo tree` before claiming compliance (GOAL §2).

## Contracts to stabilize before parallel implementation

The following are semantic contracts, not prescribed Rust signatures. Encode all buffer and work sizes in validated limits and memory permits.

| Boundary | Required semantics |
| --- | --- |
| `MemoryBudget::try_reserve(Attribution, bytes)` | The core draft implements a process-global initializer, tenant/worker/category attribution and an RAII `Reservation`. Consumers acquire it before reading, decoding, queueing, or materializing bytes; cancellation and error release it. Add independent item-count admission at queue boundaries. Track allocator live/retained, RSS/PSS, container and filesystem cache independently of reserved bytes. |
| `ShardEngine::commit(snapshot, expected_versions, encoded_mutations, AckProfile)` | One atomic mutation batch, including active index/constraint/change records; conflict failure before visibility; `CommitReceipt` carries independent received, durable, applied, object-archived frontiers. Return only after the chosen profile barrier. Unsupported profile is rejected. |
| `ShardEngine::point/scan(ReadSnapshot, bounds, projection)` | Stable snapshot, one visible version per logical record across mutable/immutable/tier states; globally ordered bounded iteration; no unbounded collect; cursor records version and retention requirements. |
| `Wal::append/sync/recover` | Stable format and commit marker; distinguish incomplete final tail from a complete corrupt frame; no acknowledged data lost at the declared barrier; WAL record and replay allocation bounded. Version 1 frame is magic[8], major `u16`, flags `u16`, total length `u32`, sequence `u64`, transaction ID (expiry `u64` plus nonce[16]), operation count `u32`, bounded encoded operations, `TBOK`[4], and CRC32C `u32` over all preceding frame bytes, with explicit little-endian integers. The frame and marker never substitute for sync. |
| `ImmutableObjectStore::put_immutable/get_verified_range` | Generate a unique final key for each immutable upload, stream a bounded multipart upload directly to that key, verify length and content SHA-256 by bounded readback, then make it reachable. Keep `{key, length, content_sha256}` as the content identity even though the key is not content-addressed. A bounded versioned descriptor sidecar holds the segment/directory identities and each block's ordinal, offset, length and SHA-256; its SHA-256 is anchored in a trusted manifest. Verify sidecar, directory key bounds/offsets, and each fetched block independently; no ETag-as-hash assumption. Coalesce reads and budget the SSD cache. |
| `ManifestPublisher::publish(expected_generation, next)` | Upload and verify all references first; atomically and durably publish recovery authority only with a qualified conditional-write or coordinated fenced authority. Never derive current generation from listing order or last-writer-wins overwrite. If provider cannot supply the protocol, reject object-durable mode. |
| `ReplicaJournal::append/ack/replay` | Durable inbox/outbox and cursor state; receipt, stored, applied, archived are distinct; idempotent replay, bounded gap repair and byte credits; retained backlog on disk; explicit resnapshot after retention. |
| `ReplicationBatch` | Versioned Protobuf metadata for database/shard, schema/format, epoch, transaction/causal IDs, cursor range and frontiers; encoded records in a `bytes` payload; the first production peer profile negotiates only the versioned `lz4_flex` application codec, with lengths, checksum and bounded decompression. Generic Identity codec support is not a production fallback. gRPC transport compression stays off for these payloads. |

The first shipped profile is local durable if only the SSD barrier has been proven. Replicated durable requires synced acknowledgments from named failure domains; object durable requires the verified remote commit **and necessary recovery authority** to be published before acknowledgment. Object archival may lag for the first two profiles, but lag and capacity exposure must be reported and backpressured. Production configuration must explicitly select a profile and declare its failure domains and recovery objectives (GOAL §4). The remote publication protocol is an explicit qualification dependency, not a library default.

The WAL transaction ID is a 24-byte retry token: a little-endian expiry in Unix milliseconds and a 16-byte random nonce. It is not a document ULID, causal clock, or ordering source. The caller reuses the exact token after uncertain acknowledgment. For an admitted token, a durable pageable deduplication index records its scoped ID, canonical mutation digest and receipt. Same ID and digest returns the prior receipt; changed operations fail. The server checks a maximum future retry window and persists an `expired_floor` in a separate monotonic shard authority **before** publishing a checkpoint or pruning expired entries. That authority survives fallback to an older valid run manifest and retained WAL. A token with expiry at or below that floor or current checked time returns `IdempotencyExpired` and is never reexecuted, even after clock rollback. A forward clock jump may expire a token early and yields an explicit uncertainty outcome. The ID expiry does not establish causality or commit order.

## Storage, formats, and lifecycle

WAL, immutable data/index segments, manifests, snapshots, and transfer envelopes carry magic, format version, explicit length bounds, checksum or authenticated content identity, and codec metadata. Persisted integers and ULIDs have specified byte ordering independent of Rust memory layout. Documents use a versioned binary field directory that permits nested-path lookup and selective projection. Define numeric precision, missing versus null, collation, array correlation and multikey ordering before indexes and replication copy these values. Check length, version, checksum, and maximum decompressed size before allocation. LZ4 via `lz4_flex` is the initial hot codec; compressed/uncompressed thresholds and block sizes remain measured choices (GOAL §§2, 6).

An immutable segment contains an ordered key/version stream split into independently verifiable bounded blocks, a block offset/range directory, bloom/filter metadata only where qualified, and a segment footer. The local CRC32C block descriptor checks accidental corruption but does not by itself establish a cryptographically authenticated remote range. For the object tier, a separate bounded versioned immutable descriptor sidecar records the full segment length/SHA-256, directory byte range/SHA-256, and each block's ordinal, offset, length and SHA-256. A future authenticated remote manifest extension binds the segment and sidecar key, length and SHA-256. Fetch and verify the sidecar; verify the directory's SHA-256 before trusting its key bounds or block offsets; then verify each fetched block against its sidecar SHA-256. This avoids a Merkle proof while a sidecar and directory can be streamed and verified within explicit memory/SSD budgets; if they require paging without full verification, introduce an authenticated hierarchy then. The existing local manifest v1 need not contain empty remote fields: add the versioned extension when the remote caller exists. The SSD cache stores verified blocks, not an unverified mirror. Remote reads fetch only required blocks, coalesce concurrent identical fetches, and keep lookup metadata hot on SSD where cost-effective. A fresh worker opens from durable manifest/checkpoint authority and lazily hydrates. Immutable-object publication is direct upload to a unique final key → full bounded readback verification → publish reachable generation. A content SHA-256 identifies bytes independently of the key; no stage-to-content-key copy is required. Reclamation requires durable proof that no manifest generation, replica frontier, snapshot, backup, or recovery range references an object; use grace periods and restartable sweeps. An abandoned upload is not published state (GOAL §4).

Checkpointing and compaction preserve versions pinned by admitted snapshots, replicas, backup/PITR, and online conversions. A conversion builds from a snapshot, captures concurrent changes durably, catches up, validates, atomically activates, and recovers or rolls back after interruption. Keep both physical copies only during the bounded transition, with their total memory/SSD/object/write amplification counted. Static layouts qualify first; automatic switching requires workload-shift and interrupted-transition evidence (GOAL §§3–4, 6).

All work consumes process, tenant, and worker budgets before it enters in-memory queues. Evict clean cache; sync dirty state before eviction; throttle compaction, transfers, repair, and indexing under pressure; spill supported operators within SSD scratch limits. Cap open snapshots and their age, per-peer backlog cache, subscriptions, codec buffers, network streams, blocking disk tasks, logs and metrics cardinality. No synchronous lock spans an await. Monitor RSS/PSS, container memory, filesystem cache, allocator, per-class permits, SSD scratch, WAL/archive lag, segment/cache health, and costs via bounded Prometheus-compatible metrics (GOAL §§2–4; AGENTS.md).

## Replication and consistency architecture

Partition-local ownership reduces shared hot-path locks but worker count and scheduling are benchmarked. A durable local operation emits a canonical change event and cursor. The replication journal batches events by count, bytes, and flush delay over long-lived authenticated tonic streams. Explicit byte credits cover encoded/decoded/queued/in-flight bytes, alongside HTTP/2 flow control. Foreground, repair/bootstrap, and control traffic have separate fair capacity. A peer durably appends before durable ack, applies deterministically before applied ack, resumes from persisted cursor after disconnect, deduplicates and repairs gaps. It may fall behind retention and then must rebootstrap from a consistent remote checkpoint plus log tail. Epoch-fenced membership and placement state prevents stale replicas resurrecting removed data (GOAL §§7–8).

The current replication crate's cursor model must remain an internal state-transition helper until an incoming-event WAL exists. A public caller-supplied trait containing only event ID, epoch and digest cannot prove that bytes crossed an actual sync barrier; a matching received event could fabricate those fields. A real `ReplicaJournal` must own append-and-sync, invoke the private cursor transition only after sync, and issue a durable acknowledgment from that operation. Recovery derives prefixes from verified persisted records, and apply acknowledgment follows the engine's atomic visibility barrier. The local storage committed-batch cursor is an outgoing feed and does not certify incoming replica durability. This dependency is a runtime gate, not a type-name convention.

`tonic`/`prost` versions and generated code must be pinned together. Use mTLS, tenant/database authorization, deadlines, stream idle/progress timeouts, bounded message sizes, certificate rotation and drain. LZ4 is a versioned **application envelope**; do not claim native tonic LZ4 support. Public typed APIs enforce their own authorization and visibility cut. Subscriptions take a consistent snapshot then deltas, track dependencies, bound slow queues, and send resync when cursor retention expires. Outbox/scheduling supplies external idempotent side effects outside retried transactions (GOAL §§8, 11).

## Indexing, query, backup, and operations

Schema and constraint definitions are durable, versioned transaction metadata. Deterministic initial index candidates derive from bounded schema/statistical passes; enforceable constraints never derive from samples. A Von or JEV advisor may rank only supplied candidate IDs or abstain. A fenced generation records exactly one durable initial decision, including provenance and fallback. Model calls use bounded, fair asynchronous queues and minimal authorized metadata and cannot block reads/writes. The live Von service is an independently hosted, warm-up-verified test requirement; JEV is optional and requires tenant authorization for external metadata (GOAL §9).

Later adaptation uses normalized query patterns, deterministic selectivity and cost, shadow validation, measured hysteresis, and build/retire cooldowns. Build indexes from a snapshot plus durable change capture to a watermark, verify results, then activate atomically. Constraint and pinned indexes cannot be silently retired. Logical index admission occurs before commit; physical/WAL/version/scratch/backup budgets are separate. If an async index is stale, query waits, falls back to authoritative data, or exposes a declared stale contract. Point, equality/range/composite/covering, nested/multikey, relationship and supported full-text paths share comparison semantics. Bounded scans, joins, sort/aggregate and spill are advertised only after correctness and resource proof. `EXPLAIN ANALYZE` reports actual rows, I/O, memory, spill, and remote work (GOAL §§6, 9).

Native encrypted S3 backup is a retained, independently restorable lineage with consistent snapshot, incremental log archive, PITR, resumable transfer and safe retention/GC. It carries schema/index decisions, formats, transaction/causal and cross-shard restore metadata. Acceptance requires a clean-environment restore and verification; being present in the live object tier is insufficient. Readiness reports durability barrier health, capacity admission, degraded cold-cache mode, lag and cost. Qualify shutdown, schema/format/protocol upgrades, credential/certificate rotation and supported architectures through the real server (GOAL §11).

## Open product and protocol decisions

1. Which exact consistency/isolation and atomicity scopes will be supported for document transactions, convergent writes, relationships, uniqueness, and cross-region reads? The goal explicitly forbids inferring strong guarantees from leaderless replication (GOAL §§6–7). The first increment exposes only validated one-shard local transactions and rejects unsupported combinations.
2. Which provider capability and fenced ownership protocol will make a mutable remote recovery root atomic? RustFS and every production provider must be probed at pinned versions; object-durable mode remains unavailable until proven (GOAL §§4–5).
3. Numeric precision, collation, array correlation and delete policy need a single public specification before persistent indexes or typed APIs are finalized (GOAL §6). Do not silently adopt serde_json or SQLite semantics.
4. Recovery-point/recovery-time objectives, failure-domain names, production S3 providers, price schedules, and practical benchmark significance threshold require declared operational/product values. The architecture provides measurable hooks but does not invent targets (GOAL §§4, 5, 10–11).
