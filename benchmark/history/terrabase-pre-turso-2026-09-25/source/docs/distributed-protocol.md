# Distributed replication and transaction protocol

This is the implementation contract for the distributed milestone in [GOAL.md](../GOAL.md), especially sections 4, 7, 8, and 11. The initial `tb-replication` source implements only bounded event validation, causal multi-value merge, and per-origin cursor rules. Its durable, applied, and recovery cursor transitions are crate-private pure helpers; no public path can mint a durable replica acknowledgment or replicate between processes. A later replica journal must append and sync the incoming event before invoking the durable transition and issuing an acknowledgment. The first executable engine increment may implement only one-shard, local-durable transactions. It must reject requests for replicated or object-durable acknowledgments until those barriers work through the real caller. Physical storage layouts may differ, but they must produce and consume the same logical committed events.

## Scope and visible guarantees

| Operation | Initial distributed guarantee | Limit |
| --- | --- | --- |
| Convergent document mutation | Any authorized current-epoch replica may accept a supported merge operation; eventual delivery, repair, and deterministic merge converge after partitions heal. A returned durability level means only the selected acknowledgment profile below. | No global serializability, uniqueness, or linearizability. A partition may prevent the requested durability barrier even when a local mutation is possible. |
| Local transaction | Atomic durable commit and snapshot visibility within one shard, including its documents, indexes, relationship state, and change records. A replica installs a received committed transaction as one visibility unit. | This does not make concurrent cross-region multi-key mutations serializable. Merge outcomes can differ from either transaction's original values at individual keys. |
| Causal session | A read supplied with a causal token waits until all dependencies are applied, or returns a bounded `DependenciesUnavailable`/retry response. A write records the dependencies it observed. | Without a token, a remote read may be stale. Retained history and admitted token size are bounded. |
| Constrained mutation | Unique keys, referential integrity, and any invariant requiring a single agreed ordering use a separately proven coordinated transaction path with durable participant/decision recovery. | Until that path is implemented, reject these distributed operations; neither a replica quorum count nor a convergent merge enforces the invariant. No cross-shard or cross-region atomicity is advertised. |

An unresolved concurrent document conflict is visible as typed sibling versions, or a typed conflict result if the public API accepts one value only. Secondary-index queries must either define correct sibling semantics or use a source read/fail explicitly; they must never silently choose one sibling. Schema changes and constraint definitions are coordinated metadata, not mergeable ordinary documents. No ULID, wall clock, or gRPC delivery order establishes causal order.

## Durable event and merge contract

The engine's local atomic commit writes an engine-versioned `CommitEnvelope` and commit marker to its WAL before reporting local durability. A later replication adapter reads committed envelopes without imposing network metadata on the initial local WAL call path. Once distributed mode is enabled, the versioned event includes:

- database and shard IDs; schema, binary record, merge-policy, and event-format versions;
- membership epoch and its placement/configuration identity;
- stable origin incarnation plus monotonically increasing, persisted per-shard sequence; `(database, shard, origin incarnation, sequence)` is the deduplication identity and is never reused after restart or restore;
- transaction group ID and full event count/range so partial receive or apply cannot publish part of a local transaction;
- the bounded causal dependencies observed by the writer, and per-operation key, operation type, version/dot, payload or deletion marker;
- a canonical checksum/digest over the persisted event identity and bytes. Versioned encoding specifies byte order and length limits independently of Rust layout.

The append, local transaction commit marker, index/source visibility update, and change record obey one local atomic publication rule. The replication stream transfers only committed envelopes. A receiver verifies authorization, epoch, format, checksum, transaction completeness, and deduplication identity before durable append. Duplicate IDs with different content are corruption, never an overwrite. A missing sequence creates a bounded on-disk gap and requests repair; it cannot advance a contiguous cursor. Apply waits for required causal dependencies and installs a transaction group atomically at a local snapshot boundary. Persistent checkpoints include enough group and deduplication metadata to make replay idempotent. The local transaction retry token is a 24-byte `(expiry milliseconds, nonce)` value with a durable expiry and prune floor; retries beyond that floor reject without reexecution. Its expiry is not causal time. Event deduplication and tombstone/causal retention are separate from this bounded client retry window.

The first proposed replacement-document merge policy is a **causal multi-value register**: a write carries a unique dot and the versions it observed; concurrent values remain siblings, while a causally later write supersedes observed values. Deletes are versioned tombstones in the same merge domain. Join is the union of causally non-dominated versions and causal evidence, with canonical normalization; the exact state/delta encoding must be proven associative, commutative, and idempotent before exposure. This avoids silently losing a concurrent document update. Other policies, including deterministic last-writer-wins, counters, and sets, require separately versioned semantics and the same proof/tests. A last-writer-wins policy would intentionally discard a concurrent value and must not use an unqualified wall-clock timestamp as causal evidence. A policy change cannot reinterpret old persisted events without a versioned migration.

Causal evidence and tombstones remain durable until a checkpoint plus all live replicas' safe frontiers, retained backups, and recovery windows prove reclamation safe. A retired or too-old replica cannot contribute pre-reclamation state; it must rebootstrap. Bound dependency vectors, sibling counts, event sizes, and open transaction groups at admission. If a bound is reached, backpressure or reject; do not truncate evidence or silently resolve a conflict.

## Frontiers, cursors, and acknowledgment

Keep frontiers per database, shard, and origin incarnation. Each is a **contiguous prefix** plus bounded gap state; a maximum seen sequence is not a cursor. Persist these separately:

| Frontier | Meaning | May authorize |
| --- | --- | --- |
| `received` | Valid bytes accepted into bounded transient or staged storage. | Flow-control bookkeeping only; may vanish on restart. |
| `durable` | Every event/group through the prefix and required metadata passed the local WAL sync barrier, or is covered by a verified durable checkpoint. | Replica durable acknowledgment and resume cursor. |
| `applied` | Every event/group through the prefix is atomically installed with dependencies satisfied and visible to local reads/indexes. | Causal-read readiness and apply-lag reporting. |
| `object_archived` | Immutable log/checkpoint bytes, integrity metadata, and recovery authority are verified and recoverably published in the declared object-store scope. | Object-durable acknowledgment and archive-lag reporting. |

An applied frontier cannot exceed durable. An object-archived frontier may advance independently of local apply, but cannot skip required recovery metadata or a transaction group. The receiver returns distinct receipt, durable, and applied acknowledgments tagged with epoch, replica identity, and origin prefix. Sender reconnects from the last **durable** prefix, may replay duplicates, and retains an on-disk resend log until retention/replica rules permit reclamation. A receipt is never a durability acknowledgment. A checkpoint may compact a cursor only with a durable proof of the covered prefix. Report lag and stalled gaps by stage in Prometheus-compatible metrics; keep labels bounded to shard/peer classes rather than unbounded event IDs.

| Receiver transition | Required guard | Durable result |
| --- | --- | --- |
| `offered → received` | Authorized current epoch; supported version/codec; length, count, checksum, identity, and memory/SSD admission pass. | No cursor advance; staged bytes may be lost. |
| `received → durable` | Complete transaction group appended and WAL sync succeeds; prior origin sequences are present or a verified checkpoint covers them. | Persist deduplication identity and contiguous durable prefix before emitting a durable ack. A higher out-of-order sequence stays in a bounded gap set. |
| `durable → applied` | Causal dependencies are applied and a whole transaction group can be published at one local snapshot boundary. | Persist replay/visibility progress; advance contiguous applied prefix. Failure leaves durable work replayable. |
| `durable → object_archived` | Immutable content and metadata verified; recovery authority published under the object protocol. | Persist publication identity and archive prefix independently of local apply. |
| `gap/expired → repair/resnapshot` | Missing range is within retention, or a complete checkpoint and tail exist. | Repair resumes at durable prefix; resnapshot activates only after staged proof and epoch handoff. |

A change-feed or subscription cursor is derived from an **applied** snapshot cut and durable change history, not a received stream offset. Snapshot-plus-delta handoff pins its history until the subscriber advances or the bounded retention window expires; expiry returns an explicit resynchronization result. This cursor also carries tenant/authorization scope and cannot be shared across incompatible scopes.

Each database selects and persists its production acknowledgment profile and named failure domains:

- **Local durable:** acknowledge after the local transaction and required metadata have synced to the SSD WAL. It does not promise loss of that device or region.
- **Replicated durable:** acknowledge only when the configured, distinct replicas in the required named failure domains have returned durable frontiers covering the whole commit under the same certified membership epoch. A local replica counts only after its own sync. Two replicas on one failure domain do not satisfy two domains. An unreachable domain causes backpressure, timeout, or explicit failure, never silent substitution.
- **Object durable:** acknowledge only after the event and all needed recovery authority are verified in object storage and a recoverable manifest/tail publication is complete. Concurrent publishers need fenced authority and a provider-verified conditional publication protocol. Upload completion alone is insufficient. Region-loss scope follows the actual object provider topology.

Record which replica IDs/domains or object publication certificate satisfied each acknowledgment for audit and recovery. Group commit may amortize barriers but cannot acknowledge early. Limit unarchived local/replicated data in bytes and age, with admission backpressure. A timed-out client may leave a committed transaction; retry by transaction ID must report its durable outcome rather than execute it twice.

## Membership, transfer, and failure boundaries

Membership, shard placement, profile changes, schema, and constraint authority require a durable ordered metadata decision from a proven consensus/coordination subsystem. A placement plan alone is not such a decision. Every data request carries an epoch and configuration identity. A replica rejects an unknown or retired epoch; during a transition, an old placement remains protected until acknowledged writes and causal/tombstone evidence are handed off or retained by an independently sufficient recovery authority. Its state sequence is `proposed → certified → copying → caught_up → active → draining → retired`; only `active` members with the certified epoch may satisfy a new acknowledgment, while copying members are learners. Activation of a new configuration must prevent any former configuration from issuing conflicting valid acknowledgment certificates: use a documented joint handoff/fencing protocol, including how isolated old writers lose authority. Merely increasing an integer epoch or timing out a peer is insufficient. An old node returning after retirement must verify the current epoch and bootstrap, not gossip stale state into a live shard.

Replica count and placement distinguish machine, device, availability-zone, and region failure domains. Selective hot-key replicas may improve read capacity but are not durable acknowledgment participants until enrolled through the same epoch and catch-up proof. Placement changes cannot silently weaken a database's declared profile. Failure detection suspects peers and triggers repair or a coordinated membership proposal; suspicion alone never permits unsafe data deletion or replacement of an acknowledgment domain. A partition may reduce availability of coordinated metadata and strict durability profiles. No global strong-read promise follows from an acknowledgment quorum.

The exact consensus implementation, old-writer fencing mechanism (for example, expiring certified authority with bounded clock-skew assumptions), and coordinated transaction protocol are separate architecture decisions. Their safety proofs and partition behavior must be documented before enabling these paths. If they are absent, the runtime must keep the relevant profile or operation unavailable, rather than presenting a partial implementation as safe.

## gRPC transport and bounded framing

Use mutually authenticated, authorized, long-lived `tonic`/`prost` gRPC streams over HTTP/2 for replication, repair, bootstrap, and control. Check in a versioned `.proto` contract. Handshake negotiates protocol major/minor, feature set, database/shard, peer identity, membership epoch/configuration identity, record and schema format range, codecs, frame/count/credit limits, and both peers' durable/applied frontiers. Reject incompatible majors or unsupported persisted formats before accepting data. Rotate certificates without dropping durable cursor state. Use deadlines for bounded calls, stream progress/idle timeouts, and graceful drain.

The replication message is a typed Protobuf **application batch envelope**, not a new gRPC compression encoding. It carries batch version, database/shard/epoch/origin, transaction range or explicit event IDs, codec ID, encoded and decoded byte lengths, checksum algorithm and checksum of canonical decoded bytes, and the binary event batch in a `bytes` field. The first production peer profile advertises and accepts only the versioned LZ4 block codec. The wire enum and generic protocol helper retain Identity for protocol tests, but production peers do not negotiate it, including for small or incompressible batches. The decoder first bounds the whole gRPC message and declared lengths/count, reserves memory, verifies encoded length, decompresses into a capacity-limited buffer, verifies decoded length/checksum, then parses bounded records. Use `lz4_flex` with an explicit raw-block contract and externally validated length; never trust an unbounded embedded length. Unknown or unnegotiated codec/version is an explicit error. Disable gRPC transport compression for these application-compressed payloads. `bytes::Bytes` mapping may reduce copies where the pinned Prost stack supports it, but is not an end-to-end zero-copy guarantee.

The v1 common admission invariant is a complete local WAL transaction group of at most **2 MiB**, distributed event metadata of at most **256 KiB**, and one complete group per batch. The application batch is bounded independently to **4 MiB decoded and 4 MiB encoded bytes** and **1,024 document changes within that group**. These limits leave room for replication metadata while avoiding a committed group that cannot fit a transfer; the future distributed source-admission path must reject a batch whose LZ4 encoding exceeds the encoded cap before local commit. That source-side gate is not implemented by the current receiver-only runtime. There is no Identity fallback in the first production peer profile. Larger groups must likewise be rejected before local commit until a separately specified staged-group protocol exists. Apply independent per-peer and process limits to queued, blocked, wire, encoded, decoded, and decompressed bytes, plus stream counts and repair ranges. The sender batches by bytes **and** count with a flush deadline; application byte credits cover in-flight reservations beyond HTTP/2 flow control. Release credits on durable stage or explicit rejection, and release memory on cancellation without advancing durable cursor. Reserve separate fair lanes for foreground commits, control, and bulk bootstrap/repair so bulk work cannot starve heartbeats or foreground barriers. Retry with bounded exponential backoff and jitter; never infer exactly-once execution from gRPC.

## Anti-entropy, bootstrap, and retention

Periodic anti-entropy compares epoch, per-origin durable/applied prefixes, checkpoint identities, and scoped content/range digests. It requests bounded missing ranges or verified immutable blocks, not whole-database in-memory scans. Reorder and duplicate delivery are normal; conflicting identity/digest means corruption requiring quarantine. Repair work has byte, request, concurrency, SSD scratch, and object-request budgets. A peer that falls behind retained log history receives an explicit `ResnapshotRequired` with the minimum valid checkpoint; it does not guess a new cursor.

A replacement replica downloads a **consistent remote checkpoint plus durable log tail** from SSD/S3 architecture's verified immutable objects. The checkpoint captures a complete per-shard cut: data and causal/tombstone evidence, transaction-group and deduplication state, schema/merge/index definitions, membership epoch, and per-origin frontiers. Install in a staging generation, verify block/range checksums and manifest lineage, replay the tail idempotently, catch up to a certified handoff frontier, then atomically activate placement. Keep old generation and required log/checkpoint objects until recovery/backup/replica references release them. Crash or cancellation resumes by durable staging cursor. An unavailable, corrupt, or too-old remote checkpoint leaves the candidate unready; it cannot be counted in acknowledgment domains. Cross-shard backup/restore needs a separately defined consistent cut; independent shard checkpoints are not automatically one atomic global snapshot.

S3 is an immutable-object tier with verified range integrity, not a random-write WAL. Object archive and bootstrap must account for request count, egress, multipart cleanup, memory, and SSD scratch. Anna's evaluated RAM/EBS tiering does not validate this path.

## Implementation handoff and adversarial gates

1. **Foundation:** expose the local committed event reader and stable transaction ID through the one-shard WAL; persist group markers and replay/deduplication metadata. Keep unsupported profiles explicit in admission. Test crash at append, sync, marker, and apply boundaries.
2. **Convergent core:** add one versioned merge policy, causal token, tombstone retention, and reference-model/property tests for associative, commutative, idempotent joins. Add randomized duplicate/reorder/drop/replay tests and concurrent document/delete conflicts.
3. **Real transport:** add checked-in Protobuf, authenticated gRPC stream, bounded LZ4 application envelope, admission credits, durable resend cursors, stage acknowledgments, and Prometheus metrics. Verify two processes in separate Firecracker microVMs with real disk sync and network loss; a merge helper alone does not qualify.
4. **Recovery and elasticity:** integrate remote checkpoint + tail, per-range repair, retention expiry/rebootstrap, epoch-certified handoff, and failure-domain acknowledgment. Verify actual object provider operations against pinned RustFS, then qualify intended production providers separately.
5. **Coordinated path:** select and prove metadata consensus and any distributed uniqueness/referential or cross-shard transaction protocol before advertising those operations. Exercise participant loss, partition, and decision recovery.

Adversarial campaigns must include: duplicate/reordered batches; a gap before an otherwise durable higher sequence; duplicate ID with altered bytes; truncated/compression-bomb/unknown-codec payloads; dependency not yet applied; partial transaction group; ack lost after durable sync; restart before/after each frontier barrier; disk full or failed sync; slow/offline peers with backlog beyond RAM; partitions and heal; two replicas sharing one failure domain; stale epoch and old writer after handoff; replacement crash during checkpoint/tail replay; retention expiry and stale tombstone replay; corrupt/missing remote range or manifest; object upload complete but publication failed; clock skew; and cancellation while credits are reserved. Assert acknowledged-data survival within the selected profile, atomic local visibility, convergence or explicit conflict, no resurrection, bounded RSS/SSD/work queues, and honest stage metrics. Benchmark drivers/results remain only in `../ts-benchmark`; qualify on the required 4-vCPU/8-GiB Firecracker topology, with SQLite comparisons only where guarantees match.
