### Next source brief: immutable object tier and remote authority

**Write boundary:** `crates/tb-object/**` owns the concrete `object_store` RustFS/S3 client, immutable transfer, verified range reader, bounded cache and publication state machine. `crates/tb-format/**` owns segment/manifest bytes and validation; `crates/tb-storage/**` owns checkpoint/run production and the `CommittedBatchCursor`; `crates/tb-server/**` owns wiring/config/metrics. The object worker must not edit storage internals or infer transaction visibility from object listing. This brief starts after core/format types are stable and runs independently of a full gRPC implementation (GOAL §§4–5).

**Narrow interface:** `put_immutable(unique_key, bounded_stream, length_limit, permit) -> VerifiedObject { key, length, content_sha256 }`; `get_verified_range(object, trusted_block_descriptor, permit) -> VerifiedBlock`; `abort_upload(upload_id)`; `list_for_gc(page_token, limit)` only for inventory, never current-generation discovery. The unique final key is generated before upload from owner/generation plus a random nonce; it is never reused or overwritten after publication. Use `ObjectStore::put_multipart_opts` and its `MultipartUpload` handle for bounded parts, completion and abort, without requiring the lower-level `MultipartStore` trait or a staging-to-content-key copy. Stream SHA-256 as input is read; re-read the completed object within bounded memory to verify length and digest before publication. On uncertain completion, verify the existing unique key; on absence or mismatch, quarantine it and allocate a new key rather than overwrite. Keep the existing local v1 CRC32C segment descriptor unchanged. A separate bounded versioned remote sidecar records full segment SHA-256/length, directory offset/length/SHA-256, and each exact stored block's ordinal/offset/length/SHA-256. A future authenticated remote manifest extension binds both segment and sidecar key/length/SHA-256. Read and verify the sidecar, then the directory **before** trusting key bounds/offsets, then the requested block. A whole-object checksum, unauthenticated CRC32C, or ETag alone cannot prove a fetched range. Split a run or reject it before remote publication if sidecar/directory caps would be exceeded; only an authenticated hierarchy can permit later paged metadata. `publish(expected_generation, fencing_certificate, verified_references, next_manifest) -> PublishedGeneration` must reject unsupported or unproven conditional semantics. Every call has request, byte, concurrency, timeout and SSD-cache budgets, and cancellation releases permits. The exact Rust async signatures can follow pinned `object_store` 0.14.2 APIs.

This choice is backed by installed `object_store` 0.14.2 source: `src/lib.rs` SHA-256 `41e29dadb4dbee57f53c03dd2cdccb46887748072adf1c0407499bf6fcc7fcb4` (`ObjectStore::put_multipart_opts`, `ObjectStoreExt::copy_if_not_exists`), `src/multipart.rs` SHA-256 `b8b6f464cc0b077538c7b360cc6701d58039f9d6757ee45532e28457be6a3d5e` (lower-level API), `src/aws/mod.rs` SHA-256 `e9a77ae524df8d2dfbb8c75d702267f0496bde928c3d34518c387da03a76f86a` (`CopyMode::Create` requires configured S3 behavior), and `src/aws/precondition.rs` SHA-256 `84383b39da1a8e827a65a6564cc7ea1bdcc36ca5ff9202f3a1` (copy modes and cleanup caveat). Create-copy adds an unqualified provider feature and another full-object copy. The unique-key protocol still requires runtime RustFS multipart/readback/abort/corruption tests; source APIs alone do not qualify it. The current `crates/tb-format/src/segment.rs` SHA-256 `bf299b170129a811e700932bb4c1c64fd27b03d65480cff08e1ace8dc1d72069` has CRC32C-only `BlockDescriptor`, so a separate remote SHA-256 sidecar and later manifest extension are explicit dependencies, not already implemented features.

**Integration sequence:** (1) use the real Rust client to probe range reads, multipart/abort, conditional **manifest** publication, pagination, metadata/auth/error/checksum behavior against pinned RustFS; create-copy is not on the blob write path; (2) upload verified immutable runs, per-block digest sidecars and sealed WAL chunks, cache/retrieve trusted blocks and coalesce identical reads; (3) publish a manifest whose complete checkpoint plus required WAL tail/schema/index/membership metadata is recoverable, under a qualified conditional update and fenced owner; (4) cold-open with SSD cache erased, then full SSD loss for the object-durable profile; (5) restartable reachability GC and orphan upload cleanup. Assert no partial or early object-durable receipt and no reachable-object deletion. ### Next integration brief: private journal and gRPC caller

**Write boundary:** `crates/tb-replication/**` owns event identity, canonical event codec, logical `ReplicaJournal`, causal multi-value-register join, inbox/outbox cursors, anti-entropy and repair. Its private inbox may depend on the existing public `tb-storage` API; `crates/tb-storage/**` remains the physical WAL/sync/recovery owner and exposes the outgoing `CommittedBatchCursor` and future retention pin/copy-before-GC operation. `crates/tb-format/**` owns local WAL v1 bytes and validation. `crates/tb-protocol/**` and checked-in `proto/terrabase/v1/replication.proto` own gRPC wire schemas, negotiated envelope, mTLS and streaming flow control. `crates/tb-server/**` wires journal/transport to actual peer processes and declares profile availability. Keep these write domains separate (GOAL §§7–8).

**Storage seam:** `next_committed(after: CommitSeq, max_encoded_bytes, permit) -> Option<CommittedBatch>` yields only whole synced groups with shard, sequence, transaction ID, canonical operations and digest; it never returns half a batch or materializes the entire WAL. `pin_through(cursor)` prevents source WAL/manifest reclamation until each required peer has a durable covering cursor, or `copy_to_outbox_and_sync(range)` creates an independently durable resend source before releasing the pin. Persist the selected retention frontier and outbox identity so a crash between copy and reclaim cannot leave a gap. A new distributed event wraps each batch with origin incarnation, monotonic per-origin sequence, membership epoch/configuration, schema/format/merge-policy versions, bounded causal dependencies and transaction group boundaries. This wrapper is versioned separately from local WAL v1; local `CommitSeq` and document ULID never stand in for global causal identity. A client retry uses the durable 24-byte transaction token; an ack lost after sync returns its prior receipt while the token is live, and an expired token rejects without reexecution. Audit the transition to distributed mode so local WAL v1 records without epoch/origin cannot be silently sent as valid distributed events.

**Journal seam:** The private `ReplicaJournal` owns a dedicated local storage directory, staged chunks, a final synced marker, recovery scan and contiguous per-origin durable cursor. It verifies stored chunk/marker identity but is not a membership or document-schema authority. The runtime must supply an unforgeable semantic proof from exact `TBMET001` metadata and the complete WAL frame, and must certify the peer, tenant/database, epoch/configuration and schema bindings before treating the journal result as network durability. A missing origin sequence remains a bounded gap, not cursor progress; a duplicate identity with different bytes is corruption. Received progress is transient. Applied and object-archived frontiers require separate durable barriers and must never be inferred from a synced inbox marker.

**Current durable-proof gate:** The frozen private-journal fixture passed 21/21 tests for marker/chunk sync, restart, gap/collision and cursor rules on its captured source. The live journal has changed since that fixture. Its crate-private cursor transitions do not issue a public ACK, and the outgoing `tb_storage::CommittedBatchCursor` does not certify incoming bytes. The next real-caller gate is an authenticated receiver that holds both transport and process reservations through bounded semantic verification and the final journal sync, then emits only the journal's contiguous durable prefix. A received ACK can report transient admission; an applied ACK waits for an atomic local install and durable replay identity. Failed or uncertain sync yields no ACK until reopen and reconciliation. Test duplicate/collision, reorder/gaps, over-cap or forged mappings, cancellation and permit release, disk/memory admission, crash after chunks and after marker sync, and two real processes with network loss. Source resend and journal GC remain separate retention work; an offline peer beyond RAM must trigger bounded repair or explicit resnapshot rather than silent deletion.

**Document mapping gate before the real receiver:** The raw-key, one-shard `tb_storage::Storage` API remains the qualified shape of the first local-durable caller; opaque raw WAL groups have no implicit document meaning. Document-aware producer and semantic mapper source now exists, with facade/public tests still being completed. The transport has separate metadata and complete WAL bytes plus a domain-tagged digest, but those byte checks alone do not certify document roles, membership, schema availability or a durable ACK. The public receive path must remain fail-closed until the opaque decoded transport artifact, budgeted private semantic proof and actual journal caller are connected and tested.

**Accepted document/replication contract (implementation and real-caller proof in progress):** Allocate an immutable 16-byte `CollectionId` in a database-scoped, coordinated catalog. Human names are renameable aliases and never appear in storage or event identity; IDs cannot be reused after drop. One shard's atomic group may mutate documents in several collections. Its canonical event metadata carries exactly one sorted `(CollectionId, schema_generation, canonical_schema_digest)` binding per touched collection, and each change selects one binding. Generation is scoped to the collection, never a database-wide scalar; all referenced schema definitions must be durable and available before apply. Old generations remain readable while retained records, events, snapshots or backups reference them. A group crossing shards requires the separate coordinated transaction protocol; the first one-shard restriction does not remove that goal.

Reserve disjoint, versioned key prefixes in a document-enabled shard for authoritative logical change records, materialized primary document states, logical catalog/constraint/relationship/change state, and locally derived physical index entries. A primary key is `document-tag || key-version || CollectionId[16] || DocumentId[16]`, with database and shard supplied by the storage scope. A logical change key additionally contains the stable event identity and change ordinal so replay cannot alias another mutation. A value has an explicit magic/version, schema binding, bounded lengths, integrity check and binary field directory/payload; materialized multi-value state also retains each sibling's causal dot and its own schema binding. Initial scalar, missing/null and byte-collation semantics are fixed in [document-contract.md](document-contract.md); broader multikey and array-correlation behavior remains a later product/schema-format decision under GOAL §6 before those operators are exposed. A document delete is a versioned tombstone `Put`, never a raw WAL `Delete`, because causal evidence must survive. The raw-key API must reject document-reserved prefixes on a document-enabled shard, or use a physically isolated keyspace; existing raw WAL has no implicit upgrade into this namespace.

The document producer reserves a per-origin event sequence under a serialized durable commit rule and commits an event marker plus one authoritative logical-change `Put` per document in the same complete local WAL group as its materialized state and any local index/constraint/change updates. It must not expose a sequence gap after a failed commit. Canonical distributed metadata v1 includes the event identity, epoch/configuration, retry token, format/merge versions, sorted collection bindings, bounded sorted causal contexts, an exact change-to-WAL-operation ordinal table and a role for **every** WAL operation. The marker's WAL value equals the canonical metadata bytes; the metadata contains no digest, WAL length/CRC or hash of itself. Decode verifies exact lengths, unique ordinals and `(CollectionId, DocumentId)` pairs, key grammars, record headers/bindings, operation kind and payload equality against the **complete** CRC-checked WAL frame before constructing a verified event or admitting its journal record. Unknown roles or raw mutations fail closed. After WAL sync, compute the single authoritative `EventDigest` and sole wire `event_digest_sha256` as `SHA-256("TBREPL-EVENT-V1\0" || u32_le(metadata length) || canonical metadata || u32_le(WAL length) || complete WAL frame)`; compare it with durable deduplication identity. The sender marker is covered by this digest but does not store it. The incoming journal's own final marker is outside the sender WAL and may store it. Preserve the exact source frame through a durable resend pin or synced outbox before WAL reclamation; neither caller-supplied digest nor an unpinned frame proves remote durability. The full grammar is in [document-contract.md](document-contract.md).

The sender's complete WAL frame can contain its own physical index writes; these are covered by the event digest and role check but are never applied as the receiver's index layout. The receiver reads the authoritative logical changes and catalog definitions, merges the whole group, then atomically publishes its own primary states, required logical constraint/relationship/change state and locally chosen physical index updates at one snapshot cut. Local indexes may have different layouts or be absent where a correct source fallback is available. A replica cannot return an applied ACK until this atomic publication and replay identity are durable. Logical query results at the same visibility cut must agree regardless of physical acceleration. Unique/referential guarantees across independent leaderless writers still require the separately coordinated path, and unresolved sibling query/index semantics must be fixed before those queries are advertised. Sender physical entries must never be mistaken for authoritative relationship or constraint mutations.

**Remaining executable ownership and order:** The document owner completes the public facade tests in `crates/tb-document/**` against `tb-format` document codecs and the generic storage API. The replication owner keeps the exact `TBMET001`/WAL role mapper, private verified incoming proof, merge rules and journal in `crates/tb-replication/**`; the D1 key ordinal is the sorted logical change index, while `source_wal_ordinal` addresses the sender WAL operation. The protocol owner keeps `crates/tb-protocol/**` and the checked-in `.proto` wire-only: its opaque decoded group retains exact bytes, bounded per-peer admission and process reservation until the runtime finishes verification and journal sync. **`TBCAU001` signed payload v1 (all integers little-endian, no padding):** `magic[8]="TBCAU001" | payload_len:u32 | version:u16=1 | flags:u16=0 | cluster_id[16] | tenant_id[16] | database_id[16] | shard_id:u64 | epoch:u64_nonzero | member_count:u16 | schema_count:u16 | member_rows | schema_rows`. `payload_len` is exactly the bytes from magic through the last row, excluding the trailing signature. The complete certificate file is exactly `payload || ed25519_signature[64]`, with no leading key ID or trailing bytes; the signature covers the literal bytes `"TB-AUTHORITY-FIXED-V1\0" || payload`. The sole trusted 32-byte Ed25519 verification key comes from the local operator configuration, never the file or peer. `configuration_id = SHA-256("TB-CONFIG-FIXED-V1\0" || payload)` is the exact 32-byte nonzero value used in Hello, `TBMET001`, the journal cursor scope and ACK context; its calculation includes schema and membership bytes, not the signature. Admit a payload of at most 4 MiB, 2–64 members and 1–1,024 schema rows, charging both byte and item budgets before parsing or cloning. Those are first-slice deployment ceilings, not a new WAL/event cap.

Each **member row**, strictly increasing by `member_id[16]`, is `member_id[16] | allowed_origin_incarnation[16] | sha256_leaf_certificate_der[32] | server_name_len:u8 | server_dns_ascii[1..253] | failure_domain_len:u8 | failure_domain_ascii[1..64]`. The failure-domain label uses only ASCII letters, digits, `.`, `_` and `-`, with no case folding; it names placement for audit but cannot authorize a failure-domain client ACK in this slice. Reject zero member/incarnation/fingerprint, duplicate DNS/fingerprint, and any local member absent from the list. Before the sender trusts any ACK, its connector must perform ordinary CA, time, EKU and signed DNS-name validation **and** match the actual server leaf DER to the expected member fingerprint; a hostname match alone is insufficient.
