The host was `mariogk-dev`, Linux `7.2.7`, Intel Xeon E5-2660 v4 at 2.00 GHz, 46 online CPUs, with every lane pinned to CPU 20 at nice 19 and idle IO priority. The fresh databases used XFS. Host RAM was 32,826,844 KiB and the recorded swap total was 33,554,428 KiB. The per-lane one-minute load snapshot ranged from 1.383 to 1.713. There was no warmup or page-cache eviction, and the benchmark did not reserve the CPU or control background load. Each [host manifest](pair-01-sqlite/environment.json) records its own observation and canonical database parent; command, stdout, and stderr files sit beside each lane.

Both lanes read back 4,096-byte pages, WAL, `synchronous=FULL` (`2`), and a 64-MiB cache (`cache_size=-65536`). SQLite `3.53.2` (through `rusqlite 0.40.2` and bundled `libsqlite3-sys 0.38.2`) set and read back `wal_autocheckpoint=1000`. Turso `0.8.0-pre.13` reported SQLite compatibility `3.50.4` and uses a source-level threshold of 1,000 unbackfilled frames; it does not support that checkpoint PRAGMA. Automatic checkpoint triggers and shutdown behavior differ. This run did not test power loss or establish equal crash guarantees.

Post-reopen storage also shows the close/checkpoint difference in every lane: SQLite had a 315,392-byte DB and no WAL; Turso had a 315,392-byte DB **plus a 539,752-byte WAL** (855,144 bytes together). Preserve each Turso `data.db` and `data.db-wal` as one image; a DB-only read omits 29 rows still represented in its WAL, while WAL-aware reopen verified all 1,000 rows and integrity. Representative raw artifacts are [Turso DB](pair-01-turso/data.db) and [Turso WAL](pair-01-turso/data.db-wal). The measured operation samples exclude close and reopen, so the loop wall duration is not an end-to-end shutdown/checkpoint throughput measure. No measured files were checkpointed or altered to normalize this difference.
