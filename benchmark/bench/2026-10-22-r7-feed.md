## Measurement method

The required R0 harness commit `7a96bf45691df2bf378b5f6061a7b1e6b4af45c1` is cherry-picked only onto utility A/B refs, never onto a PR. A starts at review main `e7fa366d`; B starts at final R7 `fcc0f9a4`. Both also contain the identical validating delivery supplement. Utility refs are `feat/r7-bench-before-r0` (`5ad2e0cec5c26144ddaf80af6a6f14fc4fcfdd50`) and `feat/r7-bench-after-r0` (`889186a3f797795412624d28f515d8138f38cd77`).

R0 runs A then B back-to-back in one held dev-host slot, chosen by unpinned `ts-heavy-any`, with `TS_HEAVY_HOST=<selected-host> nice -n 19 make -f benchmark/repl.mk bench-repl PROFILE=loopback SCENARIO=feeds N=10000 REPEATS=3`. Each repeat starts fresh authenticated three-process clusters and reports N=1/10/100 requested readers, per-node CPU, allocations, instrumented storage SELECTs, write-ack latency and exact replica-document verification. Its counters use source changes as the denominator. Feed sinks drain SSE without validating every delivered identity or waiting for all feed delivery before snapshots; these results measure write/replication cost with active readers, not cost per completely delivered event or feed receipt latency.

The supplemental [`FeedCursorBench` readers mode](../dotnet/FeedCursorBench/FeedReadersBenchmark.md) then runs A followed by B in the same slot. Each of three repeats per requested N=1/10/100 has ten warmup and 200 measured changes; each next write waits for every admitted delivery. Each sink validates the exact document id, payload sequence and total delivery count, and independent cancellation. It reports admitted/rejected readers, storage SELECTs, process CPU, process allocations and write-to-feed receipt latency. The baseline admits at most 32 readers when 100 are requested; B admits 100. This capacity difference is reported explicitly.

The supplement uses the real engine and `IDatabaseChanges.StreamAsync`, excluding HTTP authorization, TLS, networking, replication and failover. Process CPU/allocations include the producer and validating SSE consumers. Setup, admission, warmup and cancellation are outside its measurement window. Storage-read counts include warm page-cache hits and metadata, not physical disk operations or every SQL statement. The `feed` path also counts the producer's append-prefix and rehash reads. Unique producer changes and delivered events have distinct denominators.

Both pairs preserve exact source manifests, source-tree hashes, all three repetitions, host topology and host-load evidence. One held slot prevents these A/B runs overlapping each other; the host can run other managed slots, so this is not an exclusive-host claim. The later Q-SLOT instruction takes precedence over the initial beta pin for this new job; A/B remains on the same selected host. The first beta attempt stopped during restore because the hashed checkout had no sibling ts-dotnet; it produced no samples. The first retry built successfully but failed before admission: canonical uppercase ULIDs were injected as machine routing names, which `ChangeCursor.Encode` rejects. The identical utility-only fix on both refs lowercases the worker routing name and member-directory names while retaining canonical entity/config identifiers; its smoke case now opens the real feed and checks the initial cursor. No production source changes are included in these harness corrections. Retry 2 sets an existing absolute SDK checkout before building and completes both A/B pairs successfully. Earlier focused runs are superseded and are not evidence for the final source.

## Bounds and limits

- One authorized database/plan, incarnation, commit sequence, heartbeat window, exact input cursor and canonical filter identify a cached read. Authentication decisions are not cached. Different histories/filter sets still require different reads; independently issued cursors initially miss until common output cursors converge.
- Four cached/running slots do not mean four total live payloads: slow readers may retain evicted pages. Producer/cache/reader references hold tenant/process memory reservations until the final owner releases them. Producers remain bounded globally at 4096 even when their readers leave.
- Readers hold one page, send chunks at most 64 KiB except a single oversized event, and have a 10 s send deadline plus a 30 min/token lifetime. One cancellation does not cancel another reader's producer. Capacity waits use the oldest listed flight; strict FIFO fairness under sustained diverse-cursor churn is not guaranteed or benchmarked.
- Materialized documents are current values, rather than historical event snapshots. This work preserves the existing at-least-once and local committed-feed contract; it does not implement the free-reads plan's sealed, remotely acknowledged publication frontier or a CDN cache.
