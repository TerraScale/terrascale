## Method and comparison boundary

- Both table and `where active = 1` / `columns id,version` shapes; N = 1, 10, 100 and 1,000 concurrent listeners, three measured repeats per region/shape/N. Each cohort starts with a fresh table and cold sealed-object URLs: 16 rows with a 128-byte body, eight matching filtered rows, one pre-sealed catch-up change and one measured live update.
- F6 sealed-chunk contract references are `edd4f9c8c` and `3baf6b501`; the CDN-capable JS SDK reader shipped in `37d7e4bb99a7db2178ede8d3e530de6e17c3e558`. Snapshot and pre-sealed catch-up payloads follow manifest URLs through Cloudflare. Authenticated discovery and the live tail retain origin work.
- The reader calls the checked-out JavaScript SDK's `shape().subscribe()` in Node.js. F12 shares identical subscriptions on one authenticated SDK transport. N counts listeners in one SDK client; it does not count independent processes, clients, browser sessions or upstream sockets. Before F12, the same one-client driver created an upstream stream for every listener. The before/after comparison therefore includes SDK sharing as well as server coalescing, CDN hints and admission changes. It cannot isolate server coalescing or establish independent-client scaling.
- Jobs run through `ts-heavy-any` on shared dev hosts. A temporary loopback SSH CONNECT proxy in each serving region selects CDN egress; observed CF-Ray locations are tabulated below, including any routing spillover. Snapshot and catch-up latency run from subscription creation to the corresponding materialized callback. Live-update latency runs from before the write request to the updated callback. These include dev scheduling, SSH transit, SDK controls and writer latency; they are not native regional browser or CDN-only latency.
- The driver requires live-tail readiness within one second after all catch-up callbacks, inside an overall 180-second cohort deadline. A readiness failure stops the attempt and is reported separately; it is not a measured 180-second delivery timeout. Each cohort holds its established live tail idle for two seconds before the measured write. The hold contributes CPU observations and request counts, but is outside live-update latency. The earlier run had no such hold. Percentiles are nearest-rank within each repeat; latency tables show the median and min–max across three repeats. N=1 has one sample per repeat and supplies no statistically useful p99 estimate.
- The corrected guard samples GRU TerraBase process CPU ticks once per second, divided by the minimum of affinity and every ancestor cgroup-v2 quota. It stops all reader load above 70%, on missing telemetry, process restart or capacity change. Capacity is two CPUs with four-CPU affinity. CPU includes other concurrent service work with no idle-baseline subtraction; tables show the highest one-second interval mean across all repeats, not instantaneous peaks. Intervals are selected by their end timestamp inside the cohort, so boundary intervals can overlap setup. Earlier CPU values are multiplied by 4/2 and remain conditional because historical quotas were not recorded. The separate F12 72.96% cold-start sample at 23:06:02.521Z was 23 seconds after restart; the [idle investigation](2026-11-04-gru-idle-cpu.md) documents it. It is not the original F10 72.48% sample from the 20:22 cohort. The original F10 audit recorded process start at 20:13:47.630Z, roughly nine minutes before that cohort, but process identity was not captured during the historical cohort. CPU changes cannot be attributed exclusively to this workload.
- Total origin attempts include HTTP bootstrap, manifests, epoch keys, head/current-offset reads, live polling, payload fallback and WebSocket upgrade attempts, including retries/refusals. A current-offset read can return live rows when the sealed object is not yet available; it is not necessarily an empty control request. `new_data` hint frames are notifications, not additional requests, and are counted separately. CDN GET attempts and HIT ratio come from actual SDK fetch responses. Fresh object URLs and one shared upstream fetch can yield cold MISS responses for every cohort; this run does not measure repeated independent CDN cache hits. Setup, usage queries, metrics observations and OAuth exchanges are excluded.
- R2 GetObject counts come from bucket-wide Cloudflare adaptive analytics, rounded outward to whole-second reader windows. They may include adjacent setup or unrelated traffic and are not per-object attribution. Missing analytics are unavailable rather than zero. The latest receipt per cohort supplies the table; two recent windows were queried again, and their earlier responses remain in the raw receipts. The unavailable window became available; the other continued to report only PutObject after two re-queries. A response containing other actions but no GetObject action is displayed as zero reported GetObject operations; adaptive analytics do not prove that the actual object-fetch count was zero. Billed read component is the monthly ledger's `units - writeUnits`; SQL read deltas and billing are separate from infrastructure requests and dollar costs.
- This is a small workload with a sealed snapshot, one sealed catch-up change and one live change. The live change can use a third CDN object or an origin current-offset response. It does not qualify larger snapshots, longer histories, browser bootstrap, independent-client fan-out, or sustained multi-write traffic. The earlier 1,000-reader pilot timed out and supplies no qualified before value.
