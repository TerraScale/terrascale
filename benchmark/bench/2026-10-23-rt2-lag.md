# RT2c lane L: replication lag, pipelined batches A/B (2026-10-23)

Supersedes RT2 lane I's draft of this file (`rt2/lag-results`, never merged). Same local three-region cell
(`tests/TerraBase.E2E/BenchmarkClusterHost.cs` in one process, peer links with fixed one-way delays gru-sjc 84.6 ms,
gru-fra 94.1 ms, sjc-fra 68.9 ms) and the same probes (`benchmark/cmd/xregion-probe`, all six directions; idle 60 probes
per direction per round, load 40 probes beside 8 origin writers, `-load 8`). Lag = write at A → readable at B; the floor
is the one-way delay.

## Setup

- Host: dev host `mariogk-dev` (46 vCPU), shared with other lanes. Load average at each run start 9-109 (median 24, in
  `runs.txt` of the raw output); round 1 of `lag-4` and `lag-on-423` overlapped this lane's own Fast runs. Every server
  ran under `nice -n 19`, as the repo requires on dev hosts, so a woken storage worker waits for CPU behind the other
  lanes: absolute numbers sit well above a quiet A1 host (RT1 measured the whole receive at 10.2 ms there). Only the A/B
  inside one interleaved job is meaningful, with the spread shown.
- One job, 3 rounds, builds rotated per round (r1 lag-1, lag-4, lag-on-423; r2 lag-4, lag-on-423, lag-1; r3 lag-on-423,
  lag-1, lag-4), each build idle then load, a fresh cell per run.
- Builds (server code; the measured SHAs predate the rebase onto `49e32e99c`, which only added #398's `expect` fields):
  - **before** = `lag-1` `5ae1fb00b`: origin/main `d9d804812` + the lag instruments (no behaviour change).
  - **after** = `lag-4` `51f7dffd7`: + protocol version, receiver chains, window 8, jittered 100 ms → 10 s retries.
  - **after+#423** = `lag-on-423` `a9831f899`: #423 head `b1ec44124` (dirty-database ship queue) + main + lag-0..4. This
    build re-queued a database after every pipelined batch; the branch now (`e075db7a4`) re-queues only for a full page
    (see "#423"). Not re-measured.

### Read

- **Under load the window works.** Pooled p50 over all directions 292 → 172 (after) → 166 ms (after+#423); per-round
  p50 drops in every direction (e.g. fra → sjc 368 → 151 / 163). The 8 writers reach 19 → 29 → 31 writes/s, and the
  remote ack delay p50 (what a client write waits for) falls from 374-435 to 181-241 ms.
- **p99 under load:** after+#423 is the only build whose tail stays bounded: pooled 609 ms vs 1574 (before) and 4271
  (after). The after build's tail comes from its r1 and r3 rounds (host load 43 and 71 at their start;
  `receive.total` p99 444 ms) and from the O(D) ship pass (`send.pass` p99 50 ms vs 8 ms with #423).
- **Idle:** no change, as expected (p50 151-158 ms; one batch is never waiting behind another). #423 cuts `send.pass`
  from 14-15 to 0.3 ms p50, within ±9 ms of p50 per direction at this noise level; the idle p99 is host noise (141-1904
  ms per round across builds).
- **The 200 ms p99 target is not met on this host.** Best per-round p99 per direction (after+#423) is 141-255 ms
  idle and 250-553 ms under load, against floors of 69-94 ms. The p50 overhead above the floor is ~68 ms idle and ~84 ms
  under load.

## Where the time above the floor goes (after+#423, p50, idle)

Visible p50 ~150 ms − floor ~82 ms ≈ 68 ms:

| Part | p50 ms | Source |
| --- | ---: | --- |
| sender change-log read (`send.read`, 2 read transactions) | 14.0 | instruments |
| receiver apply until visible (`receive.begin` + `join` + `commit`) | 16.2 | instruments |
| ship pass (`send.pass`) | 0.3 | instruments (14-15 without #423) |
| origin write commit, commit → pass wake, gRPC/LZ4, in-process link proxy, reader poll at B | ~37 | remainder, not instrumented |

## Top 3 remaining contributors to p99 above the floor

1. **Sender change-log read**: `Engine/Sqlite/TursoChangeGroupSource.cs:109` (`ReadAsync`) + `:262` (`RetainsAsync`),
   each a read transaction through `BeginAsync` (`:78`, incarnation re-read). p50 14 ms idle, p99 50-230 ms. Idle is
   slower than loaded (2-3 ms p50): the reader worker is cold and, under `nice -n 19`, waits for CPU. In #423's files
   (TursoChangeGroupSource.cs): not changed here.
2. **Receiver apply before visibility**: `Features/Replication/StorageChangeGroupSink.cs:39-53` (durable begin, coverage
   check, per-delta `JoinAsync`, FULL commit) → `Engine/Sqlite/SqliteStorageTransaction.Join.cs:66`. p50 ~16 ms, p99
   47-228 ms per step across rounds. `receive.join` alone is 8 ms p50 for single-write batches; the per-delta collection
   metadata re-read (`Join.cs`, `ReadState(DocumentDelta.Collections, …)`) is one of ~10 statements per delta, so caching
   it cannot remove more than a fraction of that: not changed without a profile.
3. **Receiver queueing behind the database's previous batch** (pipelined builds only): `receive.wait` p99 106-111 ms
   under load (`Features/Replication/PeerStreamReceiver.cs:159` `After`, `:593` predecessor await). This is the serial
   apply of one database (SQLite has one writer); the batch would otherwise not have been sent yet. The SYSTEM-frame
   part of the same wait is not visible at idle (p50 0.3 ms, p99 0.5 ms).

Ruled out again: catalog cache misses (hit ratio ≥ 0.985), receiver open (`receive.open` p50 0.3 ms).

benchmark/scripts/xregion/local-lag.sh <out>/<build>/load-r<n> 1 40 8
