# TerraBase against the raw vendored Turso driver (RT2 lane F, 2026-10-23)

Target (user, 2026-10-23): TerraBase on one node, public HTTP API included, with replication capture on (CDC tap, change
groups, feed), within 10 % of raw Turso run in-process, same host and workload. Async shipping to peers is excluded.
A 3-node number is reported separately against RTT.

**Result: not reachable.** Reads cannot get there: an HTTP round trip alone (the floor, `GET /healthz` on the same client,
no auth, no storage) costs 5–7× a raw Turso point read. Writes cannot get there without changing the write-intent design
(decision 0013a/R6): an isolated TerraBase write syncs about 4 times where raw Turso syncs once. Details, numbers and
the fixes that did land are below.

## Setup

- Harness: `benchmark/dotnet/VsTurso/VsTursoBenchmark.cs`, run by `benchmark/dotnet/VsTurso/run.sh <out>` (branch `rt2/perf-1`).
  It is compiled into `tests/TerraBase.E2E` because the local nodes need that harness; without `TERRABASE_VS_TURSO_OUT` it skips.
  `run.sh` swaps the test runtimeconfig for the production server's: workstation + concurrent GC, tiered PGO on, DI dynamic engine.
- One process, lanes interleaved inside every repeat and cell, so host drift hits all lanes alike:
  - `turso`: the vendored driver (`src/vendor/Turso.Data.Sqlite`, Turso 0.8.2) on one file. One writer connection, each write its own
    `BEGIN IMMEDIATE` upsert and `COMMIT` with `synchronous = FULL` (WAL synced before the commit returns). Turso's default WAL journal,
    4 KiB pages, one connection per concurrent reader. Table shape of a TerraBase collection: `(id TEXT NOT NULL UNIQUE, doc TEXT NOT NULL)`.
  - `turso-cdc`: the same with `PRAGMA capture_data_changes_conn('after')`, as TerraBase's writer runs.
  - `engine`: one TerraBase node outside a cell (no peers file: `LocalDurability`). Capture, change groups and feed on; nothing ships;
    no remote-ack wait. Called in process through `IDocumentService.WriteConfirmedAsync` / `GetAsync`, the path every handler uses.
    TerraBase durability as shipped: write transactions commit with `synchronous = FULL`, plus its FULL write intents (`_intents.db`).
  - `api`: the same node through its public API: `PUT`/`GET …/documents/by-key?id=`, ts-auth project JWT (enterprise plan),
    HTTP/1.1 keep-alive over loopback, `SocketsHttpHandler` with one pooled connection per worker, response bodies read in full.
  - `floor`: the same client and listener answering `GET /healthz`: Kestrel, middleware and JSON, no auth, catalog or storage.
  - `engine-3` / `api-3`: gru of a local gru/sjc/fra cell in one process (`tests/TerraBase.E2E/Cluster.cs`), answered after a remote ack.
- Workloads: `write` (replace a random existing key), `read` (point read of a random existing key), `mixed` (80 % reads / 20 % writes),
  over 10,000 keys per size, each preloaded before any cell. Sizes: small 256 B and medium 4 KiB JSON. Every write body is unique
  (13-digit counter), so no write is "unchanged". Concurrency 1 and 16 closed-loop workers. Each cell: 1 s warm-up, then 5 s measured;
  p50/p99 from every operation; CPU µs/op = process CPU / operations (it includes the node's background work).
- Hosts (dev hosts shared with the other RT2 lanes, so load varies; every table names its run):
  - delta: 16 vCPU, WD SN540 NVMe, 4 KiB `dd oflag=dsync` ≈ 0.6 ms per sync. Baseline: main `811251348` plus the harness
    (`05449f854`), load 3–15 during the run.
  - beta (12 vCPU) was used for profiles only: 11.5 ms per sync there, so writes are disk-bound.
- Profiles: `dotnet-trace collect --profile dotnet-sampled-thread-time`, analysed on managed-CPU samples only; fsync counts with
  `strace -f -e fsync,fdatasync -y`.

The gap is −58 % to −100 % in every cell. The target (−10 %) is met nowhere.

HTTP floor on the same host (from the later delta runs; `GET /healthz`, same client): **59–80 µs p50 at concurrency 1,
about 100 µs CPU per request**, 75,000–96,000 requests/s at concurrency 16. A raw Turso point read is 11–16 µs. So
the public API cannot be within 10 % of raw Turso for reads, whatever the engine does. For writes the floor is about 6 %
of one raw Turso commit on delta (≈1 ms with its fsync), so an API write within 10 % would need the engine to cost no
more than one raw commit: it costs about 4 syncs (below).

## Where the gap is, per layer (profiles and counts)

Small point read, concurrency 1, delta, medians. The baseline row is main as shipped; the other rows come from run `perf-3`
(read-intent experiment + GUID fix), so its engine row is the engine without the intent fsyncs:

| Layer added | p50 µs | CPU µs/op | What it is |
| --- | ---: | ---: | --- |
| raw Turso read | 11 | 12 | one prepared-per-call SELECT on an open connection |
| + TerraBase engine, shipped (baseline run) | 3,533 | 2,906 | below, plus two FULL commits on `_intents.db` per isolated read (write intent recorded, then retired) |
| + TerraBase engine without read intents | 195 | 299 | read transaction (`query_only`, BEGIN, ROLLBACK), certified-copy checks, document cache, usage and stats counters, `ReadUniqueDocument` (one 3-table join), Turso statement prepare per execution |
| HTTP floor alone (`/healthz`) | 59 | 108 | Kestrel, TerraBase middleware, JSON, client; no auth or storage |
| + public API (`GET …/by-key`) | 1,443 | 2,158 | floor + engine + about 1.75 ms CPU of auth and catalog: project resolution, binding check, placement, catalog gate, each a read transaction on `_system.db` with several document reads |

Engine read CPU (sampled, managed CPU, c=16, before the fixes): statement **prepare 45 %** (Turso re-prepares every
statement on every execution, even on a reused `SqliteCommand`), **schema queries for GUID detection 20 %** (driver
`GetValue` ran `PRAGMA table_info`/`index_list` for every TEXT/BLOB expression value), statement finalize 6 %, step 14 %.
API read adds: `PrepareSingleStatement` 29 % of process CPU, a third of it in system-catalog lookups per request.

Writes: `strace` over the engine write lane counts **2.9–3.3 FULL syncs of `_intents.db` per data commit** (main: 1,912 vs
577; with the fixes 939 vs 326), so an isolated TerraBase write waits for about 4 syncs (write intent, data commit, intent
retire, and the CDC tailer's own write transaction with its intent) where raw Turso waits for 1. CPU per isolated write
is 5.5 ms on delta (raw: 0.45 ms), most of it in the write lane: `FlushStates`, `AppendFeed`, `ReadState`, Merkle fold,
unique keys, intent statements.

Ship pass: not seen in the 1-node profiles (no peers). In the 3-node runs it is part of the remote-ack wait (below).

## Layers that cannot reach 10 %, and what would move them

| Layer | Gap it holds (delta) | Why | Next step (owner) |
| --- | --- | --- | --- |
| HTTP itself | +45–70 µs p50 per request, ≈100 µs CPU, vs an 11 µs raw read | a socket round trip, Kestrel and JSON against an in-process call | none: physical floor for reads |
| Write intents (0013a/R6) | about 3 extra FULL syncs per isolated write, 2 per isolated read | intent before native use (FULL) and retire after the last operation (FULL), also for reads and for the CDC tailer's own write transactions | R6: decide whether a retire may be NORMAL (process crash still safe; power loss then faults the copy) and whether reads may record at damage detection instead of at begin; the read-intent branch shows the read gain |
| Statement preparation | ≈45 % of engine read CPU, 29 % of API read CPU | the vendored driver prepares every statement on every execution | land `ReuseStatement` once kept statements are dropped on a schema change before reuse (per-transaction schema check), not retried in place |
| Auth and catalog per request | ≈1.75 ms CPU per API request on delta | 3–5 read transactions on `_system.db` (project, binding, placement, catalog gate) per request | catalog owner: one read transaction per request, or a cache invalidated by catalog commits |
| Write-path work | 5.5 ms CPU per isolated write (raw 0.45 ms) | states, feed, Merkle, unique keys, intents and the tailer per write | profile owners (R1 capture, R7 feed, R9 engine) |

## Not measured

- Live OCI cells (lane B owns them); a 3-region number bound by real RTT.
- Production `Production` environment: the local nodes run `Development` (developer exception page in the pipeline).
- API keys instead of ts-auth JWTs.
- Hosts were shared with the other RT2 lanes (loads 3–111 on delta): within a run lanes interleave, but write cells of the
  `perf-2`/`perf-3` delta runs are unusable (other lanes saturated the disk: raw Turso writes fell from 949 to 117–310/s).

Raw per-cell JSON lines: kept with the runs (`~/vs-turso-*.txt` on delta and mariogk-dev), not committed.
