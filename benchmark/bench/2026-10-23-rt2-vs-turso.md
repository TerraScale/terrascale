# TerraBase engine against raw Turso, in process (RT2c lane P, 2026-10-23)

Target (user, Q-TURSO10): TerraBase on one node, replication capture on (CDC tap, change groups, feed), within 10 % of
**in-process** raw Turso (vendored driver) on the same host and workload. HTTP is off the fast path: the `api` rows are a
reference only. Headline gap: `engine` against `turso` and `turso-cdc`. Lane W adds the non-HTTP client protocols to the
same harness (its tables go in a section of their own).

**Result: not reached.** Point reads went from 4.9 ms to 56 µs p50 (small, c=1), still 5× raw Turso's 11 µs (−79 % ops/s).
Writes now do one sync each, as raw Turso does, but cannot be compared on this run: the host's disk was saturated by other
lanes (raw Turso itself wrote at 4–70 % of its quiet rate). The quiet-window write cells (one repeat) are below.

## Setup

- Harness: `benchmark/dotnet/VsTurso` (branches `rt2c/perf-7`, `rt2c/perf-8`; `rt2c/perf-harness` for lane W), run by
  `benchmark/dotnet/VsTurso/run.sh <out>` with `TERRABASE_VS_TURSO_LANES=turso,turso-cdc,engine,api`, 5 s cells after a 1 s
  warm-up, 10,000 keys per size preloaded, ids are canonical ULIDs. Production runtime settings (workstation + concurrent GC,
  tiered PGO). Lanes interleave inside each run.
  - `turso`: one writer connection, each write its own `BEGIN IMMEDIATE` upsert + `COMMIT` with `synchronous = FULL`; one
    reader connection per worker; table `(id TEXT NOT NULL UNIQUE, doc TEXT NOT NULL)`. `turso-cdc`: the same with
    `capture_data_changes_conn('after')`.
  - `engine`: one TerraBase node, no peers. `IDocumentService.WriteConfirmedAsync` / `GetAsync` in process, capture, change
    groups and feed on. Write transactions commit with FULL.
  - `api` (reference): the same node over its public HTTP API, project JWT, HTTP/1.1 keep-alive.
- Workloads: `write` (replace a random key), `read` (point read), `mixed` (80/20); 256 B and 4 KiB JSON; 1 and 16 workers.
- Before: `origin/main` `b578d5b0f` + harness (`rt2c/perf-bench-before`). After: the same main with every lane P branch
  merged (`rt2c/perf-bench` `c99d5b602`, never a PR).
- Host: delta (16 vCPU, NVMe), shared with the other RT2c lanes. 3 runs alternating before/after/before/after/before/after,
  2026-10-23 12:55–13:37Z, load 5–24. 4 KiB `dd oflag=dsync` took 3.4 ms per sync at the end (0.6 ms when quiet), IO
  pressure 9–15 %: disk-bound cells (writes) are not comparable.
- Cells: median ops/s (min–max of 3) · median p50 µs · median CPU µs/op (process CPU / ops, background work included).
  `turso`/`turso-cdc` pool all 6 runs (same code on both sides).

## Where the gap is, per layer

Small point read, c=1, engine lane, p50:

| Step | p50 µs | Evidence |
| --- | ---: | --- |
| raw Turso read | 11 | `turso` rows |
| main as shipped | 4,853 | two FULL commits on `_intents.db` per read (write intent + retire) |
| + reads record no intent, intents NORMAL (`perf-6`, decision 0013d) | ≈ 220 | RT2 lane M, `benchmark/bench/2026-10-23-rt2-intents.md` (on `rt2c/perf-6`): 3.5 → 0 syncs per read |
| + GUID check from native metadata (`perf-1`), kept statements (`perf-2`/`perf-3`), project-token cache (`perf-4`, API only) | 83 | profile run `read1` (40 s cell, load ≈ 20): statement prepare was 45 % of read CPU in RT2's profile |
| + no link checks on an open database (`perf-10`) | 56 | profile runs `read1` → `read2`, same host and hour: small 8,978 → 14,464 ops/s, medium 4,741 → 11,487; `RejectDatabaseLinks` was 23 % of read CPU (7 `readlink` per open, 3 opens per read). The final table's 56 µs agrees |

What the remaining 45 µs is (sampled CPU, `dotnet-trace` `dotnet-sampled-thread-time`, after `perf-10`): the 3-table
`ReadUniqueDocument` statement 21 %, GC 28 % (18 KB allocated per small read, 41 KB per medium), the hop to the storage
I/O pool and back (thread-pool dispatch and semaphore wake-ups), `BEGIN`/`ROLLBACK` and the per-transaction
`PRAGMA schema_version` check 5 %, `File.Exists` on the three opens 9.5 %, usage and stats counters 4 %.

Writes: one FULL sync per isolated write now (RT2 lane M strace: 4.9 → 1.04 syncs per write), the same as raw Turso. What
remains is CPU in the write lane, about 3 ms per isolated write against 0.4 ms raw (quiet window): state flush (13 % of
write CPU), put (10 %), feed append (8 %), state reads, Merkle fold, the intent record and retire on `_intents.db`
(about 5–9 %), and the async hops between the batch loop, the write lane and the I/O pool.

## What reaches 10 % and what cannot

- **Nothing reaches 10 % today.** Closest: medium point read c=16 −72 %, small mixed c=1 −19 % against `turso-cdc`.
- **Point reads cannot** with a storage transaction per read: a transaction (`BEGIN`, snapshot, `ROLLBACK`), a thread hop
  and a 3-table read cost more than the whole raw read. Getting there needs reads served without a storage round trip
  (the document cache already does that for hits; the run's 10,000 random keys exceed its 4,096 entries) or a read path that
  runs the statement on the caller's thread with a cached snapshot. Both are design changes, not fixes for this lane.
- **Writes might**, in principle: both sides do one FULL sync. The engine adds about 2 ms of CPU and hops per isolated write;
  at c=16 the gap was −26 % (small) in the quiet window because group commit amortizes the sync. Needs a quiet host to
  measure and write-lane CPU work (below).

## Suggestions (not done: each is over 2 h or changes a design decision)

1. Retire write intents lazily (after an idle second instead of after every last operation): removes two journal
   transactions per isolated write; the restart proof (0013c) already covers a lingering intent. Needs a shutdown retire
   and a 0013d amendment.
2. Run point reads on the caller's thread (no I/O pool hop) when a pooled session is free; keep the pool for queueing.
3. Cut read allocations (18–41 KB per read): pooled buffers for document bytes, no copies between the cache and the caller.
4. One `OpenDatabaseAsync` per read instead of three (stamping engine, rebuild-ledger refusal check, the read itself).
5. Profile the write lane on a quiet host and merge state flush, feed append and Merkle fold into fewer statements.
