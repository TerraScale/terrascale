# TerraBase against in-process Turso, over HTTP and over the wire protocol (RT3c)

## Q-PARITY (user 2026-10-24): reads against in-process Turso plus the bare round trip

**Target.** Remove TerraBase's server overhead from wire reads: at concurrency 1, p50 and p99 within 10 % of in-process
Turso's plus the bare TCP echo round trip's; at concurrency 16, throughput within 10 % of the lower of in-process Turso and
the TCP echo floor. Writes are RT2d's (engine) and not in this target.

**Result.** Both concurrency-1 p50 cells and the small p99 cell are met; the medium p99 cell and both concurrency-16 cells are
not. Run: beta (12 vCPU), `benchmark/dotnet/VsTurso/run.sh` on `main` `a7904e6ba` (with #607, #620 and #625), 3
interleaved repeats, 5 s cells, 2026-10-24 19:00–19:18Z, load 0.56 before and 3.05 after (the run's own workers), a 4 KiB
`dsync` write 1.6 ms before and 1.4 ms after.

The engine in process went from 840,050 to 1,512,591 small reads per second at concurrency 16 (#607, #620), and the HTTP API
from 35,559 to 39,872.

**Why concurrency 16 stops at about 63 % of in-process Turso.** Measured by answering each frame right after a stage of the
request (an experiment switch, not shipped), one process, same host:

| Stage answered at (small read, concurrency 16) | Kestrel transport | own sockets |
| --- | ---: | ---: |
| the frame is read, nothing else | 214,563 ops/s | 232,214 ops/s |
| after re-authorization, admission and metering | 190,720 ops/s | — |
| after the document read (cache hit) | 158,260 ops/s | — |
| the whole request (ETag and answer) | 143,529 ops/s | 150,918 ops/s |
| tcp-echo, same client | 268,374 ops/s | |

- The transport alone costs 13 % of the echo floor: frames answered with no work reach 232,214 ops/s against 268,374 for
  the bare echo (the server's receive, pipe and send per request), leaving 16 % of headroom over the 200,690 target for
  the request itself.
- The request then costs about 30 % of throughput: admission and metering (the catalog gate, the request lease, the memory
  budget, usage and pressure counters), the document cache hit (its lock, memory reservation and defensive copy), the
  ETag (SHA-256 of the stored state, 0.5 µs small and 2.2 µs medium) and the answer, about 30 % where the headroom is 16 %.
  None of these is a single dominant cost any more. Measured with #607 (before #620 and #625 cut allocation further): lock
  contention is low (277 contentions per 5 s), GC pauses take 7 % of wall time (61 gen0 collections a second, 510 MB/s
  allocated, client included), and the CPU is not saturated (6.4 of 12 cores, 44 % of it in the kernel).
- Concurrency 16 is latency-bound: 16 requests in flight on 16 connections, so throughput is 16 divided by the mean round
  trip, and the request's work plus its tail (p99 826 µs against the echo's 387 µs) sets that mean. Pipelining over fewer
  connections (4 or 8) did not help, and neither did a larger gen0 budget.

Closing the remaining 30 % would mean making admission, metering and the document cache hit nearly free per request, or
batching several requests per receive and send. Neither is done here; both touch shared request paths beyond the wire
protocol.

### Round 2 (after #637): batching and the remaining request costs, measured

Same host and harness (beta, `main` with #625, 2 interleaved repeats per variant, load 4.4–6.7; experiment builds, nothing
here shipped). Concurrency 16, ops/s.

**Batching several requests per receive and send.** With fewer connections each carrying several requests, a receive and a
send carry several frames: CPU per small read drops from 55.7 µs (16 connections) to 29.3 µs (2 connections), but throughput
does not rise (2: 134,160; 4: 145,484; 8: 136,578; 16: 133,802), because one connection's frames then run one after another
on its reading loop. Running the frames of a received batch in parallel on the thread pool (the last one inline) gives
144,204–151,544 small reads per second across 2–16 connections: a few percent, within run noise. Throughput is set by the
server's CPU per request (about 25 µs over the echo's), not by syscalls per request.

**Where a small read's server time goes, by stage** (answered right after each stage, own sockets):

| Answered after | small c=16 | medium c=16 | CPU µs per small read |
| --- | ---: | ---: | ---: |
| the frame is read | 239,107 | 237,574 | 26.0 |
| re-authorization (catalog sequence, key expiry), request metering | 214,891 | 212,001 | 29.6 |
| admission (catalog gate, request lease) and the cache share reconcile | 197,945 | 200,863 | 32.5 |
| the document read (cache hit) | 165,324 | 144,659 | 42.2 |
| the whole request (ETag and answer) | 152,945 | 93,771 | 45.8 |

The small concurrency-16 target is 200,690: a request answered after admission and before any document read already falls
short of it (197,945). That cell cannot pass while each request keeps its re-authorization, admission and metering.

**The candidate cuts, each switched off alone** (same build, back to back):

| Switched off | small c=16 | medium c=16 | small / medium c=1 p50 |
| --- | ---: | ---: | ---: |
| nothing | 147,411 | 88,231 | 44.6 / 61.8 µs |
| the cache share reconcile (a global lock per request) | 146,192 | 92,024 | 45.4 / 62.3 µs |
| the cache hit's defensive copy of the document | 147,478 | 99,672 | 44.3 / 62.0 µs |
| the ETag's SHA-256 (a fixed tag) | 154,940 | 96,570 | 41.4 / 56.6 µs |
| all three | 155,820 | 102,796 | 40.9 / 56.9 µs |

All three together leave the concurrency-16 cells 22 % and 21 % short of their targets (200,690 and 130,666), and two of them
would change shared contracts: callers receiving the document cache's own buffers, and versions cached with documents.
Not done. The medium concurrency-1 p99 (target 106.8 µs) stays at 176–205 µs in every variant, so none of these costs sets
its tail; the 4 KiB answer's allocations and copies (and the collections they cause) are the likely remainder, not measured
separately here.

## The parity table of 2026-10-24 (#585): against in-process Turso alone

**Goal (user, 2026-10-23):** TerraBase within 10 % of in-process Turso (the vendored driver) on one node with change
capture on, through a fast path without HTTP (Q-TURSO10). Pass mark: throughput at concurrency 16, p50 and p99 at
concurrency 1.

**Result.** The wire protocol (`docs/terrabase/wire-protocol.md`) passes both write cells at concurrency 16 (+30 % and
+151 % over raw Turso) and none of the read cells or concurrency-1 cells. Its point reads are 3.1× (small) and 2.5× (medium)
the HTTP API's at concurrency 16, and 2.6× / 2.4× at concurrency 1. The read cells cannot pass through any socket: the
transport floor (`tcp-echo`, the same client and frames against a loopback socket that echoes them, with no server work) is
only 9 % above in-process Turso for small reads at concurrency 16, and its p50 at concurrency 1 (24 µs) already matches
in-process Turso's (23 µs). In process, the engine itself beats raw Turso on every read cell (3.0–4.7×) and loses every
concurrency-1 write cell (−54 to −55 %).

- Host: beta (12 vCPU, NVMe), 2026-10-24 07:49–08:07Z, load 2.7 before and 4.3 after (the run's own workers); a 4 KiB

- Harness: `benchmark/dotnet/VsTurso/run.sh` (production runtime settings: workstation concurrent GC, tiered PGO), 5 s
  cells after 1 s warm-up, 10,000 keys per size (256 B small and 4 KiB medium JSON), 3 repeats with every lane interleaved
  inside each repeat and cell.
- Lanes:
  - `turso`: the raw driver, one upsert per transaction, WAL, synchronous FULL, a connection per concurrent reader.
  - `turso-cdc`: the same with change capture.
  - `engine`: `IDocumentService` in process on one TerraBase node, change capture on.
  - `api`: the public HTTP API over loopback with a project token.
  - `floor`: that listener answering `GET /healthz`, the HTTP floor.
  - `wire`: the wire protocol with an API key, a connection per concurrent worker; puts ask `local_durable`, as HTTP's
    default.
  - `tcp-echo`: the wire lane's client and frames against a loopback echo socket, the wire's floor.
- Cells: median of 3 (min–max); latencies are the median of the 3 runs' p50 and p99. Raw rows (with CPU µs and bytes
  allocated per operation) are in the run's output; the table keeps what the verdict needs.

## Verdict per cell

- **Passes (2 of 8):** writes at concurrency 16, both sizes. Pipelined puts on different documents share the engine's
  group commit, so TerraBase commits more writes per sync than raw Turso's one upsert per transaction.
- **Cannot pass over a socket (4):** reads. At concurrency 16 the small-read floor is +9 % over in-process Turso before
  any server work, and the medium floor's head room is spent by a 4 KiB answer per read; the wire server costs about
  39 µs of CPU per small read above the floor (60.0 against 21.3 µs per operation, client and server in one process).
  At concurrency 1 the loopback round trip alone (p50 24 µs) equals Turso's in-process read.
- **Fails on the engine (2):** writes at concurrency 1. The engine spends about 2.5 ms of CPU per write against raw
  Turso's 0.4 ms (feed, state, Merkle and capture rows per write; see RT2c's lane P3 analysis) and the wire adds
  nothing to it (p50 3,515 against the engine's 3,489 µs).

## Where the time goes now (wire, small read, concurrency 16)

Sampled CPU on beta (with #563, before #574): socket sends and receives (one each per request on both ends) and their thread wake-ups are about
half; GC suspensions are most of the rest (6.4 KB allocated per wire read, client included, against 2.3 KB in process).
The server path above the engine is admission, the catalog-sequence check, the API key's re-check, metering and the
answer frame. Skipping the open-store `File.Exists` check (an `lstat` per database lookup; experiment only, not changed)
added 14 % to wire reads and 19 % to engine reads; it guards against a database file deleted outside TerraBase and stays.

## Not done here

- Concurrency-1 writes: fewer rows and statements per write (feed, state and Merkle bookkeeping folded per batch) changes
  the capture design and the crash-restart proof; owned by the engine lanes (RT2c, RT2d).
- SDK support in ts-dotnet and ts-orch routing of port 7464: follow-ups; the wire listener serves only the mesh until then.
