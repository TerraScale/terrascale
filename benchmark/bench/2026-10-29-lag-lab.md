# W0-4: one-host multi-region lag lab, 2026-10-29

This measures the pinned Turso prototype, not the production SQL pivot. All four paths use real Turso source commits; `page` and the second hop of `combined` use the official native sync client applying real protobuf page replication. `push` commits each received row at a real Turso home. `direct` models a provisional overlay, with no destination SQL commit. There is no simulated page transport. After-images are deterministic inserted values validated against source SQL contents; this prototype does not capture CDC or implement a durable outbox.

Two profiles separate SQL visibility from durable-commit capacity: WAL/FULL (5-second measured workload) and WAL/NORMAL (10 seconds). NORMAL omits per-commit fsync, so its successful offered rate cannot prove durable local acknowledgment. Neither profile implements the required second-node quorum, TLS/mTLS, HLC conflict resolution, CDC/Shapes, reconnection, failover or durable revision generations. No production paths or settings changed; main remains deployable.

Each profile covers 70/90 ms **one-way**, 100/1,000 offered **single-row commits/s**, four paths and **three repeats**: 48 cases/profile, 96 total. Each has two additional seconds of warm-up with separately retained samples. FULL has exactly 500 or 5,000 measured samples/case; NORMAL has 1,000 or 10,000. Counts are per commit, not rows in a multi-row transaction. Transport batching preserves one SQL commit per row.

The independent producer keeps absolute monotonic deadlines even when the writer or sender queues fill. The tables include source achieved rate and scheduled-to-observed p99 so source saturation is visible. Lag starts at source commit return and ends at destination SQL commit return, provisional overlay parsing, or a replica SQL query after page application. Combined lag is measured on the same transaction through both actual hops; it is not a sum of hop percentiles. Percentiles are nearest rank, include every measured commit, and omit no outliers.

All files are synthetic ULID-keyed rows with a 256-byte value. Every case verifies the exact expected ordered row/content hash, every sequence, and all warm-up and measured counts. Native source/home use Btrfs NOCOW directories and recorded WAL/synchronous settings. The official replica uses its pinned client defaults. Connections and two seconds of actual transactions warm the streams before measurement. Namespace interfaces alone receive netem; raw evidence contains RTT probes, qdisc counters, source queues, batch timings, source hashes and before/after root-network snapshots. Owned namespaces and processes are cleaned up; scratch databases and sources are retained.

## Findings and corrected targets

The audit passed all **96 cases and 396,000 measured source commits**, plus 105,600 separate warm-up source commits. Every expected row/content/sequence check passed. Both profiles recorded zero qdisc drops, unchanged root-network snapshots, and no remaining owned namespaces/processes. At 70 ms, the first ping was about 280 ms before neighbor caches warmed; subsequent probes were about 140 ms, giving a roughly 154 ms mean. At 90 ms, mean RTT was 180.1–180.3 ms. Raw individual probes are retained; the first probe is not discarded.

FULL sustained the 100/s workload but **did not sustain 1,000/s**: measured source rate across those offered-load cases was **459.8–822.2 commits/s**. Source writer queues peaked at 3,309 entries, and scheduled-to-observed p99 reached 6,258.5 ms. These are overload results, not evidence of FULL latency at a sustained 1,000/s. NORMAL achieved 999.9–1,000.0/s, with source queues peaking at 1,569 and scheduled p99 reaching 2,787.2 ms. Both queues have a 4,096-entry bound. No production durability choice is changed to obtain the NORMAL numbers.

The direct provisional estimate is supported by the sustained NORMAL workload: across both rates and all three repeats, p99 was 70.3–71.4 ms with 70 ms netem and 90.3–90.8 ms with 90 ms netem. That supports a development regression ceiling of one-way delay + 5 ms for this insert-only overlay prototype. It does not qualify durable acknowledgments or production Shapes.

The home-confirmed 150–190 ms estimate is **missed even at p50**. NORMAL combined p50 was 247.6–320.1 ms at 100/s and 264.0–762.9 ms at 1,000/s; p99 reached 907.2 ms and 2,786.9 ms respectively. Long-poll still serializes request/reply rounds between batches, and page serving/application adds work. A continuous streaming page implementation is not measured here and must not inherit these results as proof of its projected latency.

For the current NORMAL prototype only, use provisional regression ceilings of **p50 ≤350 ms / p99 ≤1,000 ms at 100/s**, and **p50 ≤800 ms / p99 ≤3,000 ms at 1,000/s**, across these 70/90 ms links. These ceilings round above the worst observed repeat; they are not statistical confidence bounds or customer SLOs. Preserve 150–190 ms as an unproven engineering goal until a genuine page stream, bounded apply queues and production durability/security have been measured. R2/R3, R7 and R10 still need their own qualification; Q2 must repeat on real regions.

Push is pipelined and usually near a single hop, but its tails cannot be assumed to equal network delay. In the worst NORMAL 70 ms push repeat at 1,000/s, commit-to-send p99 was 0.18 ms, send-to-application-read p99 was 634.0 ms, and parsed-to-SQL-commit p99 was 0.55 ms. Send-to-read includes receiver/socket waiting. In the worst combined repeat (90 ms, 1,000/s), those corresponding values were 0.19, 91.3 and 0.62 ms: the much larger end-to-end tail accumulated after home acceptance, before replica query visibility. These component percentiles are diagnostic and are not added together.

Source queue high-water marks can be large even when the final achieved rate is nominal: a paused writer can catch up later. Scheduled p99 therefore remains part of the result. Source enqueue time includes normal queue-operation overhead, while full-queue counts identify encounters with backpressure. Receiver SQL processing naturally backpressures the TCP stream; raw send timings and parsed/commit timestamps retain that delay. Qdisc snapshots are end-of-case counters, not continuous queue-peak measurements.

No checkpoints, restarts, conflicts, customer traffic or failures were injected during measurement. The upstream host disables automatic WAL actions, so this run does not qualify checkpoint revision correctness or bounded history. There is no bandwidth cap, jitter or deliberate packet loss. Hardware, shared-host load, Python/JS observers, filesystem behavior and the official replica's defaults are part of the measured prototype; extrapolating production TLS, quorum or real-region behavior from these numbers would be unsupported.
