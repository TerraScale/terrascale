## Reviewed contracts

1. **Redelivery and lattice joins:** the storage sink rejoins delivered groups; `SqliteStorageTransaction.Join` skips unchanged document state before writing its feed/state rows. Lattice counters join componentwise maxima, bases choose a deterministic version/value order, and sets retain their add/remove dots. This is idempotent state application, not a persistent transport-message deduplication ledger.
2. **Origin order:** one batch per database is in flight on a stream; decoded group IDs increase within a batch and successful batches increase within a sender incarnation. Replacement streams cancel and join all predecessor work before the welcome. Different origins can apply concurrently and resolve through the lattice.
3. **Durability:** `StorageChangeGroupSink.ApplyAsync` groups whole origin groups into bounded transactions and uses `BeginDurableTransactionAsync` for every chunk. The receiver waits for sink completion and stable lookup before returning an ACK. No change to transaction size, FULL synchronization, ACK eligibility, wire format, or disk format is proposed by this review.
4. **Incarnations and refills:** source digest and bucket reads are pinned to the named incarnation; a missing/replaced source refuses. Failed or interrupted refills keep the database cut across reconnects and sender incarnation changes. The receiver serializes same-database refill/application work. Push incarnations scope change IDs rather than document versions: a new incarnation may restart IDs. Reconnect replay joins lattice state; blanket rejection of every old sender incarnation is not the current contract (`replication-incarnations.md`).

## Measurement method

Use R0 harness commit `7a96bf45691df2bf378b5f6061a7b1e6b4af45c1`, cherry-picked only onto temporary measurement refs. It is not included in the R3 PR. A: `8197fcf56` (main `e7fa366dd` plus harness); B: `042b5ba31` (R3 `39d181906` plus harness). Both run back-to-back on beta with identical arguments:

```sh
TS_HEAVY_HOST=beta nice -n 19 make -f benchmark/repl.mk bench-repl SCENARIO=writes N=3000 REPEATS=3 OUT=benchmark/bench/2026-10-22-r3-before
# B uses the same command with OUT=benchmark/bench/2026-10-22-r3-after.
```

The harness drives three real authenticated server processes, one write origin and two receivers, with 16 concurrent requests, single-document and 16-document HTTP batches, deterministic seed 20261022, and a 256 B / 1 KiB / 8 KiB document mix. Each repetition uses fresh clusters and verifies every document's count and digest on every replica. CPU/allocation windows include load, remote durable confirmation, background work and low-rate visibility probes; exact listing verification follows the cost window. Receiver CPU and managed allocations are measured separately on sjc/fra using runtime counters. The initial 100,000-document run was stopped before producing a complete repetition: at roughly 40 documents/s on the busy host, both revisions would take hours. Both final revisions use the same reduced 3,000-document workload.

Report median and min–max across three repetitions. Dispatch-to-visible lag includes a 10 ms polling interval and GET latency; it is a local convergence measurement, not WAN latency. Do not infer receiver throughput in isolation from end-to-end HTTP throughput. FULL commit behavior, apply transaction size, wire format and disk format are unchanged.
