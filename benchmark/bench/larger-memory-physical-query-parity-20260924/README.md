# Larger-than-memory physical-query qualification

This C# runner extends the separate SQLite parity baseline to a dataset larger than an enforced memory limit. It exercises direct `DurableIndexStore` queries and embedded SQLite JSONB queries. Each engine gets two fresh, separate one-index databases: one indexed on `status`, one on `profile.segment`. Each database runs equality on its indexed field and a scan on the other field. Indexes are explicitly chosen from the evaluation predicates; this is physical-query qualification, not advisor evaluation.

The qualification fixture has 3,000 base documents plus 100 maintenance documents. Each body carries a deterministic 98,304-byte high-entropy payload before Base64 encoding, as well as the same `status`, nested `profile.segment`, and `value` fields used by the 2,000-document held-out baseline. Base documents are inserted in 25-document commits, then the 100 maintenance documents are updated in four 25-document commits without changing predicate membership. This runner inserts SQLite's 100 maintenance seed documents in one transaction, while TerraBase inserts them in four 25-document frames. Its build and maintenance timings therefore do not have equal transaction sizing. Both fields return 31 ordered IDs. Every first and repeat result is checked against the exact expected IDs. This fixture is distinct from the 100-row held-out baseline.

The default TerraBase arm deliberately closes and reopens its physical index every 500 base documents and after maintenance. At every checkpoint it verifies all committed IDs, body fields, deterministic payloads, versions and durable watermark using 100 indexed equality queries. Checkpoint reopen, GC and verification work are included in the reported seed/maintenance wall time and separately itemized in raw receipts. SQLite does not perform these intermediate reopens. The `--continuous` mode keeps one store open throughout ingestion, then closes and reopens once for query and full-body verification. The two modes have separate receipts.

Build outside the limit, from this directory:

```sh
dotnet build LargerMemoryPhysicalQuery.csproj -c Release
```

Run alone in a zero-swap 256 MiB user scope, also from this directory:

```sh
systemd-run --user --scope --collect --quiet \
  -p MemoryMax=256M -p MemorySwapMax=0 -p OOMPolicy=stop \
  env DOTNET_GCHeapHardLimit=8000000 \
  dotnet bin/Release/net11.0/LargerMemoryPhysicalQuery.dll --continuous
```

The runner reads its own cgroup v2 `memory.max` and `memory.swap.max`, requires an effective cap no greater than 256 MiB with swap disabled, and rejects any lane whose database/index file lengths fail to exceed 256 MiB. The explicit 128 MiB GC heap hard limit is also checked; it applies to the entire runner, including both SQLite and TerraBase lanes. It writes a new `run-YYYYMMDDTHHMMSSZ/` directory containing Markdown and raw JSON. The raw receipt contains the actual cgroup path and counters, source hashes, exact IDs, physical plans, each repeat sample, phase timings, process RSS and `/proc/self/io`, file lengths, and reopen evidence. It deletes successful disposable database files after capturing their measurements. A failed run leaves `failure.txt` and the unfinished database files for diagnosis.

The first 100-row attempt failed under the 256 MiB cgroup while TerraBase encoded an index frame. Its exact source and stack are preserved in `run-20260924T045220Z/`, with a Markdown and JSON failure receipt. The second 25-row/GC-cap attempt failed during TerraBase frame staging and ZoneTree segment compression; its own source and stacks are preserved in `run-20260924T045816Z/`. Neither failure is a warmup or excluded measurement.

The periodic-reopen diagnostic completed in `run-20260924T050613Z/`: all four final physical databases exceeded 256 MiB, every indexed and scan query returned the expected ordered IDs, and each TerraBase checkpoint verified all committed bodies, versions and watermarks. Its final cgroup sample had `memory.peak=268,439,552`, `oom=0` and `oom_kill=0`; `memory.events max=215382` records pressure at the cap. This success qualifies only periodic-reopen ingestion.

The first byte-cap/gate `--continuous` attempt is a separate failure in `run-20260924T051817Z/`. All 3,000 base documents, 100 maintenance inserts and 100 maintenance updates committed in-process at watermark 128. The first TerraBase durable reopen then threw `OutOfMemoryException` while `HasStaleEntryGeneration` built a list of every retained full document. No post-reopen correctness or query result was obtained. Its failed-attempt receipt preserves the exact source, hashes, stack, last committed progress, and last observed cgroup events. The sampled segment-WAL total and on-disk metadata count in that attempt do not establish live mutable-WAL or read-only-segment peaks.

After the streaming reopen/repair fixes and ZoneTree byte-cap fixes, a fresh `--continuous` run completed in `run-20260924T054213Z/`. Each TerraBase lane continuously committed all 3,000 base documents, 100 maintenance inserts and 100 updates, then closed and reopened at watermark 128. Each lane verified every one of the 3,100 IDs, complete bodies, deterministic payloads and versions after reopen. Both one-index TerraBase databases exceeded 306 MiB; both SQLite databases exceeded 408 MiB. The final cgroup sample had `memory.peak=268,435,456`, `memory.events max=95269`, `oom=0`, and `oom_kill=0`. The live ZoneTree samples after committed frames found at most 8,278,189 bytes in the current mutable WAL and a read-only segment count of 3. These are sampled values, not strict between-frame peaks. The raw receipt records every query plan, exact ordered ID result, timing sample, source/assembly hash, and resource observation. `frozen-provenance.json` maps hash-checked copies of the exact runner, TerraBase and ZoneTree source and assemblies used. This run supplies evidence for the exact valid-generation continuous-ingestion, durable-reopen and physical-query path; it does not itself exercise stale-entry repair or missing-proof recovery. Independent source review remains in progress.

For a quick functionality check without a cgroup, run `dotnet run --project LargerMemoryPhysicalQuery.csproj -c Release --no-build -- --smoke --continuous`. The smoke uses 200 base documents with 1 KiB payloads, labels its output **unqualified**, and makes no larger-than-memory claim.

The first timed query occurs after closing and reopening the physical store. It qualifies durable reopen, not a cold disk: the OS page cache is untouched. Same-connection repeats are warm at the API boundary, although the full qualified dataset cannot fit in the cgroup memory limit. SQLite `PRAGMA integrity_check` and row count are verified after queries; the TerraBase watermark is checked on reopen. All queries check exact ID order.

Input JSON generation is timed separately from incremental seed/index maintenance. Output ID JSON serialization is timed separately from query plus ID extraction. SQLite selects IDs, while TerraBase `QueryAsync` decodes and materializes each matching full body before the runner extracts IDs. This difference is especially material for the 98,304-byte raw payload, so the query timings are not pure engine cycles and no cross-engine speed ratio is supported. SQLite uses WAL with `synchronous=FULL`, a 16 MiB page cache and 16 MiB mmap; the direct TerraBase index store uses its normal durable WAL, includes full document copies, and omits its authoritative source database, planner and advisor. The two implementations have no shared index-admission or cache-budget contract.
