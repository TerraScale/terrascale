# Changes feed cost on the TerraBase write path, resource-limited local box (2026-10-12)

Slice R8 (`GET /databases/{id}/changes`) makes every document write also insert one `_tb_feed` row in the same
transaction, so each write carries one more CDC-captured row. This measures what that costs, with the load of
[2026-10-12-r3-cdc-cost.md](2026-10-12-r3-cdc-cost.md).

- Builds: Release. **base** = `07f8d81f` (R3 stack, no R8); **r8** = `b8e011c9` (`feat/r8-changes-sse`). ts-dotnet
  `bcd2060`. `repl-bench` built from each tree (benchmark/ is identical in both).
- Load: one region (gru), `TERRABASE_BENCH_REGIONS=gru`, BenchmarkClusterHost started as in
  `benchmark/scripts/repl-local.sh`,
  `repl-bench --docs 30000 --batch 1 --concurrency 16 --conflict-docs 0 --probe-every 0`: one PUT per document, sizes
  256 B 70 % / 1 KiB 25 % / 8 KiB 5 %, 1 % deletes.
- R3's runs had the same uncontrolled CPU limit as the exploratory set below: `AllowedCPUs=0,1` did not take effect in
  their user scope either.

## Controlled

### Host topology (beta)

AMD Ryzen 5 PRO 6650H; 1 socket, 6 cores, 2 threads per core; `nproc` 12; 1 NUMA node (CPUs 0-11). SMT siblings are
(0,1), (2,3) ... (10,11): **CPUs 0 and 1 are the two threads of one physical core.** CPU frequency scaling is active
(`lscpu` showed 45 %).

### Limits

The TerraBase host process (the process that serves the region) was started as:
`systemd-run --user --scope -p CPUQuota=200% -p MemoryMax=512M -p MemorySwapMax=4G taskset -c 0,1 dotnet run ...`.
`AllowedCPUs` is not used because beta's user manager does not delegate `cpuset`, so it would not take effect. The load
driver ran with `taskset -c 2-11`, outside the scope. No root, no host setting, no cgroup write outside the run's own
scope.

Effective limits were read 15 s into every load from the process that serves the region: it is the pid in the
benchmark's targets file (`TerraBase.E2E`, which hosts the node in-process: no child processes) and the owner of the
region's listening port (`ss -ltnp`). Every run, both builds:

| Limit | Value read from the server process |
| --- | --- |
| `Cpus_allowed_list` (`/proc/<pid>/status`, `taskset -cp`) | `0-1` |
| cgroup (`/proc/<pid>/cgroup`) | `/user.slice/user-1000.slice/user@1000.service/app.slice/run-p<…>.scope` (one per run) |
| `cpu.max` | `200000 100000` (2 CPUs) |
| `memory.max` / `memory.swap.max` | `536870912` (512 MiB) / `4294967296` (4 GiB) |
| `cpuset.cpus.effective` | absent in the scope (`cpuset` not delegated); nearest ancestor `/user.slice`: `0-11`. The CPU restriction is the affinity above |
| load driver | `Cpus_allowed_list 2-11`, its session scope, no cgroup limits |

### Result

- **Throughput: −8.9 %** (385 vs 423 documents/s, means of three runs); p50 +3.6 ms, p99 +3.9 ms. CPU per document
  +7.3 % (3.81 vs 3.55 ms of CPU).
- **Both builds are below the design's 500 operations/s floor** (docs/terrabase/multi-region-replication.md, section 22,
  item 1) on these 2 CPUs, base included. The host used 1.5 of its 2 CPUs on average.
- Disk +5.7 % (149 vs 141 MB; nothing trims `turso_cdc` in this harness, see R3). Memory unchanged.
