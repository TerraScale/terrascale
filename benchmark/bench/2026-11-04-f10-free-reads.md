## Method

- Measured checkouts: `f7ab01c85552baf146aa2ccf6c390a856b3f3957` (beta, Node v24.21.0), `9c462073a829554873731e8912fc6b31a4c032b6` (delta, Node v24.21.0); shipped CDN reader: `37d7e4bb99a7db2178ede8d3e530de6e17c3e558`.
- Generators are admitted with `ts-heavy-any`; no load generator runs on serving hosts. Completed cohorts are retained across resumed runs without being measured again.
- One throwaway Free account, one gru home database, fresh table and cold object URLs for every cohort. Each table has 16 rows and a 128-byte text field; the filtered shape uses `active = 1` and columns `id,version` (8 rows).
- Public origin reads publish one snapshot and a one-row catch-up update before measurement; both sealed objects must be listed in the manifest. These setup requests are excluded. The measured readers use `db.shape().subscribe()` without a replacement transport or synthesized response.
- Each region runs separately through a temporary loopback-only SSH CONNECT egress proxy in gru, sjc or fra. Reported Cloudflare locations come from `CF-Ray`. Latencies include dev-host/tunnel transit and SDK control requests; they are not native regional browser latency or a CDN-only latency estimate.
- N independent subscriptions start together, reach the snapshot and current head, then receive one committed row update. Snapshot latency ends at the first materialized snapshot callback; tail latency starts before the write request and ends at each updated callback. The writer stays on the dev host.
- A cohort that hits its deadline is recorded and the next cohort proceeds, unless the CPU guard aborts the run. Percentiles require every reader in that phase; a completed subset never substitutes for the full cohort. The tail update is not attempted if the full cohort cannot reach the current head.
- Target: three measured repeats for every shape/region/N; the repeats column records completed cohorts. Nearest-rank p50/p99 within each repeat; tables show the median and min–max of completed repeat percentiles; fewer than three repeats remain unqualified. N=1 supplies one latency sample per repeat, so its p99 is not a statistically useful tail estimate. Cohort deadline: 180 seconds.
- The authenticated bootstrap, manifests, keys, empty head probes and live tail remain origin requests. Counts include retries and refusals, exclude setup, usage observations and OAuth exchanges, and are separated from immutable payload requests. A shared token provider refreshes the synthetic account's 60-second access token before expiry.
- CPU is sampled every second from TerraBase's runtime CPU-time counters in gru, divided by its reported processor count. Every phase stops if the sample exceeds 70%, telemetry disappears or the process restarts. Table values are the highest sampled one-second mean, not instantaneous CPU.
- Usage observations include the database's best-effort operation counter and the project's monthly ledger. SQL read-unit deltas are fair-use units; the billed read component is `month.units - month.writeUnits`. This is ledger evidence, not a Stripe invoice or an infrastructure-dollar estimate.
- R2 counts are Cloudflare `r2OperationsAdaptiveGroups` results for `ts-terrabase-shapes-prod`, rounded outward to whole-second reader windows. They are bucket-wide adaptive analytics, may include unrelated traffic/adjacent setup, and are not per-object attribution. An empty analytics result is unavailable, not zero. Client MISS counts are not substituted for R2 GetObject counts.

- This is a small two-object workload. It does not establish latency or origin cost for larger snapshots, longer catch-up histories or browser bootstrap behavior.
