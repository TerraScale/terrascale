# F7: live sjc shape overlay

On 2026-11-05, a Free synthetic account proved local `provisional` → `confirmed`
and a home rejection producing `revert` on a live sjc shape tail. Three measured
forwarded-write repeats had acknowledgement-to-provisional p50 of **4.261,
3.994 and 4.316 ms**, below the 10 ms steady-state target. All 60 measured
forwarded writes appeared first as provisional, then as confirmed rows.

[Raw results](2026-11-05-f7-live.json) contain every measured sample, the fixed
warmup, transaction-level local tail responses, the rejection and regional
health snapshots. Every proof database and the synthetic account were deleted;
regional credential files and executables were removed.

## Deployed source and method

Authenticated health snapshots initially identified F7 source
`6cacd06cf63aa75d91eaac5d1230b550ffc87fae` in gru, sjc and fra, image
`ghcr.io/terrascale/terrabase@sha256:e8a4665a262477a6bb008949d98c292daf06f379fbbe42697b14bfa4862922ad`.
Production subsequently rolled forward during the proof window; final health
snapshots identify `d38f9b02e73c49d2322cc33fc042f0a068ca414a` in all three
regions and are retained separately in the raw results. The later source contains
F7; this report does not attribute the whole measurement window exclusively to
the initial image. The F7 shape implementation was unchanged by that roll-forward.

Both clients ran on `ts-sjc-1`, connecting to `127.0.0.1:443` with the public
`api.terrascale.tech` TLS name through the existing edge. Databases were homed in
gru with an sjc replica. No serving configuration, clocks, links or security
permissions were changed. Credentials were supplied on stdin from mode-0600
files. The Go binary was cross-built for linux/arm64 on a dev host through
`ts-heavy-any`; the network-bound production HTTP proofs ran directly, as
instructed by the parent.

## Forwarded writes: three measured repeats

[`overlay-bench`](../cmd/overlay-bench/main.go) ran with `-region sjc -writes 20
-repeats 4`. The first complete repeat was the fixed warmup; repeats 2–4 are
the three measured repeats below. Raw samples keep their original repeat
number and explicitly mark `phase` and `measuredRepeat`.

A parked HTTP/2 live tail sends `local=<digest>`. The client then inserts one
row through sjc without the home-durability header, so the write is forwarded
to gru. The response injects its rows into sjc's provisional layer. The client
times the write response, first provisional tail response, and later confirmed
row with no pending provisional copy. The 150 ms parking delay, setup and token
acquisition are outside the measured interval. Connections are reused. Quantiles
use the tool's sorted index `floor((n - 1) * p)`.

| Repeat | Writes | Provisional first | Write p50 (ms) | Ack → provisional p50 (ms) | p95 (ms) | p99 (ms) | Ack → confirmed p50 (ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 20 | 20 | 196.659 | 4.261 | 25.661 | 25.661 | 35.070 |
| 2 | 20 | 20 | 204.406 | 3.994 | 23.701 | 23.701 | 34.128 |
| 3 | 20 | 20 | 198.459 | 4.316 | 29.540 | 29.540 | 32.707 |

With 20 samples, these p95/p99 order statistics resolve to the same sample;
they do not establish a production tail-latency SLO. The warmup repeat had
ack-to-provisional p50 **21.528 ms**, so the sub-10 ms result qualifies steady
state, not startup or every individual update.

## Local writes: provisional then confirmed

[`overlay-proof/run.py`](../overlay-proof/run.py) first followed the snapshot
redirects and qualified an immediate live response from sjc. After five warmup
writes it ran three measured repeats of 20 inserts, each with
`TerraScale-Durability: home`. Every response identified sjc and `commit=local`.
Each tail showed the row with its local transaction ID and provisional key,
then received that same ID in `confirmed` and dropped its pending copy.

| Repeat | Writes confirmed | Write p50 (ms) | Write start → provisional p50 (ms) | Ack → provisional p50 (ms) | Ack → confirmed p50 (ms) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 20 | 206.863 | 25.261 | -180.109 | 55.024 |
| 2 | 20 | 204.000 | 23.445 | -179.521 | 54.832 |
| 3 | 20 | 203.826 | 24.509 | -178.592 | 54.253 |

These are medians from the Python HTTP/1.1 client, with separate persistent
connections for the writer and tail. Negative ack-to-provisional values mean
the tail showed the row about 179–180 ms **before** the home-durable write
response. Write-start timing includes the local commit and JetStream publish;
it does not isolate commit-to-tail execution time. The public API currently
waits for the home when committing locally, so these numbers do not establish
a sub-10 ms local write-ack SLO or an exact local commit-to-tail percentile.

## Forced home rejection

The runner parked the tail, dispatched a home-only insert, then sent a local
insert of the same primary key 10 ms after the home request had left the socket.
The home insert crossed the link while sjc still had the preceding copy. The
home insert won; the sjc transaction committed provisionally and its pushed
insert was rejected at gru. This succeeded on the first overlapping attempt.

The retained transaction `01M6NTCEZKDMYEHJPH8DKBXPBX` appeared as:

1. A provisional sjc row, key `~01M6NTCEZKDMYEHJPH8DKBXPBX.66`, at offset `279`.
2. A `revert` with that same transaction ID at offset `285`, `local: "0"`, an
   empty provisional set, and the confirmed home row `v: "gru"` under key `66`.

The local write returned HTTP 400 `primary_key_violation`; the home insert
returned HTTP 200. A subsequent home read verified `v: "gru"`. The rejection
did not require cutting a production link or disabling validation.

## Qualification and cleanup

Preliminary attempts qualified the runner's arm64 target, redirect following,
HTTP header case normalization and new-replica retries. A sequential conflict
attempt was refused locally after the replica had already pulled the home row;
it was not counted as a home rejection. One preliminary live request returned
HTTP 500; its server exception was not retained. The final run recorded four
HTTP 503 catch-up retries before measuring, and no HTTP 500s. Read retries are
bounded and retained in the raw results; the runner does not retry writes.

The final local/rejection run exited successfully and deleted its database.
The Go run completed all four repeats and deleted its database. The account
deletion helper returned `DELETED` after its documented second call; its local
state and API key were removed. The proof uses no new service tests; F7's
existing two Slow integration tests cover confirmation and home rejection.
