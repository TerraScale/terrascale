# RT2 lane B: live 6-direction replication on OCI gru / sjc / fra (2026-10-23)

Replication works in all six directions and concurrent same-document writes converge everywhere to the LWW-by-(HLC, node)
winner. Lag misses the p99 < 200 ms target in every direction: p99 is 344 to 352 ms between sjc and fra (A1 hosts) and
506 to 609 ms for the gru rows, which ran on a CPU-starved free VM. No link's RTT makes p99 < 200 ms impossible for
one-way lag. Raw data: [2026-10-23-rt2-live-6dir-raw.tar.gz](2026-10-23-rt2-live-6dir-raw.tar.gz)
(sha256 `69a590b4458099a2301611a07015cebedb0732a099409849f54a2283cd9c029d`).

### Convergence of concurrent same-document writes

[`repl-converge`](../cmd/repl-converge/main.go), client on ts-sjc-1 every repeat. For each pair it PUTs `{"w":"<region>-<n>"}`
to both regions at the same instant, waits until all three regions serve identical bytes, then reads every region's changes
feed for both writes' (HLC, node) stamps and checks that the survivor is the LWW winner.

| Repeat (binary) | Raced | LWW-correct | Throttled out (429 ×10) | Converged p50 gru+sjc / fra+gru / fra+sjc |
| --- | ---: | ---: | ---: | --- |
| 1 (`8a891620`) | 142 | 142 | 8 | 192.9 / 216.2 / 274.4 ms |
| 2 (`8a891620`) | 147 | 147 | 3 | 200.7 / 200.6 / 219.8 ms |
| 3 (`8a891620`) | 150 | 150 | 0 | 202.5 / 195.3 / 207.1 ms |
| 3 earlier repeats (pre-commit build, no 429 retry) | 450 | 450 | 0 | – |

- **0 LWW violations in 889 races.** Every region ended on the same bytes, and the survivor was always the write with the
  higher (HLC, node), as `EntryVersion.CompareTo` orders them.
- **Survivors follow arrival:** the client sits in sjc, so its sjc write lands first and loses to fra and gru. gru wins
  against fra (gru's write lands later). That is the expected LWW behaviour.
- **Feed coverage:** each region's feed holds its own write. It holds the other region's write only if that write arrived
  first (repeat 3: sjc 127, fra 86, gru 52 of 150). A later-arriving loser never commits there. The union of the three feeds
  always held both stamps.
- **Convergence tails:** max 7.0 s (fra+sjc, repeat 1) and 43.4 s (gru+sjc, repeat 3). Lane C was loading the same cell
  then, and polls answered 429 count as "not agreed", so these tails mix throttling with lag.

### SQL / pgwire

- **No write path:** main accepts SELECT only (`Features/Postgres/PostgresStatements.cs:23`, `PgKind` has no write kind;
  the SQL subset is `SELECT … FROM`). Nothing to test for writes.
- **Reads over pgwire (each host's loopback :16432):** one document written in each of gru, sjc and fra is returned by
  `SELECT … FROM probe` in all three regions. One query on fra got `53300 tenant busy` while the convergence run polled;
  the retry passed.
- **SQL over HTTP:** `…/sql` is a management route and needs a ts-auth `databases:read` project token. The cell cannot
  mint one; the internal listener answers `unknown_route`.

### "query too expensive" on gru (lane D's question)

The same verify-style listing (`GET …/documents?limit=1000` pages, 9 collections, 7,200 documents) passes on sjc and fra.
On gru it fails after about 1.1 s per page with `400 invalid_query "query too expensive"`, then `429 tenant_memory`.

- **The limit is real, and it is the plan's:** the test organization is Hobby (`Features/Qos/QosPolicy.cs:21`), which
  allows 1 s of SQLite execution per statement, 1 M work units, 50 rps, concurrency 4 and 6.25 % of the node's memory
  budget. The budget check is in `Engine/Sqlite/SqliteStorageTransaction.cs:546-547`.
- **The VM trips the time part:** a 1,000-document page takes over 1 s on the starved VM and less on A1. The VM's 1 GB
  RAM shrinks the memory share.
- **Finding:** the deadline is wall clock, so the same request is valid in one region and refused in another on a slow or
  loaded node.

## Where the time goes (sjc → fra, p50)

Packet captures on wt0 at both ends, 60 probes each, parsed with #417's `capture-stages.py` (ports adjusted).

| Stage | RT1 (`eec12aee`) | 3-region db | sjc+fra-only db |
| --- | ---: | ---: | ---: |
| origin: request in → batch out (sjc's own clock) | 16.8 | 114.7 (p10 47.0, p90 165.1) | 86.5 (p10 64.6, p90 193.3) |
| dest: batch in → ack out (apply + fsync + ack) | 10.2 | 34.9 | 36.0 |
| dest: batch in → first GET that sees it | 12.5 | 44.3 (p90 215.6) | 37.2 (p90 150.7) |
| end-to-end latency p50 / p99 | 98.7 / 239.0 | 234.1 / 331.8 | 206.1 / 415.5 |

Checked and ruled out as the main cause:

- **The slow gru peer:** a database placed only in sjc + fra (no gru link) shows the same origin stage, 86.5 ms.
- **The ship pass scanning databases** (`PeerStreams.cs:621`, `TursoChangeGroupSource.cs:54`, owned by R1/R3): the cell
  nodes hold 3 databases, so ~3 ms.
- **fsync:** 4 KiB fsync p50 / p99 / max is 2.0 / 6.3 / 12.4 ms on sjc and 1.8 / 8.0 / 10.9 ms on fra (RT1: 2.0 ms avg).
- **GC:** 11.8 s of pause in 40 min of uptime, ~0.5 %.

Measured contributors:

1. **Prod TerraBase now shares both A1 hosts.** It was rolled to sjc and fra at about 02:20 Z. PSI shows cpu `some`
   15–19 % and io `full` 13–16 % on both hosts, plus 11–18 % steal and 13–22 % iowait on fra. A loopback GET on fra takes
   ~12 ms per poll (RT1: ~1 ms). This inflates all three stages and was absent in RT1's run.
2. **Possible code regression between `eec12aee` and `888ea413`: not proven.** On delta (loopback, two nodes, same
   harness) the interleaved pair at equal host load (6.6 / 6.8) gave p50 45 / 43 ms (old) against 55 / 204 ms (new). A
   first sequential run gave 22–57 ms against 170–363 ms. A bisect over the 6 TerraBase commits was abandoned when delta's
   load rose to 40–110 from other jobs; every arm then read 67–122 ms. Raw: `raw/local-ab/`. Candidates by path:
   - #399 `912f9737`: R9 Merkle digests on the write path.
   - #405 `a269d44f`: all-regions placement; platform databases replicate.
   - #376 `477414a2`: per-peer cursor isolation and envelope buffer reuse.
3. **Code points on this path that add waiting (file:line, main `888ea413`).** None explains a 47 ms floor at idle on
   its own:
   - `Features/Replication/PeerStreams.cs:703`: one batch per database in flight per link. The next write waits a full
     RTT for the previous ack. Only for back-to-back writes, so it is the under-load cost (RT1: +141 ms p50).
   - `Features/Replication/RemoteAckWaiter.cs:65` with `PeerStreams.cs:142`: the 201 is released by the first ack from
     any region. A batch to a slower peer can still hold that link's slot when the next write commits.
   - `Features/Replication/PeerStreamReceiver.cs:153-155`: a batch on B waits for any in-progress system-database frame:
     usage flushes every 10 s (`Features/Management/Usage/UsageFlushService.cs:29`), system frontiers every 5 s
     (`PeerStreams.cs:30`). The wait is an fsync, and it matches the p90 tails of the dest stages.
   - `Features/Replication/PeerStreamReceiver.cs:270-276`: a batch also queues behind the same database's frontier write.
   - `Engine/Sqlite/TursoChangeGroupSource.cs:41`: `TailRefresh` every 5 s takes each database's writer for a trim
     transaction. A probe commit that lands then waits for it.
   - `Engine/Sqlite/SqliteDatabaseStore.cs:371-374`: every write commit is `synchronous = FULL`, at the origin and again
     at the destination.

**To prove item 2:** run the bisect on a quiet host (load < 2), 3 arms per commit, or on the cell once the other lanes
release it. Each arm needs fresh data directories, since #399 changed the storage format.
