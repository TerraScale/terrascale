# SQL execute-only admission correction

## Current path and the failure

`QueryStore::compile` in `src/query/mod.rs:493-539` parses and validates the
SQL, then lowers only the single-collection live shape. Joins, aggregates,
windows, CTEs, subqueries, and `EXPLAIN` are retained as `SqlRuntime`, with
`tables` populated by `sql::table_names`.

`src/query/sql_execute.rs:121-229` opens the read-only SQLite connection,
installs the progress callback, begins a rollback transaction, calls
`check_input_bounds`, creates a temporary view for every runtime table, and
only then prepares and executes the user statement. `check_input_bounds` at
lines 300-327 counts every visible document and body byte for the whole
tenant. Consequently `SELECT ... LIMIT 1` against a selective collection is
refused as soon as unrelated tenant data exceeds 65,536 rows or 64 MiB.

The ordinary query executor already has the required bounded collection
interfaces: `Engine::snapshot_documents_in_collection_filtered` in
`src/engine/mod.rs:3181`, `StoragePort::collection_scan_filtered` in
`src/storage/mod.rs:1020`, and SQLite's implementation in
`src/storage/sqlite/mod.rs:6155-6205`. `query::execute::pushdown_filter` at
`src/query/execute.rs:931-981` produces a sound narrowing filter over active
extracted columns, while the executor rechecks the complete predicate.

## Correction seam

Do not use tenant-wide `check_input_bounds` for execute-only SQL. Add a
query-aware candidate-budget stage between `open_storage_connection` and
`create_collection_views`:

1. Extend the private `SqlRuntime` (in `src/query/sql.rs`) with a bounded list
   of per-table candidate filters. The list is derived from the already parsed
   AST and bound values in `compile_sql`; it is not reparsed from text at
   execution.
2. Extract only sound conjunctions of scalar comparisons whose operand is a
   literal or bound value and whose left side resolves to one base relation
   and one field. Push a condition only when its table alias maps uniquely to
   a `SqlRuntime::tables` entry. Do not push OR branches, negated predicates,
   join-to-join comparisons, subquery predicates, HAVING, window expressions,
   or predicates whose alias/table cannot be proven. A missing filter means
   “scan this relation”, never “return no rows”. Reuse the existing
   `ScanFilter`/`ScanCondition` shape and scalar type rules from
   `pushdown_filter`; this keeps extraction sound and avoids a second value
   coercion policy.
3. For each referenced table, perform a bounded candidate estimate over the
   requested snapshot: latest version per `(tenant, collection, id)`, then
   live/expiry filtering, then the extracted scalar narrowing. Return row and
   body-byte totals. The estimate must bind tenant, collection, sequence,
   expiry time, and values with rusqlite parameters. It must use the same
   “latest row wins before predicate” rule as `filtered_page_sql` (the comment
   immediately above that helper explains why filtering historical versions
   first is incorrect).
4. Reject only when the sum of candidate rows or candidate body/id/collection
   bytes for the referenced tables exceeds the existing input budgets. A
   query over a large unrelated collection therefore does not consume this
   query's budget. A query with no sound narrowing remains bounded by the
   existing limits and fails closed when its actual source set is too large.
5. Apply each sound filter to the corresponding temporary view after the
   latest-version/deleted/expiry boundary. The original SQL remains the exact
   evaluator, so pushed conditions may over-match but can never remove a row
   that the caller statement could return. Preserve `MAX_SQL_OUTPUT_ROWS`,
   `MAX_SQL_OUTPUT_BYTES`, `SQL_PROGRESS_INTERVAL`, `MAX_SQL_STEPS`, deadline,
   cancellation, and rollback behavior unchanged.

The estimate and view predicates should be generated by one private helper
(for example `sql_execute::candidate_scope_sql`) so they cannot drift. The
helper should return SQL fragments plus a `Vec<Value>` and quote identifiers
with the existing `quote`/`sql_string` discipline. Never interpolate a user
parameter into SQL text. Collection names and aliases must come from the
validated AST and pass the existing identifier validation.

This is deliberately an admission/narrowing change, not a general SQL
optimizer. Execute-only joins and aggregates still run through SQLite and may
scan their candidate views. The progress handler remains the hard VM-work
bound for shapes that cannot be narrowed.

## Discriminating regression

Add a `#[cfg(test)]` regression beside the existing execute-only binding test
in `src/query/tests.rs`:

* create one tenant with a small `users` collection and a second unrelated
  collection containing more than `MAX_SQL_INPUT_DOCUMENTS` visible rows (or
  enough body bytes to exceed `MAX_SQL_INPUT_BYTES`);
* execute an execute-only statement that references only `users`, for example
  `SELECT count(*) AS total FROM users WHERE age >= :minimum`, with a bound
  scalar parameter;
* assert it succeeds and returns the expected count;
* execute the same statement with an unfiltered reference to the oversized
  collection and assert `QueryError::CandidateBoundExceeded`.

The first assertion fails with the current tenant-wide preflight and proves
the fix is collection/query scoped. The second preserves the abuse guard. A
second useful case places the selective predicate on a collection that itself
has many unrelated rows and verifies the candidate estimate, rather than
tenant isolation alone.

Do not weaken the existing `sql_readonly_tests` connection guarantees or the
parameter tests in `src/query/sql.rs`; those already cover durable-write
rejection, numbered/bare slots, unused/unbound bindings, and MATCH bounds.

## Scope and verification

Implementation files should be limited to `src/query/sql.rs`,
`src/query/sql_execute.rs`, and focused query tests unless the existing
`ScanFilter` interface proves insufficient. No API contract change is
needed. Verify with the focused terrabase query test target and the existing
read-only/SQLite storage tests; then run the repository's required check at
the parent level.
