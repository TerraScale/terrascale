# Native multi-participant backup — Luna execution briefs (2026-09-08)

This is a planning/evidence note for `/root/backup_integration`; it does not establish acceptance. Product source remains owned by the implementation owners below. The shared Cargo lane is `/root/tb_check`; submit selectors and source cohort to that owner and do not run Cargo/builds in this lane.

## Accepted contract and current gap

The public outcome is one recoverable backup point for an admitted logical database whose shard participants were read at one common storage cut. The envelope binds logical database ID/incarnation, route generation, common cut, ordered participant IDs/physical IDs, and canonical manifest bytes/digests. Every participant archive and manifest must verify before one envelope is published. A participant, provider, staging, or durability failure leaves no discoverable complete envelope.

Current code already provides the envelope value/codec/manifest verification in `src/backup/envelope.rs`, public `BackupManifest::verify` in `src/backup/manifest.rs`, and a non-publishing assembly seam at `crates/terrabase-server/src/native_backup_runtime.rs:110`. `DatabaseLease::admitted_shard_read_cut` captures all admitted participants and snapshots under one publication gate (`src/member/mod.rs:1698`; cut types in `src/member/shard_registry.rs:30`). Existing `BackupPlan::snapshot_at` (`src/backup/mod.rs:555`) and `run_backup` (`src/backup/mod.rs:995`) pin a source boundary and atomically publish `rp-*` directories. The production caller still invokes one `fleet.capture_snapshot(database)` (`native_backup_runtime.rs:252`), so no common-cut multi-participant capture or durable envelope catalog exists. Restore currently reaches one-provider restore after suspension and target reservation (`crates/terrabase-server/src/production_data_runtime.rs:1257-1535`) and therefore does not validate an envelope/all participants before the serving switch.

## Brief A — `TB-BACKUP-CAPTURE-ENVELOPE`

**Outcome and real caller.** `NativeBackupRuntime::capture` (the native recovery/API caller) returns/publishes one envelope-backed point for the admitted logical database. The observable success is a restart-discoverable envelope whose every participant archive verifies and whose manifest cut equals the captured admitted cut.

**Write ownership.** Owner may write `crates/terrabase-server/src/native_backup_runtime.rs`, a narrowly scoped production backup composition adapter if needed, and focused tests/evidence adjacent to those files. `src/backup/envelope.rs`, `src/backup/manifest.rs`, `src/backup/mod.rs`, `src/member/*`, `runtime.rs`, `api.rs`, engine `branch_restore`, object-store protocol internals, and shared Cargo outputs are read-only dependencies. Do not alter `runtime.rs`/`api.rs` constructors without an explicit handoff; trace their existing `AdmittedDatabaseRegistry` composition and propose the smallest injected registry/lease seam. Tests, staging logs, and envelope fixtures count as owned writes.

**Chosen design.** Capture retains the admitted lease/host long enough to call `admitted_shard_read_cut`; reject absent route generation, empty/mismatched participants, or a changed current route. Derive the one common boundary from the cut and run one `BackupPlan::snapshot_at(common_cut, encryption)` per participant against its retained engine, using participant-private staging roots and existing database-bound backup keys/placement. Do not call the fleet’s unconstrained `capture_snapshot` for these participants: it chooses each stream’s current high-water independently. Verify each returned manifest against its participant `rp-*` archive (`BackupManifest::verify`/archive verification), then call `assemble_shard_envelope`; encode the envelope canonically and publish it only after all participant points and envelope bytes are durable. Publication must be a single atomic rename/commit marker under the configured private staging/catalog path, with directory/file fsync as required by the repository’s existing publication helper. Provider uploads/inventory must consume the committed envelope as one catalog item; individual `rp-*` points are not a complete multi-shard recovery point. On any error, remove only the private attempt tree and leave no envelope catalog entry; retry may reuse content-derived participant identities safely.

**Boundaries.** Preserve logical database/tenant/Region placement and the existing backup key capability. All participant IDs must be unique, canonical and ordered; all manifests must carry the same database incarnation, route generation and boundary. Bound participant count and aggregate bytes by existing fleet limits before reads; cancellation and process crash must leave an uncommitted orphan ignored by discovery. Never mark the frontier/protection state advanced from one participant. Avoid synthetic keys, local destinations, per-participant publication as success, broad exception swallowing, or compatibility fallback.

**Acceptance cases.** (1) Two admitted participants with writes before the captured cut produce one envelope; decode after reopening staging, verify every archive, and query restored data from both physical lanes. (2) A participant capture/manifest/checksum failure, provider upload failure, cancellation, or crash before commit leaves no discoverable envelope and does not advance complete protection. (3) Route generation/incarnation mismatch or a stale/foreign participant is rejected before publication. (4) Repeating the same operation after an interrupted commit yields one valid catalog item and no duplicate complete point. Tests must use the real `NativeBackupRuntime::capture` caller seam and staged files, not only `assemble_shard_envelope` in memory. Submit focused test selectors/source hash to `/root/tb_check`; no independent Cargo invocation.

**Dependency/decision.** Astra must choose the durable envelope catalog/object-store key and whether the envelope is a manifest sidecar in the existing provider inventory or a separate atomically committed object. The choice must preserve provider read-back verification and restart discovery; a filesystem-only marker is insufficient if restore selects remote points.

## Brief B — `TB-BACKUP-RESTORE-ENVELOPE`

**Outcome and real caller.** `ProductionDataRuntime::restore_native_with_workers` → `restore_native_to_target` must select and validate one envelope-backed point before target admission is resumed. A successful restore exposes logical routed queries/writes from every participant; a failed participant/envelope validation leaves the target suspended/unchanged and returns the existing redacted native restore failure.

**Write ownership.** Owner may write `crates/terrabase-server/src/production_data_runtime.rs` only if `/root/serving_fixer` hands off the overlapping serving boundary, plus focused restore tests in its owned test module. `native_backup_runtime.rs` restore adapter and `src/backup/restore/*` are separate owners unless explicitly handed off. `runtime.rs`, `api.rs`, engine `branch_restore`, and authority/grant code are read-only. The existing `reserve_restore`/rollback path and `NativeRecoveryRuntime` authority checks remain authoritative.

**Chosen design.** Resolve the selected envelope through the accepted provider/inventory catalog, decode strictly, verify logical source/target identity, placement, expected digest/boundary, route generation/incarnation and ordered participant set. Before `reserve_restore` or any serving publication, verify every participant manifest and every archive member using `BackupEnvelope::verify_staged` plus existing encrypted-chain/manifest verification. Restore each participant into its target physical location under one reservation/fenced suspension, then verify all target participant identities and routed readback. Only after all participants and the receipt authority checks succeed may `reservation.complete`, registry resume, and backup capture rebind occur. Preserve the original signed lifecycle grant; keep nonzero `restore_epoch` separate from lifecycle `authority_epoch`. A missing/corrupt/incomplete participant, envelope digest mismatch, stale route, foreign source, or provider read error must fail closed and retain rollback cleanup; never restore a single participant as a logical success.

**Boundaries.** Target remains paused and fenced throughout; no serving switch precedes complete decode, archive verification and participant restore. Restore retries retain operation identity and original grant; no synthetic receipt signer/key or local provider. Selection and expected manifest digest remain operation-bound. Recovery receipt is emitted only after all participant facts are durable and signer validation succeeds.

**Acceptance cases.** (1) A two-participant envelope restores into a fresh admitted target and a real routed query sees documents originating on both participants; a PATCH/write through the target remains visible after resume. (2) Corrupt envelope bytes, one missing archive member, one participant checksum failure, stale route generation/incarnation, foreign source/target, or provider outage leaves target unserved and no receipt. (3) Crash/failure after one physical participant restore rolls back or leaves a durable fenced reservation discoverable for reconciliation; it never resumes partially restored serving. (4) Retry with the same operation/grant is idempotent and does not mint a new authority epoch. Use existing native restore tests plus one real multi-participant integration fixture; send selectors to `/root/tb_check`.

## Confirmed recurring lesson

- **Cause:** The first implementation added only an in-memory `assemble_shard_envelope` seam while the real caller still used `fleet.capture_snapshot(database)`, which captures one stream at its own high-water. **Correction:** briefs require the admitted common read cut, per-participant pinned `snapshot_at`, archive verification, and a durable atomic envelope catalog through the actual capture/restore callers. **Prevention:** acceptance must reopen staged/provider state and exercise `NativeBackupRuntime::capture`; an unused helper or green unit codec test cannot establish multi-participant backup.
- **Cause:** Existing `run_backup` atomically publishes each `rp-*` directory, which can be mistaken for an atomic multi-shard point. **Correction:** treat those directories as participant artifacts and commit one envelope catalog only after all verify. **Prevention:** reject tests that label individual `rp-*` points complete and require a failure case proving no envelope is visible after one participant fails.
- **Authority distinction (confirmed from `qualification/restore-authority-fix.md`):** lifecycle grant/authority renewal is independent from the original signed restore grant and restore epoch. **Prevention:** restore briefs retain the original grant and test renewal/retry without equality against the latest observation epoch.
