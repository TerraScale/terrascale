# End-to-end volume qualification — 10M documents (2026-09-19)

Same harness as the 100k qualification, two orders of magnitude larger:
10,000,000 documents (lean random bodies, ~110 B: short unicode names, 1–3
tags, small payload, optional note, nested object) written in committed batches
of 5,000, verified by exact read-back, captured by one full backup plus one
incremental backup (8 publications), restored twice (full boundary and interior
PITR cut), and verified again document-by-document on reopened engines. All
four verifications reported 10,000,000/10,000,000 exact matches.

Two 10M runs exist for 2026-09-19: the morning run on the v2 zlib NDJSON
artifacts and the evening run on the v3 binary LZ4 artifacts (see
[`backup-optimization-20260919.md`](backup-optimization-20260919.md) for the
codec and format work between them). Both passed all four verifications
exactly.

Run with:

```text
nice -n 19 env DOTNET_gcServer=1 DOTNET_PROCESSOR_COUNT=8 \
  dotnet bench/TerraBase.Benchmarks/bin/Release/net10.0/TerraBase.Benchmarks.dll \
  --workload e2e-volume --documents 10000000 --batch-size 5000 --updates 8 \
  --seed 1337 --output <run>
```

Receipts: `bench/receipts/e2e-volume-10m-20260919/` (v2 run) and
`bench/receipts/e2e-volume-10m-v3-20260919/` (v3 run) — summary, receipt
JSON, both backup manifests, incremental artifact. Full snapshot artifacts and
engine roots were not retained.

| Full backup | 667.3 s | 652.1 s |
| Incremental updates (fresh engine open) | 95.6 s | 50.7 s |
| Incremental backup | 95.6 s | 50.7 s |
| Full-boundary restore | 519.5 s | 552.2 s |
| Full restore verify | 428.8 s | 392.5 s |
| Interior PITR restore | 549.5 s | 464.5 s |
| PITR restore verify | 442.4 s | 387.3 s |
| Full artifact | 749,261,827 B | 1,104,429,319 B |

Treat the v2→v3 column as **directional, not controlled**: the write phase —
whose code path the format work never touched — ran 42% slower on the evening
host, so shared-tenant load moved every number. The controlled comparisons
live in the optimization report (same-session microbench at 1M documents and
the 100k end-to-end run: full backup −25%, incremental −29%, restores −13 to
−21%). At 10M the phases are dominated by the engine's own replay and
materialization cost (~30 s per million documents), which no backup-side
change can shrink; the incremental-backup phase, whose fixed cost the cut
caching removed, halved.

## Fixes required to complete the run

Ten failed attempts preceded the passing run; each exposed a real defect or an
unbounded allocation that 100k never surfaced. Fixes are at the root, in
production paths, not in the harness.

1. **Snapshot artifacts could not be streamed.** The v1 artifact was one JSON
   object holding a 10M-element `documents` array: deserialization allocated
   the whole corpus as `JsonElement`s (>20 GB) and restore died before the
   first document applied. Artifacts are now zlib-compressed line-delimited
   JSON (`terrabase-storage-backup-snapshot-v2`): a header object on line 1,
   then one self-contained document record per line. Restore reads the header
   without touching documents, then applies lines in 4,096-record frames;
   memory is bounded by the frame, not the corpus.
2. **`Utf8JsonWriter(Stream)` never auto-flushes.** The first streaming writer
   buffered the entire 1.5 GB of JSON in a growing internal buffer and OOM'd.
   Per-record `JsonSerializer.Serialize` to the zlib stream (one line per
   record) replaced it. The same writer also rejects a second top-level value,
   so header and documents are written by separate serializers.
3. **Authority capture built a full in-memory record dictionary** (~5 GB at
   10M docs) before digesting anything. It now streams physical records in
   4,096-record batches (`StorageEngine.CopyBackupPhysicalRecords`) and relies
   on deterministic `StorageRecordCodec.Encode` for digests; peak capture
   memory is one batch.
4. **Snapshot capture held both the spool file and the full artifact byte
   array.** Capture streams into a temp-file spool and the artifact is read
   back once for upload; the spool is deleted in a `finally`.
5. **Engine open tripled the record list** (list + array copy + ToArray in
   `ReadAllRecordsUnsafe`). It returns the list directly now.
6. **Server GC created one heap per logical processor** — 46 heaps on this
   host, 17 GB RSS at 6M docs. The qualification pins
   `DOTNET_PROCESSOR_COUNT=8`; RSS dropped to ~3.3 GB for the same state.
   This is a runtime configuration note, not a code change.
7. **Restore pre-built every mutation before applying the first frame.**
   Mutations are constructed per-frame now (`ApplySnapshotDocumentsUnsafe`),
   so the 10M-element array never exists.

## Efficiency changes versus the first 10M-capable build

- Snapshot capture and restore are single-pass streaming over the spool /
   artifact; no corpus-sized JSON graph exists on either side.
- `physicalEncodedSizes`, a per-record size dictionary, was removed; the
   replication journal computes sizes on demand via
   `StorageRecordCodec.EncodedSize`.
- `SnapshotState` sorts collection identifiers lazily per snapshot and pages
   with binary search instead of re-sorting per page.
- Restore frames grew 512 → 4,096 records per atomic WAL frame (same fault
   semantics, 8× fewer fsyncs), matching the 100k qualification.

## Capacity notes (not defects)

- The engine's resident cost is ~1.4 KB per small document: the body is held
  twice (`Document` + `StorageLogRecord`), plus three dictionaries and two
  sequence indexes. 10M lean documents ≈ 14–17 GB RSS. Bodies scale the cost
  linearly beyond that floor. This is the current capacity limit of the
  all-in-memory engine design.
- The compressed full artifact is ~75 B/doc for lean bodies (749 MB for 10M);
   the incremental delta for 8 small publications is 105 KB.
- On a shared 31 GB host, only one phase's engine fits at a time; the harness
  reclaims between phases (`GC.Collect` + finalizers) and the run interleaves
  with other tenants. Peak RSS per phase was ~17 GB.

## Limits

- Single process, single host, local filesystem object store: no S3/OCI
  network transfer, multi-region recovery, or provider latency is qualified.
- Timings are from one run on a shared-tenancy host under `nice -n 19`; treat
  them as directional.
- The PITR cut applies one of eight publications; deeper chains are exercised
  by `native-restore` (8 entries, five samples).
- Crash drills (power loss during upload, manifest commit, materialization,
  pointer replacement) are covered by test suites, not this run.
